# v0.6.5 — 调度器自己把消息发出去了，而且拒绝得不含糊

上一版证明的是**操作者命令**能送达（`coord-uia`）。这一版动的是另一条代码：
`ui_fallback.run`——调度器和心跳真正走的那条路。它现在第一次自己把消息送进了
提权 Qoder 的会话，并拿回了挑战应答：

```
send_status: message-visible     send_retry: paste+enter     composer_clear_polls: 16
读回: AEP-ACK: C0F5868E719945    <- 反序校验串，比"回了句话"更强
```

顺带修掉四个缺陷，其中三个的共同点是**回执说的和事实相反**。

## 1. 「没发出去」被记成了「已输入」

`commander.provider_readback` 原来是一张**失败状态白名单**，其余一律落到
`INPUT_SUBMITTED`。实测四个明确表示「什么都没发」的回执全被记成已输入：

```
urgent-interject-unavailable  -> INPUT_SUBMITTED
composer-not-confirmed        -> INPUT_SUBMITTED
composer-confirmed-no-send    -> INPUT_SUBMITTED
LAUNCH_FORBIDDEN              -> INPUT_SUBMITTED
```

也就是说：每加一个新失败状态，它就自动变成一条「我发过了」的假证据。现在极性反过来——
回执必须**自己挣到** `INPUT_SUBMITTED`（`input_verified` / `composer_verified` /
`submitted-unconfirmed` 三者之一），否则是 `FAILED`，并把原始 status 留在 `error` 里。

## 2. 打不动就当场说，不要先烧掉 75 秒

`annotate_elevation` 早就在回执上写了 `drivable` / `blocked_by`，但**没有人据此行动**。
普通权限的执行器对着提权客户端会走完整个 UI 尝试，最后记成

```
CEASED  SUBMISSION_UNCONFIRMED: possible send; do not retry automatically
```

这是最坏的一种：花掉一分钟，还宣称「可能已经发出去了」——而 UIPI 保证了**一个字都没打进去**。

现在 `ui_fallback.run` 在观察到窗口之后、任何写操作之前就判定，并返回
`EXECUTOR_TOO_LOW` + `blocked_by: TARGET_NEEDS_ELEVATION`。`commander` 把它记成
`DEFERRED`（可续跑），不是 `CEASED`，note 直接给出操作动作：*start the executor elevated*。

两侧实测（同一份 profile、同一个窗口 pid 22796、同一个探针，探针里的 `deliver` 故意抛异常，
所以两种情况下都不可能真的打字）：

| 执行器 | state | capture 次数 | deliver 次数 |
|---|---|---|---|
| 普通权限 | `EXECUTOR_TOO_LOW` / `TARGET_NEEDS_ELEVATION` | 0 | 0 |
| 管理员 | 通过闸门，走到 deliver 才被探针拦下 | 1 | 1 |

闸门是**有判别力**的，不是一律拒绝。

## 3. profile 里的会话标记和真实窗口不一致（这是无人值守的真阻断）

调度路径比操作者命令严格：它要先验证会话和模型，才允许输入。实测提权跑一次，卡在

```
SESSION_LABEL_NOT_UNIQUE_IN_SIDEBAR: 0
```

核对真实读回（74,891 字符）后：

```
'赛事守冠执行'  -> 0 次     <- profile 里写的
'赛事夺冠执行'  -> 5 次     <- 窗口里真的
'FlagGems-sgIang' -> 0 次   <- profile 里写的（OCR 混淆）
'FlagGems-sglang' -> 8 次   <- 窗口里真的
```

一个字的差别（守 / 夺）加上一个 OCR 混淆（I / l），让**每一次**调度都在会话校验处
`DEFERRED`，而且永远等不到「ready」——从外面看只是一条卡住的任务。profile 已按实测改正。
同时 `SESSION_NOT_VERIFIED` 回执现在写出它找的是哪个字符串、找到没有、读回多少字符：
标记写错和会话消失从此可以区分。

## 4. `transport: ocr` 已经不是该走的通道

改对标记后，同一份 profile 仍然失败在

```
send_status: composer-not-confirmed
```

即 OCR/几何兜底的 compose 通路读不回输入框内容，于是拒绝按 Enter（这是对的，它没有硬发）。
而 uia 通路（无障碍树 + `ValuePattern`）在同一天早些时候已经把消息送进同一个会话。
`transport` 改为 `uia` 后，同一段代码、同一份 profile 立刻得到
`message-visible` + `paste+enter` 重试成功。

无障碍树能建起来（`SPI_SETSCREENREADER`）之后，OCR 只该是退路，不该是默认。

## 5. 「已送达」不能因为「没回话」被抹掉

调度引擎自己也有同一类假阴性：消息 `message-visible` 之后等回复，超时后回执里
`task_delivered` 仍是初始的 `false`。已送达和已接受是两件事，现在分开写：
`task_delivered` 来自发送回执，`agent_accepted` 只认目标自己的应答。
状态名也从 `REPLY_TIMEOUT_UNCERTAIN` 改成 `NO_REPLY_WITHIN_TIMEOUT`——它只陈述确定的事实，
不再暗示送达与否。

实测：探针 20:54 发出，引擎在 60 秒窗口内没等到回复，20:55 会话里出现了

```
AEP-ACK: C0F5868E719945
```

正是那次的 `expected_ack`。**送达和应答都发生了，只是应答比窗口晚。** 因此
`reply_timeout_seconds` 由 60 提到 120（有实测依据的调参，不是为了让测试变绿）。

## 仍然没做到的

- **迟到的应答没有被回收**：`NO_REPLY_WITHIN_TIMEOUT` 之后，没有任何只读步骤会去
  读回那个 `expected_ack` 并把订单升级成已接受。现在只能靠人再看一眼。
- `--urgent-interject` 仍未在真实忙碌会话上验过。
- `TASK_RESULT_READBACK`：能读回屏幕文本，没有「按任务号判定完成」的读取器。
- `codebuddy_cn` 未实测；跨机联邦未做。
