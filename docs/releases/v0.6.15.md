# v0.6.15 — 「没有 ACK 不得推进」从阻断条件降级为记录条件

v0.6.10 立的规矩是：订单已发出、对方没回 ACK，任务就不许完成，下游不许启动。
v0.6.13 给这个「等」加了出口（签字放弃），v0.6.14 让它超限时有人看见。
但**阻断本身没有例外**——而现实里例外的成因不止一种：

- adapter 根本不能报 ACK（客户端没有可读回执）；
- 会话被人关掉了；
- 客户端不渲染那条回复，ACK 在物理上不存在。

这三种情况下「没有 ACK」都不等于「活没干」。原来的规则把它们全部钉在 `running`，
在无人值守下就是静默死锁。

**这一版按用户指令放宽：默认不再阻断。**

## 1. 两个策略，不是一个开关

```
step(..., ack_policy="record")   # 新默认：推进，并把判定写进回执
step(..., ack_policy="enforce")  # v0.6.14 行为：保持，不推进
```

只有两个值。**没有第三个「N 分钟后放行」**——那正是 v0.6.13 明确否掉的东西：
定时器不是判断。放宽的形态是「换一种判据」，不是「给同一个判据加个闹钟」。

`"enforce"` 保留，不是为了向后兼容，是为了**让放宽这件事本身可被测量**。
一个只能放宽、无法回到严格模式的实现，没法回答「放宽之后我们丢了什么」。

## 2. 放宽的是阻断，不是记录

这是本版唯一需要守住的东西。**任务可以推进，但回执必须说清楚它是在没有 ACK 的情况下推进的。**

`_ack_blocks()` 原本用 `None` 表示「可以推进」，把三件完全不同的事压成了一个值：

| 事实 | 原来 | 现在 |
|---|---|---|
| 对方回了 ACK | `None` | `{"verdict": "clear", "reason": "acked"}` |
| 订单从未发出 | `None` | `{"verdict": "clear", "reason": "not_sent"}` |
| adapter 不能报 ACK | `None` | `{"verdict": "clear", "reason": "no_ack_support"}` |
| 已发出、无 ACK | `{"verdict": "hold"}` | 同左 |

在 `enforce` 下这四者的差别不影响推进，所以 `None` 够用。在 `record` 下它们**全都推进**，
回执是唯一的区别所在，而 `None` 装不下任何区别。于是「我们核实过对方回话了」
和「根本没人能回话」原本无法区分——这正是本项目一直在修的那类缺陷。

现在每一次完成都带 `ack`：

```json
"closed": [{"task": "execute", "action": "complete",
            "ack": {"verdict": "hold", "reason": "no_ack", "state": "sent_unacked",
                    "sent_at": "2026-11-01T14:49:39.297217+00:00",
                    "unacked_for_seconds": 22}}]
```

`ack.verdict == "hold"` 出现在一条 `complete` 上，就是「它推进了，而且它说了」。
另外返回值新增 `released` 桶：`closed` 里一条放行完成和一条干净完成只差一个字段，
`released` 让不想解析每条回执的观察者也能看见。

## 3. 什么没有放宽

**人签字的放弃照旧阻断。** `abandon` 不是「没有 ACK」，它是**另一种证据**——
一个人的决定。放宽一个缺失的确认，绝不能顺带放宽一个签字，否则「我们放弃了」
会变成「它完成了」。这一点在 `_settle` 里写在注释上，并有测试守着
（`test_a_human_abandonment_still_blocks_under_the_record_policy`）。

**确凿矛盾照旧阻断。** `match is False` 是**指向工作的证据**（agent 说产物是 A，
会话里说的是 B）；缺失 ACK 只是**关于投递的证据不足**。把两者一起放宽，
等于用「投递不可证」的宽松去掩盖「产出对不上」的严重。

## 4. 代价：`record` 下不再有超限告警

v0.6.14 的 `hold_alerts` 是给「卡住的任务」报警的。`record` 下任务不卡了，
`held` 恒为空，于是**一封告警也不会发出**。

这是放宽的真实代价，不是细节：**可见性换来了流动性**。想两者都要，就用 `enforce`。
把它写进发布说明而不是留给人自己发现，因为「什么都没发生」和「功能没接线」
在日志里长得一模一样。

测试 `test_no_alert_is_raised_because_nothing_is_stuck` 断言的是这个**沉默**
（并且断言 `released[0].over_limit` 为真，证明不是「没算出来」而是「算出来了但不报」）。

## 5. 实测（真实 CLI，临时工作区，非真实订单）

同一份夹具、两个全新工作区，只改 `--ack-policy`：

| | `record`（默认） | `enforce` |
|---|---|---|
| `held` | `[]` | `[execute / hold_unacked / over_limit=True]` |
| `released` | `[execute / released_unacked / no_ack]` | `[]` |
| `closed` | `[execute / complete]` | `[]` |
| `alerts.count` | `0` | `1`（收件人 `kernel`） |
| `execute` / `review` | `done` / `running` | `running` / `pending` |

`record` 那一行的完整 `ack`：
`{verdict: hold, reason: no_ack, state: sent_unacked, unacked_for_seconds: 22}`。

「不告警」不是从 `alerts.count` 推的，是查了盘：

```
record  工作区: coordination/messages/           不存在（没有写出任何文件）
enforce 工作区: coordination/messages/kernel/20261101T145009127101Z-cab5d539.json
```

`alerts.count == 0` 只能说明函数返回了 0；目录不存在才说明**真的没写**。

CLI 入口：`aep federate step|serve --ack-policy {record,enforce} --hold-limit-seconds N`
（`--hold-limit-seconds 0` 表示完全不告警，即 v0.6.14 之前的形态）。

## 6. 同时推进的其他三项

### 6.1 回读的会话守卫终于接线了

v0.6.14 发布说明里写着「会话守卫没接线，`session_checked` 如实写 `False`」。
这一版接上了：`_result_blocks` 从订单里取 `session_id` 作为锚点，
`observe(events, session_id=...)` 只比那个会话的行。

三件事同时落定：

| 字段 | 含义 |
|---|---|
| `session_checked` | 给了锚点，**且**确实有行经过守卫 |
| `session_unknown` | 给了锚点，但有可比较的行**不带**会话 id |
| `session_reason` | `applied` / `session_unknown` / `not_requested` |

**一条旧的判定被推翻**：异会话里出现了这个产物，原本判 `False`（矛盾）。
现在判 `None` + `reason=foreign_session`。理由：`False` 的定义是「有正面证据证明声称是错的」，
而异会话里有这个产物恰恰说明产物**存在**——缺的是归属，不是产物。
把一个可能真实存在的产物判成矛盾并阻断，会卡住一个活其实干完了的任务。
`foreign_session` 这个名字**保留**，只把 verdict 从 `False` 改成 `None`，
因为「异会话」和「本会话什么都没说」成因不同、处置也不同。

**同一类推翻还有一条**：事件不带 `session_id` 时，原本「抓取缺口不算异会话，所以照算一致」。
这是把「不知道」读成「知道」。现在判 `None` + `session_unknown`。

**一处信息丢失，接线时才发现**：锚定会话里有一条 ACK 行（可归属、但不带产物），
异会话里有那个产物——判定走到「转录里没有结果」就返回了，把
「产物找到了，在别的会话」丢成「什么都没有」。已修：报 `no_result_in_transcript` 之前
先看 `rejected` 里有没有 `foreign_session`。这条是**集成时才暴露的**，
模块自己的 25 项测试一条都没覆盖到。

`match` 与 `session_checked` 回答两个不同问题，故意不合并：
前者是「说的和记录一致吗」，后者是「比较锚定到那个会话了吗」。
订单没有 `session_id`（磁盘上 24 张真实单里有 6 张）时，`match` 仍可为 `True`
而 `session_checked` 为 `False`——把两者压成一个字段，要么丢掉真实的吻合，要么夸大它。

### 6.2 被放弃的任务可以复活

`engine.revive(root, state, task_id=, reason=, actor=)`：把**因放弃而** `blocked` 的任务
拉回 `running`。`reason` 与 `actor` 必填（和 `abandon` 一致：没有理由的复活不是记录），
只接受 `blocked`，重复复活幂等并保留第一次签名，记 `task_revived` 事件，
**不删**原来的放弃记录。

**下游也要跟着活**：`_tick` 会把依赖失败/阻断的任务置 `blocked` 且永不复查。
只复活上游会让下游永远停在 `blocked`，note 里还写着「blocked by ['execute']」而
`execute` 明明在跑——一条说假话的记录。所以 `revive` 会按 `blocked_by_deps`
把「所有依赖都活了」的任务重开，跑到不动点为止（阻断会沿链传播）。
只重开带 `blocked_by_deps` 的任务，所以认领冲突、拒绝等其它原因的 `blocked` 不会被误放。

CLI：`aep federate revive --workspace <id> --task <id> --reason <text> --by <name>`。

实测（真实 CLI，临时工作区）：

```
放弃后        execute=blocked  review=blocked
revive 之后   execute=running  review=pending   note='reopened: execute was revived by love'
              abandonments=[{by:love, reason:'client wedged',
                              revived_by:love, revived_at:..., revive_reason:'the client came back'}]
第二次 revive already_revived=true，revived_by 仍是 love（第一次签名），不是后来的 someone
复活 pending 任务  protocol error: only a blocked task can be revived; this one is pending
```

`abandonments` 里**签字和复活并存**，不是后者覆盖前者——这是「不删事实」原则在这一项上的落点。

### 6.3 迟到 ACK 不再撤销人的签字（本版最严重的一个）

v0.6.14 发布说明把这条写成「迟到 ACK 仍会把订单从 `ABANDONED` 升成 `AGENT_ACK`
而任务停在 `blocked`，两者会不一致，需要人收拾」。**实际情况比这严重得多。**

链路是这样的：`check_acks` 把订单 `state` 覆盖成 `AGENT_ACK` →
`ack_protocol.abandoned()` 只在 `state == ABANDONED` 时返回签字，于是返回 `None` →
`_ack_blocks` 跳过放弃分支 → `may_advance()` 返回 `True` → **任务被完成成 `done`**。

也就是说：**一个人的签字被一条迟到的机器事件静默撤销，撤销之后任务反而完成了**——
和 `abandon` 承诺的「后果是 blocked，永远不是 done」正好相反。
这不是「两者不一致需要人收拾」，这是自动流程把人的决定推翻了。

修法不是删掉那条 ACK（它也是真发生的事实），而是**两条都留下**：

- 订单 `state` 保持 `ABANDONED`，`abandoned()` 照常返回签字；
- 迟到的回复写进订单的 `late_acks`（按 `event_id` 幂等，append-only），
  `verdict` 里新增 `late_ack` / `late_acks` 两个字段；
- `may_advance()` 额外加一条：有签字就返回 `False`，即使 `accepted is True`。

实测（`.probe_late_ack.py`，临时协作区）：

```
abandon 后        state=abandoned  accepted=False
迟到 ACK 之后      check_acks acked=[]   order state=ABANDONED   abandoned_by 仍是 love
verdict           acked / accepted=True / abandoned={by:love,...} / may_advance=False
```

**「机器事件不得撤销人的决定」现在是 `may_advance` 里的一条明文规则**，
不再是靠调用顺序碰巧成立。

## 7. 仍未做

- `enforce` 下「没有 ACK 不得推进」仍可被一次 handoff 绕过（`engine.tick` 在两步之间
  生成第二张从未发送的订单，下一轮 `sent: False`、hold 合法消失）。**未实测**。
- `revive` 只处理「因放弃而 blocked」。因 `scope_conflict` / `refusal` 而 blocked 的任务
  仍然只能人工处理——这是有意的，但意味着 `revive` 不是万能的「恢复」按钮。
- 回读的 `match is None` 的完成仍然不要求人复核。
- `ack_tracker`（租约式 ACK）仍未合并（见 v0.6.14 的调查文档）。

### 并行协作的诚实记录

本版两个独立方向由两个 subagent 并行产出，集成与验证由主进程做。按上一版立的规矩，
**每个 subagent 声称的事实都自己复跑或独立核算过**，其中三项查出问题：

1. **「迟到 ACK 只是不一致」是低估**。我核了链路（`abandoned()` 只在 `state == ABANDONED` 时返回签字），
   确认实际后果是「签字被撤销 → 任务被推成 `done`」，比 v0.6.14 写的严重一级。
2. **「`judge` 能区分 `foreign_session`」只在没有其它可归属行时成立**。集成时构造
   「锚定会话有 ACK 行 + 异会话有产物」，判定直接落到 `no_result_in_transcript`，
   理由丢了。模块自己 25 项测试一条都没覆盖这个组合。已修并补测试。
3. **我自己写的一个缺陷**：`released` 行原本在矛盾闸门**之前**追加，于是
   「无 ACK + 产物矛盾」时 `released` 会声称一个没发生的推进。已修，并做了回退验证
   （把顺序改回去，测试确实报 `released` 多一行）。
