# v0.6.13 — 给「等」加一个出口，但不给「推进」加一个定时器

上一版让 `supervisor` 在「已发送但没有 ACK」时扣住任务。这个机制是对的，
但它有一个我在发布说明里自己写下的缺陷：**hold 没有上限**。一个永不 ACK 的 agent
会把任务永久钉在 `running`，下游永不启动，而回执里除了 `hold_unacked` 什么都没有。

无人值守系统里，这不是「谨慎」，是**静默死锁**。

## 错误解法先排掉

最自然的修法是「超时就当失败，换人重发」。这会把整个保证删掉：

> 没有 ACK 不得推进 → 没有 ACK，等 N 分钟后推进

一旦「等」有保质期，这个规则就退化成一张时间表，而不是一条判据。
而「换人重发」更糟：它假设第一次**没送到**，但我们并不知道——那正是 `CEASED`
里 `SUBMISSION_UNCONFIRMED` 说的「可能已经发出去了」。

所以这一版**不动推进条件**，只做两件事：让等变得**可见**，让结束等变得**需要签字**。

## 1. 让等可见

`held` 里现在带：

| 字段 | 含义 |
|---|---|
| `unacked_for_seconds` | 这张单从发出到现在等了多久 |
| `sent_at` | 发出时刻（来自判定，不是另外读一遍订单） |
| `limit_seconds` | `step(..., hold_limit_seconds=)` 传进来的上限，没传就是 `None` |
| `over_limit` | 是否已超限 |

**超限什么也不做，只是把话说出来。** 这是刻意的：`over_limit: true` 是给人看的
报警，不是给机器看的触发器。测试 `test_crossing_the_hold_limit_reports_it_without_advancing`
专门断言超限之后任务仍是 `running`、`closed` 仍是空——否则「上限」就成了新的推进条件。

`sent_at` 由 `ack_protocol.verdict` 一并返回，而不是让 supervisor 另外去读订单：
两处各读一次，迟早会不一致，而那时谁对谁错无法判断。

## 2. 让结束等需要签字

```bash
aep --coord-root coordination coord-ack --order-id <id> \
    --abandon --by love --reason "qoder 客户端卡死，今天不再等"
```

`--reason` 与 `--by` **都是必填**。缺 reason 时：

```
protocol error: a reason is required: 'we gave up' is not a record
```

三条硬规则：

1. **结果是 `blocked`，绝不是 `done`。** 放弃投递不是工作完成的证据。
   一个因为操作者不耐烦而被标成 `done` 的任务，正是这套协议存在的理由。
2. **不走 `fail_task`。** `fail_task` 问的是「谁接下一个」，而放弃问的是「别等了」。
   转交给后继者等于重发，正是放弃要排除的那个动作。
3. **已 ACK 的订单不许放弃。** 记录里有一个真实答案，用「我们放弃了」把它盖住是降级。

重复放弃是幂等的，且**保留第一次签名**——第一次是决定，第二次是重试。

## 3. 实测（`.tools/abandon-demo/`，临时协作区，不碰真实订单）

```
放弃前:  state=sent_unacked  accepted=False  sent=True   delivery=proven
放弃:    state=abandoned     accepted=False  sent=True   delivery=proven
         abandoned={by: love, at: 2026-11-01T09:57:32Z, reason: "qoder 客户端卡死，今天不再等"}
再放弃:  already_abandoned=True, 仍显示 by=love 与第一次的理由
```

`supervisor` 侧的实测（`test_an_abandoned_order_blocks_the_task_and_downstream_stays_pending`）：

```
第一次 step → held: [{action: hold_unacked}]
放弃后 step → closed: [{action: abandoned}]，held: []
              execute: blocked（不是 done）
              review : blocked，note 含 "blocked by"
```

下游不是停在 `pending` 等着——引擎既有的传播把它标成 `blocked` 并写明原因，
所以「为什么这一步永远不会开始」也是一个字段。

## 4. CLI 实测抓到的缺陷：放弃把「已经发出过」抹掉了

第一次跑 CLI 实测，输出是：

```json
"state": "abandoned", "sent": false, "delivery": "none"
```

**这张单明明是 `MESSAGE_VISIBLE` 发出去的。** 原因：`_record_attempt` 会把
`order["state"]` 覆盖成 `ABANDONED`，而如果那条 `MESSAGE_VISIBLE` 只存在于
`order["state"]` 而不在 `attempts` 里（手工构造或更老的记录），`delivery()`
就再也看不到它。

一个动作删掉了一条事实——和 v0.6.11 修的是同一类错误，只是这次是我在同一个版本里
刚引入的。修法：放弃前把原状态记进 `state_before_abandon`，`delivery()` 把它当作
一个候选来源。修后同一条命令输出：

```json
"state": "abandoned", "sent": true, "delivery": "proven"
```

守卫：`test_abandoning_does_not_un_send_the_message`、
`test_the_state_before_the_sign_off_still_proves_the_send`。

## 5. 这一版仍然没有解决的

- **上限只是报告，不是策略。** 谁在什么条件下该收到 `over_limit` 报警，本版没写
  （没有告警通道，`held` 只在 `step()` 的返回值里）。7×24 运行需要有人读它。
- **放弃之后不能复活。** 订单停在 `ABANDONED`，任务停在 `blocked`，
  没有任何「重新打开」的路径。要重做只能新建任务。
- **迟到的 ACK 仍会升级订单。** `check_acks` 只跳过 `AGENT_ACK`/`FAILED`/`RETIRED`，
  所以 `ABANDONED` 的单在收到真回复时会变成 `AGENT_ACK`，签名记录保留。
  这是有意的（「迟到回复必须被接受」），但意味着**放弃不是不可逆的**，
  而任务仍停在 `blocked`——两者不一致，需要人来收拾。
- 会话内容不进指纹、`ack_tracker.py` 未合并、`TASK_RESULT_READBACK` 未实现，
  这三条与 v0.6.10 相同。
