# v0.6.24 — 怎么完善桌面投递：先补确定性预检，不急着改活路径

操作员问「怎么完善桌面投递呢」。本版的回答不是再造一个发送器，而是先量出两个真实断口，
补上第一块地基，并把后续路线写成可复算的分期。

## 1. 现状：手脚能发，但「发之前能不能发」没人回答

桌面投递链路本身是通的：`commander.tick` → `dispatch` → `_dispatch`
（`_dispatch_lock` / `_preinput_retryable` / `_mark_dispatching` /
`session_fingerprint.compare` / `_gate_refusal` / `_pick_transport`）→
`_profiled_deliver` 或 `_uia_deliver` → 回执 → `AGENT_ACK` / `MESSAGE_VISIBLE`。
Qoder 双构建的「粘贴 → 强制回车 → 等待插话控件 → 点击」在 11-05 有真机回执。

但两个断口很硬：

1. **投递前没有确定性结论**。`desktop-preflight.ps1` 只查 client 注册、exe 与窗口数；
   `probe_uia.ps1` 只答「树可不可读」；`coord-uia observe` 回执字段齐全
   （`input_found / input_region / activity_state / session_marker_check`），
   但 `commander._uia_observe()` 是**死代码，src 内零调用方**；
   `dispatch_gate.check` 是纯文本闸门；`input_routing.delivery_verdict()` 本来
   能给出 `send / send-after-verification / defer`，却只在 `coord-route` 离线重放里用。
   ⇒ 这就是上一轮「只读观察拿不到可判定结果，所以不投递」的根因。
2. **投递后复算没有消费者**。`action_verification.from_send_report()` / `verdict()` /
   `provider_readback()` 全是「有代码无消费者」，`commander._dispatch` 直接读
   `task_delivered` 布尔 —— 侧栏编辑器曾误报 `task_delivered=true`、毁掉 112 行仍缺闭环。

真机证据也薄：11-05 全部 `uia_receipts` 最高到 `message-visible`，
`agent_accepted` 全为 `false`、无一 `AGENT_REPLY_VERIFIED`；
`last-codebuddy_cn.json` 是 `input_found=false / transcript-unreadable`；
1452+ 个测试无一真机打字，投递路径全靠 mock 与 `.ps1` 源码文本断言。

## 2. 完善路线（这是本版给出的主答案）

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| **P0（本版）** | 只读预检 + 回执第二意见 | 不打字、不改活路径、复用 `delivery_verdict`、复算 `advisory_only` |
| P1 | 真机单条无害挑战串（qoder 已验证通道） | 四项检查字段齐全、`verified=true`、转写回读 + 见证人三条件一致 |
| P2 | 把 `from_send_report/verdict` 接进 `_dispatch` 作为**并列字段**（先不替换布尔） | 布尔与复算不一致时显式报出，不静默 |
| P3 | 复活 `_uia_observe()`，在输入租约前调用预检 | 每次真发前有 `DEFERRED` 拦截记录，且不增加重复投递 |
| P4 | 补测未复测客户端（codebuddy_cn / workbuddy3 / chatgpt 忙碌插话） | 每个 profile 有当日真机回执，再决定是否放开 `interject_after_send` |

**为什么不能直接跳到 P2**：真机上从未有一次 `AGENT_REPLY_VERIFIED`；
4 项检查字段在旧适配器回执里缺失，改活路径会让历史订单被判 `unknown` 大面积停摆
（`verdict()` 对缺失检查返回 `None`，不猜）。项目规则也不允许靠未实测路径替换既有闸门。

## 3. 本版落地：P0

新增 `coordination/delivery_preflight.py`，**纯只读**，读磁盘上已有的四类事实：
`ui_profiles/<agent>.json`（transport / session_marker / interject_after_send）、
`clients/<agent>.json`、`uia_receipts/last-<agent>.json`（观察回执）、
`desktop_health.json`（窗口枚举熔断）。

- 复用既有 `input_routing.delivery_verdict()`，**不造第二套判定**；
  因为预检从未输入过，`needs_verification` 恒真，最好的诚实结论也是
  `send-after-verification` / `READY_UNVERIFIED`，不是「可以发」。
- 硬闸门 fail-closed：`PROFILE_MISSING` / `OBSERVE_MISSING` /
  `CAPTURE_ONLY_RECEIPT` / `TRANSCRIPT_UNREADABLE` / `SESSION_MARKER_NOT_SEEN` /
  `INPUT_NOT_FOUND` / `INPUT_REGION_MISSING` / `ACTIVITY_UNKNOWN` /
  `ACTIVITY_BUSY` / `WINDOW_ENUMERATION_DEGRADED`。
  `CLIENT_NOT_REGISTERED` 只作警告（commander 用 `registry.profile` + `discover`）。
- `route` 由 profile 的 `transport` 推导；运行时才能发现的 CDP 路径**不猜**。
- `postflight()` 用 `action_verification.from_send_report()` + `verdict(required=四项)`
  复算发送回执，`advisory_only=true` 恒真，明确写着 commander 仍读布尔。
- 硬边界 `ui_input_performed=false` / `models_loaded=0` / `processes_started=0` /
  `deployment_performed=false` / `system_tasks_registered=false`；源码不出现任何
  外部适配器或输入 API，有 AST/文本守线；**不新增 `coord-*` 命令面、不新增 schema**。

## 4. 只读预演实测（5 个 profile，零写入、零输入）

| agent | route | readiness | missing |
|---|---|---|---|
| chatgpt | uia | **READY_UNVERIFIED** | 无 |
| qoder | uia | DEFERRED | `CAPTURE_ONLY_RECEIPT` |
| qoder_cn | uia | DEFERRED | `CAPTURE_ONLY_RECEIPT` |
| codebuddy_cn | ocr | DEFERRED | `TRANSCRIPT_UNREADABLE`, `INPUT_NOT_FOUND`, `INPUT_REGION_MISSING`, `ACTIVITY_UNKNOWN` |
| workbuddy3 | ocr | DEFERRED | `SESSION_MARKER_NOT_SEEN`, `INPUT_NOT_FOUND`, `INPUT_REGION_MISSING`, `ACTIVITY_UNKNOWN` |

注意：`qoder` / `qoder_cn` 当天明明有真机投递成功回执，但它们的 `last-*` 文件是
**capture** 回执，不能当预检证据 —— 预检如实报 `DEFERRED`，而不是拿旧成功当放行。

**真机回执第二意见**（`AEP-INTERJECT-20261105-04-qoder.json`）：

```text
declared_task_delivered : True
verified                : None   (MISSING_CHECK)
checks                  : 0
missing                 : text_visible_before_send, text_arrived,
                          text_left_composer, composer_emptied
advisory_only           : True
```

回执里有 `composer_cleared` / `event_witness` 等字段，但**没有** `SEND_REPORT_CHECKS`
契约要求的四项。按项目自己的规则，布尔不是证据；也说明 P1 必须先让适配器产出
契约内字段，P2 才谈得上切换。**本版刻意不把 `composer_cleared` 硬映射成检查项** ——
那等于放宽别人的验收契约来让自己通过。

## 5. 顺手修掉上一轮承诺的缺陷

`legion_announce.plan()` 动态推导的收件名单会把发起者自己算进去
（`coord-send` 会拒 `sender == receiver`）。现在动态名单与显式名单都排除 `source`，
命令说明补上「已自动排除」，并为两条路径各加了测试。

## 7. 明确未做

- 没有执行 `coord-uia deliver` / `compose` / `--urgent-interject` / `coord-commander tick`；
  没有聚焦窗口、打字、点击、粘贴，没有启动适配器或模型；
- **没有改 `commander._dispatch` 的判定**，没有把 `_uia_observe()` 接进活路径；
- 没有自动判定 UIPI / 执行器完整性级别（真发前仍需操作员确认，执行方 IL 必须 ≥ 目标）；
- 没有给未复测客户端放开 `interject_after_send`，没有注册 OS 任务或常驻进程；
- 不承诺 7x24 无人值守，不宣称「代替人类工程师」，不追踪积分/额度。
