# v0.6.34 — 每客户端桌面可操作性探针与原子 READY 握手

## 解决的问题

“桌面 provider 已安装”“能列出窗口”“快照有一个 ref”都曾被误读成可以向
原会话派工。它们不是同一件事：一个 Electron 客户端可能只暴露标题栏，或根本
没有把 composer/发送按钮暴露给 UI Automation。

v0.6.34 把这种差异变为每个 Agent、每个 provider 的只读事实，而不是调度器的
猜测；同时修复 improvement watcher 的 READY 发布竞争，使“已就绪”不再短暂
暴露空文件。

## 新能力

### `coord-desktop capability-probe`

```powershell
aep --coord-root coordination coord-desktop capability-probe `
  --agent qoder --provider agent_desktop --timeout 4
```

该命令：

1. 以 roster 的唯一 `PID + title` 对齐 `agent-desktop` 的
   `window_id + process_instance`；
2. 分别观察普通 UIA 与 Electron 辅助树；
3. 只保存最小化证据（状态、ref 数、编辑器/发送候选数、短错误码），不保存
   聊天文本或整棵可访问树；
4. 输出 `TREE_USABLE`、`TREE_PARTIAL`、`TREE_OPAQUE`、`TREE_TIMEOUT`、
   `WINDOW_NOT_BOUND` 等明确状态；
5. 永远不聚焦、不输入、不点击、不发送。

`TREE_PARTIAL` 特别用于“有 ref 但只有 title bar/group”的情形。它不再被误报
为可写通道。即便 `TREE_USABLE`，结果也只能是 `SESSION_UNATTESTED`，直至同一
原会话完成消息可见、目标 ACK 和结果读回。

探针证据保存在：

```text
coordination/desktop_providers/capabilities/agent_desktop--<agent>.json
```

### 无人值守 watcher 的 READY 原子发布

`scripts/watch-improvements.ps1 -ReadyFile <path>` 现在先把 JSON 写入同目录临时
文件、`Flush(true)`，再原子移动到 `<path>`。消费者只有在完整 JSON 可见后才会
向 watcher 投递事件。这把“进程启动”与“已能消费事件”分开。

### 接入文档同步

`coord-desktop` 现在具备 parser-level description，生成的
`docs/coordination/SKILL.md` 会明确告知接入 Agent：capability probe 是只读动作，
不应把它当作发送或 ACK。

## 可复核验证

- 5 个本机目标客户端完成只读 probe；当时均未发现可证明的 composer 输入候选，
  因此没有执行任何输入或发送。
- `tests/test_improvement_spool.py::SpoolTests::test_live_watcher_receives_event_and_stops`
  连续运行 3 次通过。
- 发布前完整套件：**1696 passed, 3 skipped, 1017 subtests passed**。

## 明确不声称的内容

- 不声称 `agent-desktop` 已能向 Qoder、Qoder CN、WorkBuddy、WorkBuddy AI 或
  CodeBuddy CN 自动输入或发送；本机实测仍要求走客户端特化的 CDP、官方接口，或
  已标定的严格 UIA/OCR 路线。
- 不把 `TREE_USABLE`、窗口发现、输入完成、或 CLI exit 0 视为
  `MESSAGE_VISIBLE`、`AGENT_ACK` 或 `TASK_RESULT_READBACK`。
- 不替代 AEP 的严格原会话 attestation、共享 session lease 和五段验收链。
