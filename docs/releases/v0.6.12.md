# v0.6.12 — 一条太紧的护栏，让「全量通过」变成掷硬币

纯测试改动，产品代码零改动。

## 现象

v0.6.11 的第一次 Windows 全量：`1 failed, 967 passed, 3 skipped`，失败项
`test_improvement_stage_watcher.py::test_second_instance_fails_before_reconciliation`。

定性三条，不是「大概是偶发」：

1. traceback 是 `subprocess.TimeoutExpired`，不是断言失败；
2. 该文件单跑 **9 passed / 57.84s** —— 一次 pwsh 启动约 6 秒；
3. 第二次全量 **968 passed / exit 0**，同机同码。

## 那条 `timeout=12` 到底在断言什么

**什么都不断言。** 这两个用例断言的是：

```python
self.assertNotEqual(second.returncode, 0)
self.assertIn("watcher.lock", second.stderr)
```

`timeout=12` 只是「别挂死」的护栏。它被当成延迟断言用了，于是它一旦触发，
报出来的失败和被测行为毫无关系——而它离实测成本只有 2 倍余量，全量并发下不够。

## 改法

```python
PWSH_HANG_GUARD = 60   # 挂死护栏，不是延迟断言
```

只改两处 `subprocess.run(..., timeout=)` 的 spawn 护栏，**断言一个字没动**。

刻意**没有**动另外两个 `process.wait(timeout=12)`：它们等的是「已经在跑的进程响应
一个文件事件」，不是 pwsh 启动，而且没有失败证据。没有证据就不改——否则「修一个 flake」
会变成「把所有超时都调大」，那只是把问题藏起来。

## 为什么不改断言

如果为了让测试变绿而放宽断言，那是把失败抹掉；这里放宽的是**护栏**，
被测行为仍然被完整检查。两者的区别在于：改完以后，一条挂死的脚本仍然会让测试失败
（只是晚 48 秒），而一条慢启动的脚本不再让测试失败。

## 回归

| 环境 | 结果 |
|---|---|
| 该文件单跑 | 9 passed, 2 subtests, 63.51s |
| Windows `.tools/agent-runtime` 3.13.9 | 968 passed, 3 skipped, 113 subtests |
| WSL anaconda 3.12.7 | 921 passed, 50 skipped |

计数与 v0.6.11 完全一致（968 / 921），因为没有增删用例，只放宽了一处护栏。
Windows 这一跑没有触发那条超时——但这**不能**当成「修好了」的证据：
一次通过说明不了护栏是否够宽。真正的证据是「护栏从 2 倍实测成本提到 10 倍」，
以及「断言一个字没动」。

## 没做的

只处理这一条。其他 `process.wait(timeout=12)` 与 `_wait(timeout=12)` 保持原样：
前者没有失败证据，后者自带明确的失败消息（`filesystem event did not reconcile within 12s`）
而不是一个 `TimeoutExpired` 栈。**有证据才改。**
