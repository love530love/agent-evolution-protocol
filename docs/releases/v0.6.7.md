# v0.6.7 — 两条腿都装上，并且规定谁先走

这一版没有改变送达路径。它新增的是**输入定位的两条备选腿**，以及一条规定它们先后顺序的规则：

- **perception 腿**（`vision_grounding.py`）：问一个视觉模型「控件在哪」，把答案当作**提议**。
- **policy 腿**（`policy_executor.py`）：把模型提议的动作流放进 AEP 的守卫里跑。
- **路由**（`input_routing.py`）：决定这一次该用哪条腿、以及当两条腿都不行时是**不发**。

三条腿共用一个前提：**看见不等于打通**。UIPI 拒绝的是输入注入，不是感知；所以任何一层的成功
都不能冒充送达。送达仍然只由证据阶梯（`commander` / `ui_fallback`）判定。

## 1. perception 是一条提议，不是一个观测

`Proposal` 带 `confidence` 与 `source`；`admissible()` 会拒绝低置信度、拒绝落在窗口外的框，
**而不是把它们夹到边界上**。理由是同一个：模型答 `x=1200` 时不是「稍微偏了一点」，是在回答另一个
问题；夹到 999 就把它变成了一次很自信的角落点击。

`from_normalised()` 负责把 `[0, 999]` 网格换成窗口像素，越界直接 `GroundingRefused`。

`require_provider()` 读的是**同一份** `status` 字段，也就是 `coord-providers promote` 拒绝无证
晋升的那一个。所以「登记了」和「可以跑」不是一回事，`HttpGrounder` 的**构造函数**就是权限检查——
不存在一个「已构造但从未 probe 过」的可用 grounder。

`agreement()` 同时报 IoU 和中心点，因为一个把整个窗口都框进去的大框，IoU 对 500×60 的 composer
很低、中心点也落在 composer 外面，两项都不过——这才是真失手，而 IoU 单独会放过它。

`disagreement_rate()` 把「没意见」和「答错」分开计：只有后者构成反对采纳的理由。

## 2. policy 是唯一的执行者，四条规则不由模型自觉

1. **动作词表是 AEP 的，不是模型的。** 白名单就是 `desktop_providers.OPERATIONS`。没有对应
   operation 的原语**拒绝**，不降级——把双击降成单击是一个「看起来成功」的错误动作。
2. **不许 shell。** 训练配方里的 bash 通道是 guest 侧的便利；在活宿主上它叫「提权」。
   `bash` / `shell` / `exec` / `run_command` / `python` / `terminal` 一律拒绝，名字里带也算。
3. **坐标先查范围再换算。**
4. **一步没验证就停。** 没有「继续看看」；`verified is None`（没装验证器）也不等于通过。

`coord-policy validate` 是这条链的离线演练：不碰桌面，只跑守卫。

## 3. 路由：UIA 能自证时，不问模型

`input_routing.resolve_target()` 的顺序与理由：

| 顺序 | 条件 | 结果 | `needs_verification` |
|---|---|---|---|
| 0 | `drivable is False` | 直接 `EXECUTOR_TOO_LOW` | — |
| 1 | `input_candidate_count == 1` | `uia`，**不调用 grounder** | `False` |
| 2 | 候选 >1 或 0，且提议可采纳 | `vision` | `True` |
| 3 | 前两条都不行，有配置区域 | `geometry` | `True` |
| 4 | 都不行 | 无源，`NO_TARGET` | — |

第 1 行是这一版的核心判断：**已经定下来的问题不该再问一个更弱的回答者**。UIA 给出唯一候选
加 `write_method`，那是观测；这时再问视觉模型，只会让一个好答案被一个猜测投票掉。
第 3 行同理反过来：一个今天恰好正确的硬编码区域，正是 UI 改版后静默打错框的东西，所以它永远需要验证。

`delivery_verdict()` 默认**不发**。三条能走到「发」的路径都是证据形状的：位置由能自证的一方给出、
策略的每一个写操作都有账、策略是因为跑完而停而不是因为预算耗尽而停。
`click` / `type` / `keys` 的 `verified is None` 也算没账——「没装验证器」不能解释成「当作点中了」。

## 4. 实跑证据

`coord-policy validate`（`--window 1920x1080`）：

| 计划 | `stopped_because` | 说明 |
|---|---|---|
| `click,type,bash` | `REFUSED:bash: shell actions are never executed, on any host` | 前两步已记录，第三步记为空 operation + 理由 |
| `double_click` | `UNSUPPORTED_ACTION:double_click` | 附「a double click would become a single click」 |
| `click,type,keypress` | `policy-finished`（`COMPLETED`） | `verified` 全为 `null`，因为没有验证器 |

`coord-route`（同一份 observation 回放）：

| observation | 决策 | 备注 |
|---|---|---|
| 1 候选 + `input_region` | `uia`，`needs_verification=false` | grounder 调用 0 次 |
| 2 候选、无 grounder、有 `--reference` | `geometry`，`needs_verification=true` | `considered` 里保留 `vision: NO_PROPOSAL` |
| `drivable=false` | `locate_source=null`，`EXECUTOR_TOO_LOW` | `blocked_by` 原样带出 |

把**真实**的 dry-run 输出当 `--policy-result` 喂回去，判决是：

```json
{"action": "defer", "state": "DEFERRED", "reason": "STEP_NOT_VERIFIED",
 "step": 0, "operation": "click",
 "note": "a write step is unaccounted for; deferring beats sending blind"}
```

这条是故意留的：**一次 validate 通过不能当成放行**。dry run 没装验证器，所以每个写操作都没账。
已经写成测试（`test_a_dry_run_cannot_be_mistaken_for_a_green_light`）。

## 5. 顺手抓到的一个静默

`coord-policy` 原来用 `plan.get("actions") or plan.get("plan") or []`。于是
`{"steps": [...]}` 这种拼错的计划会变成**空计划**，跑 0 步、`COMPLETED`——和「校验通过」的输出
一模一样。现在没有这两个键就报 `plan object needs an 'actions' or 'plan' list`，exit 2。

## 6. 没做的（这一版明确不做）

- **路由还没接进活路径。** `ui_fallback.run()` 目前仍只走 UIA，`resolve_target()` 只在
  `coord-route` 里离线回放。接进去要动送达路径，而这一版刻意不碰它——先让规则可回放、
  可争论，再接。
- **没有 probed 的 grounder，所以 vision 腿一次都没真跑过。** `mage_vl_cowork` 还是
  `candidate`；`coord-vision ground` 在无 `--endpoint` 时只跑 `NullGrounder`，报
  `NO_PROPOSAL` 而不编数字。这是设计，不是缺陷，但也意味着「视觉定位在本机可用」**尚未验证**。
- `agreement` / `disagreement_rate` 只有单元测试，没有真实截图对；判决点仍然是
  `docs/MAGE_VL_COWORK_ASSESSMENT_20261031.zh-CN.md` 里预注册的那四步。
