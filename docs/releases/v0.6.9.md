# v0.6.9 — 先证明这条消息该发，再谈怎么发

上一版把「哪条腿定位输入」接进了活路径，并实测出一个结论：闸门管合法性不管对错。
这一版把同一条判断往前挪了一步——**在输入之前，先判断这条消息该不该发。**

起因是一次真实事故：消息内容发错了会话。事后查代码，两处都能复现，也都不在 UI 层。

## 1. 窗口身份：`Qoder` 是 `Qoder CN` 的子串

`client_registry.matches()` 的兜底分支是「进程名出现在标题里就算匹配」。实测：

```
qoder profile  vs 'Qoder CN' 窗口 : True      <- 错的
qoder profile  vs 'Qoder'    窗口 : True
qoder_cn prof  vs 'Qoder'    窗口 : False     <- 不对称
```

只跑 Qoder CN 的机器上，发给 `qoder` 的派工单会找到并进入 **Qoder CN 的窗口**，
而且 `unique: True`——一个错误的窗口被描述成「唯一、无歧义」。

### 修法：exe 只当仲裁者，不当过滤器

本机四条 profile 里**两条已经漂移**（`qoder` 的 exe 停在 `D:\Programs\Qoder\Qoder.exe`，
真实是 `.qoder-versions\0.5.1\Qoder.exe`；`qoder_cn` 停在 `0.4.11`，真实是 `0.5.1`）。
如果 exe 不匹配就算「没找到」，这两个客户端会**同时变成不可达**——用一个「发不出去」
换掉一个「发错」，不是明显更好的交易。

所以规则是：**当某个窗口的可执行文件正是另一个已登记 profile 声明的路径时，那个 profile
拥有它，其他 profile 的匹配作废。** 版本漂移不触发（路径对不上任何别人的声明），
跨产品误配触发（`Qoder` 与 `Qoder CN` 装在不同目录）。

### 本机真实发现（只读，2026-11-01）

```
workbuddy    -> [('WorkBuddy','exe','WorkBuddy.exe')]       unique=True
workbuddy_ai -> [('WorkBuddy AI','exe','WorkBuddyAI.exe')]  unique=True
--- rejected ---
workbuddy refused 'WorkBuddy AI' owner= workbuddy_ai
```

**`workbuddy` 之前一直在把 WorkBuddy AI 的窗口算成自己的**，而两个客户端当时都在跑。
这条是仲裁跑出来的，不是推测出来的。

每个窗口现在上报 `identity`：`exe`（强）/ `title`（中）/ `process-substring`（弱）。

## 2. 发送前门禁：12 项，硬阻断

`coordination/dispatch_gate.py`，位置在 `commander._dispatch()` 取到窗口之后、选传输之前。
放在这里而不是每个传输里，因为「哪段文字发给谁」是订单的属性；按传输各写一份，
下一个新增的传输就会漏掉。

纯函数，不碰窗口、不碰进程、不碰网络——**只有这样才能在桌面出问题时仍然可靠**。

| 检查 | 强度 | 抓什么 |
|---|---|---|
| `content_hash_recorded` | 阻断 | 有 envelope 却没有内容哈希 |
| `content_unchanged` | 阻断 | 入队后被改过的正文 |
| `one_event_id` | 阻断 | 正文里有第二个 event id（旧任务内容混入） |
| `one_task_marker` | 阻断 | 多个 `[AEP:<task>]`，或那一个不是本单的 |
| `event_id_in_text` | 阻断 | 正文里找不到本单 event id |
| `ack_requirement_in_text` | 阻断 | 没有 `AEP-ACK` 要求 |
| `target_matches_profile` | 阻断 | 订单目标是 `qoder`，绑定的 profile 是 `qoder_cn` |
| `not_superseded` | 阻断 | 同一 task 已有更新的订单 |
| `dag_event_matches` | 阻断 | 工作区 DAG 里的 event id 与订单不一致 |
| `not_expired` | 阻断 | 已过期 |
| 自报家门三项（task / assignee / workspace） | 告警（`--strict` 阻断） | 正文没有说明自己是谁 |
| `window_identity` | 告警（`--strict` 阻断） | 窗口只靠进程名子串绑定 |

后四项默认只告警，因为决定「这段内容是不是这张单的」是**哈希 + 唯一 event id + task 标记**，
那三项已经是硬阻断；而一条临时通知（"read your inbox"）没声明过任务，
却会因为它没写出任务号被拒——那会把门禁变成噪音源。

### 判 `FAILED` 而不是 `DEFERRED`

内容不对的单子不会因为等一会儿就变对。可重试状态会让它每个 tick 重新排队、重新被拒，
一个穿着勤勉外衣的日志洪水。`receipt.signal = "dispatch_refused"` 在诊断表里落到
`unknown → escalate`：**这需要人，不需要重试。**

### 真实 dry-run

干净派工单（`federation.assignment.render` 的真实输出，1028 字符）：

```
verdict: send   checked: 12   failed: []   warned: []   exit=0
sha256 08ab2f7f4bd4d561   ack AEP-ACK:EVT-0A35419357B2467E
```

把旧任务的 ACK 行追加进去（复现事故形状）：

```
verdict: refuse
reason : content_unchanged
detail : deposited 08ab2f7f4bd4d561, now 916592874d21ae12
failed : ['content_unchanged', 'one_event_id']
exit   : 2
```

两条独立判据同时命中——就算有人把哈希重算一遍，`one_event_id` 仍然会拦住它。

### 离线复算

```powershell
aep --coord-root coordination coord-dispatch --order-id <id> --show-body
aep --coord-root coordination coord-dispatch --all --strict
```

## 3. 这一版明确没做

- **没有「用户确认」环节。** 它和 7×24 无人值守直接冲突，所以做成可复算的拒绝，
  而不是等人点一下。`--strict` 是给「这一批必须全项通过」的场合用的。
- **不解决「单子对、会话错」。** 订单和 profile 都指向 `qoder_cn`、但窗口里不是该发的那个会话时，
  门禁看不出来——那要靠会话校验，本版没有改动它。
- **不证明对方接单。** `AGENT_ACK` 仍然只认目标自己的回复。
- **没有在事故那张原单上回放过。** 现场订单不在 `coordination/inbox` 里，
  手上只有形状相同的复现。
- **紧急插话没有单独门禁**，但它走同一个 `_dispatch`，因此同样受检；插话状态机本身仍未补齐。
