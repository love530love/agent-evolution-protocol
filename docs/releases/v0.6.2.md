# v0.6.2 — 让判断依赖比较，不依赖别人的失败模式

本次两个改动都来自同一类缺陷：**代码把「某个操作没报错」当成了「条件成立」。**

## 1. 可驱动性判定改为显式比较完整性级别

`a11y.drivability(target, executor)` 取代了「目标令牌能不能打开」这种间接判断。
`coord-a11y` 与驱动层回执现在同时给出两侧：

```json
{
  "target_elevation": "unknown",
  "executor_elevation": "standard",
  "drivable": false,
  "blocked_by": "TARGET_NEEDS_ELEVATION"
}
```

本机实测（普通权限终端）：

| 目标 | target | executor | drivable |
|---|---|---|---|
| Qoder（管理员启动） | `unknown` | `standard` | `false` |
| ChatGPT（普通启动） | `standard` | `standard` | `true` |

`unknown` 只说明「读不到它的令牌」，也就是它更高；这不能反推「读得到就等于能驱动」。
旧实现在目标可读时一律给绿灯，于是任何「能读但等级更低」的情形都会被误报为可驱动。

## 2. 作业对象的断连承诺按解释器如实报告

`windows_job.interpreter_profile(command)` 新增。实测差异：

| 启动解释器 | 大小 | 子进程最内层作业 flags | 断连 |
|---|---|---|---|
| `D:\A\python.exe` | 104,264 | `0x2000` | `DENIED 5` |
| `.tools\agent-runtime\Scripts\python.exe` | 253,256 | `0x3000` | 放行 |

venv 的 `Scripts\python.exe` 是重定向启动器，重新执行基解释器时套了一层带
`JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` 的嵌套作业。终止仍然有效（嵌套作业随父作业死，
实测两边都杀干净），但「被关住的测试无法断连」不再成立。

`test_contained_test_cannot_request_breakaway` 因此按 profile 决定断言还是跳过，并打印原因；
新增 `InterpreterProfileTests` 把判定逻辑本身钉住（纯路径逻辑，Linux CI 同样覆盖）。
**一个会随解释器漂移的断言不是安全属性。**

## 3. 锁的首次字节竞态

全量并发下 `test_two_processes_never_lose_an_increment` 偶发
`PermissionError: [Errno 13]`：`fstat` 看到 size 0 之后、写首字节之前，另一进程已建好该字节
并锁住区域，写入落到被锁区。此时预填充已是多余的，不应升级成加锁失败。
