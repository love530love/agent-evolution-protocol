# v0.6.21 — 居中协调一拍：把三条既有单步接起来

本版落地 `docs/COORDINATOR_VISION_EVIDENCE.zh-CN.md` 的 **P0「一拍接线」**。
核心判断是：**项目不是没有调度，而是三拍彼此不通** —— 所以这一版只接线，不造第四条链。

## 1. 三条本来就存在、却互不调用的单步

| 既有单步 | 内部做什么 | 含真发 |
|---|---|---|
| `coordination/campaign_tick.py:tick()` | `presence.reconcile` → `team_dispatch.process` → `command_memory.ingest_journal`（协作区与 bridge 各一次）→ `campaign_cycle.reconcile`（ACK/工作截止、容量释放、超时接力、通知修复） | 否 |
| `coordination/mission_pulse.py:pulse(apply=True)` | 扫 `missions/M-*.json`，过 11 类硬闸门 + 复算，把 `ready` 阶段投成 `DEPOSITED` | 否（`submit_order` 明写 `Nothing is sent until a tick runs`） |
| `federation/supervisor.py:step()` | `_settle` 结案 → `hold_alerts.emit` → `engine.tick` 排程 → `_claim_scopes` 租约 → **`commander.tick` 真发** | **是** |

第三条已经是一个完整的一拍并返回统一回执。因此新增的
`coordination/coordinator_tick.py` 是一个**薄接线层**：一次性、零模型、零子进程、零常驻，
默认只读，`--apply` 才按固定顺序调用上述既有函数。
**不改任何既有函数签名，不新增 schema，不新增 `coord-*` 命令面，不改 mission 文件。**

## 2. 固定顺序与两条硬安全性质

```text
--apply  →  campaign_tick.tick()  →  mission_pulse.pulse(apply=True)  →  恰好一条投递路径
                                                                        ├─ federation/supervisor.step()  （有 DAG 上下文）
                                                                        └─ commander.tick()             （无 DAG 上下文）
```

顺序与既有 `commander.tick()` 的「先结案 → 排程 → 认领 → 最后真发」一致：
先结清回表与截止，状态才已知；再让 mission 入队；最后才允许发送。
任一步前置失败即 `halted=SETTLE_FAILED` / `MISSION_FAILED` 并**立即停止**，
不排队、不真发 —— 状态不明时继续推进就是拿不确定状态去发消息。

**性质一：投递路径严格二选一。** `supervisor.step()` 内部已经调 `commander.tick()`，
两者都调就是**重复投递**。`dispatch_path` 在执行前写定，回执里只有一个值。

**性质二：失败不回退。** `supervisor.step()` 抛错时它可能已经发过；改调
`commander.tick()` 不是重试，是第二次发送。所以 federation 路径失败后只记录
`stages[-1].status=failed`，`dispatch_path` 保持 `federation_step`，绝不 fallback。

DAG 上下文须同时给 `--kernel-root`、`--workspace`、`--agents` 才启用；缺任一项时
回报 `skipped[].reason=FEDERATION_CONTEXT_MISSING`，**明确记为「没跑过」**。

## 3. 默认只读预览

不带 `--apply` 时零写入：`preview` 给出 mission 的
`scanned / candidates / verified / rejected`、campaign 任务数、`presence.strength`、
`commander.orders`，以及 `campaign_tick.next_due()` 汇总的 `next_due_at`
（`next_due_source` 标明来源，不自算）。某个只读源损坏写 `unavailable: <异常>`，
不猜、不补、不让整个预览崩掉。空仓也必须报扫描量。

`plan` 列出将要调用的四行既有单步；`stages[]` 只记录**实际执行**的步，
`skipped[]` 单独记录没跑过的步。

## 4. 回执与边界

硬字段恒为 `models_loaded=0` / `processes_started=0` / `ui_touched=false` /
`deployment_performed=false` / `system_tasks_registered=false`；任一变真即越界。

| 动作 | 是否自动 |
|---|---|
| 只读预览、汇总最近截止、给出调用计划 | ✅（默认） |
| `--apply` 时按固定顺序调用既有单步 | ✅（需显式开关） |
| 判断某 Agent 是否接单、产出任务结论 | ❌ 由目标 Agent 与回执表负责 |
| 改 mission 阶段 / 接管他人 claim / 评审晋升 | ❌ |
| 启动模型、常驻进程、后台线程、OS 计划任务 | ❌ |
| 关单 | ❌ **只有 `VERIFIED` 能关单** |

`DEPOSITED / WINDOW_FOUND / INPUT_SUBMITTED / MESSAGE_VISIBLE` 不是送达；
`WAKE_QUEUED_UNVERIFIED / RELAY_QUEUED_UNVERIFIED / MAILBOX_ONLY / REJECTED` 不是接单。

`scripts/run-coordinator-tick.ps1` 是一次性有界脚本：纯 ASCII、不循环、不 sleep、
不后台运行、不注册任务，默认不带 `--apply`。**定时器只负责触发只读命令，定时器不是判断。**
