# v0.6.14 — 主链最后一环：回执之后，还要看结果

前三版把「正确派工 → 正确会话 → 正确回执」逐段补上。这一版补第四段：**正确结果**。
同时把上一版留下的「超限只报警给空气」接通到人。

本轮由三个并行 subagent 分头做独立模块，集成、验证、发布由主进程负责。
下面每一条都注明哪些是**真跑过的**，哪些**只跑了单测**。

## 1. `result_readback`：ACK 不是产出

`assignment.complete_evidence()` 至今接受 agent 自己写 `phase=done`——「活干完了」仍然只是它自己的说法，
顶多钉了一张回执。新模块把两个已经存在的陈述摆在一起比：

- agent 在 `coord-task-state` 里**声称**了什么（`claim()`）；
- 会话记录显示它**说了**什么（`observe()`）。

三条性质撑住整个模块：

| 性质 | 为什么 |
|---|---|
| `match` 是三值 | `None` = 「会话里没有可比的东西」，**它不是 `True`**。捕获失败时转录为空是常态，把它读成「一致」就是把回读变成装饰 |
| 产物是**路径**不是词 | `done` / `tests pass` 没有第二方可以打开的东西，进 `unchecked`，判 `None`——不是通过，也不是失败 |
| 转录要能**归属** | 我们自己那条派工里的路径不是 agent 在指认产出；别的会话里的路径也不是本任务的结果 |

**没有新 schema。** `aep-readback-v1` 是**传输阶梯的回执**：五个状态、两个布尔、一个字符串列表。
它没有字段能装「比过了、不一致」，也没有字段能装「没有可比的东西」，
而它的 `accepted()` 定义在 `AGENT_ACK` 上——正是本模块要检验的那个声称。
硬塞进去要么得发明第六个状态（被它自己的验收测试拒），要么把 `None` 写成 `observed: False`（说的是反话）。
所以它**不带 `schema` 键**，像 `session_fingerprint.compare()` 一样：它消费回执，它自己不是回执。

### 接线：只在「确凿矛盾」时阻断

`supervisor._settle()` 现在在 ACK 闸门之后、`engine.complete()` 之前比对：

```
match is False  → hold_result_mismatch，任务保持 running，不完成
match is True   → 完成，回执带 result.match = True
match is None   → 完成，回执带 result.match = None + 原因
```

**`None` 不阻断是刻意的**：一个「agent 没写文件路径就不许完成」的模块，会在第一个任务上锁死 DAG。
但 `None` 也不许读成已验证——所以它作为字段出现在完成回执里，而不是默认假设。

单测：`test_result_readback.py` 19 项 + supervisor 层 3 项（矛盾 / 确认 / 不可验证）。

## 2. `hold_alerts`：超限现在真的会有人看到

v0.6.13 让 `held` 带上 `over_limit`，但它只活在 `step()` 的返回值里。这一版把它送到**已有的信箱**：

```
coordination/messages/<to>/<id>.json     kind = "warning"
```

选它而不是新造通道，理由是仓库里已经有这套标准：`coord-send` 写这个路径，`coord-inbox`/`coord-digest` 读它，
`kind` 里本来就有 `warning`，收件人取订单自己的 `sender`（谁派的活是记录下来的事实，
而 `"operator"` 是一个没人答应去看的信箱）。被否掉的两条也写进了模块文档：`EventLog` 是校验用的历史不是收件箱，
`presence/notices` 是在线状态流、塞进去会让 `transition` 一个词指两件事。

**幂等**：消息 id 由 hold 的身份（`task|event_id|sent_at`）派生，**信箱文件本身就是那把持久标记**。
第二次 tick 算出同一个 id、发现文件在、保持沉默。没有账本、没有计数器、没有第三处存储。

真跑（临时协作区，非真实订单）：

```
第一次 emit: count=1  消息 messages/kernel/20261101T102113966336Z-06d0bc05.json
第二次 emit: count=0  suppressed=[{reason: already_alerted}]
```

正文点名 task / agent / order / 等了多久，并给出签字放弃的完整命令。

`step()` 的默认 `hold_limit_seconds` 从 `None` 改为 **3600**。这是**策略不是测量**——
代码里没有任何东西推导出这个数；选它的理由只有一条：要短到人还能在自己手上做决定。
传 `None` 可关掉，那是 v0.6.13 的行为，故意保留。

## 3. 顺带修的两个同类缺陷

**① 订单没有 `session_id` 时被说成「别的会话」。**
`ack_protocol.classify` 原本 `if not session_id or 不相等: reason = foreign_session`。
实测 `coordination/commander/inbox` 的 **24 张单里有 6 张没有 `session_id`**（我自己数的，与并行分析的文档一致），
它们的判定永远不可达，而理由写的是「回复来自别的会话」——我们并不知道这件事。
新增拒绝原因 `session_unknown`：「这张单没记下发给哪个会话，所以任何回复都无法归属到它」。
不是同一件事，处置也不同（前者去找别的窗口，后者只能补发或接受）。
`test_a_reply_from_another_conversation_is_still_foreign` 保证真正跨会话的情况仍叫 `foreign_session`。

**② 人已经放弃的单，过期后会被改写成失败。**
`commander.tick` 的跳过列表是 `("AGENT_ACK","CEASED","RETIRED")`，**没有 `ABANDONED`**。
一张已放弃的单过了 `expires_at` 就被改成 `FAILED`/`EXPIRED`：签字字段还在，
但 `state` 不再这么说，`ack_protocol.abandoned()` 随之返回 `None`——**人的决定静默变成自动失败**。
已修，并做了回退验证：去掉修复后测试确实报 `'FAILED' != 'ABANDONED'`。

顺带查了 `reinforce`：补位**不会**给放弃的单派替补（状态白名单挡住了），
但仍加了同样的守卫，并在测试注释里写明**它今天不是修 bug 而是纵深防御**。

## 4. 并行分析：两套 ACK 能不能合并

`docs/ACK_TRACKER_MERGE_20261101.zh-CN.md`（只读调查，未改任何代码）给出的结论是**部分合并**，要点：

- 租约式（`ack_tracker.py`）记录的是「这次等待结束了没有」，事件式记录的是「这个 agent 在这个会话里回没回这句话」。
- 磁盘上租约式**实有 0 行**（`coordination/clients/acks/` 不存在），24 张单都在事件式里。
- 真正的硬约束是 `wake_ingress` 在崩溃重放时会**复用 `event_id`**，与租约式「一个 event 只允许一行」直接冲突。
- 同一个词 `ack` 在仓库里指五件事，其中只有一个回答「对方接单了」。

合并本版**没有做**，只把路探清了。这条债仍在。

## 5. 集成时发现的一个 caveat（未修）

`engine.tick` 在两步之间会做 handoff，**生成第二张从未发送过的订单**。于是下一轮的判定是 `sent: False`，
hold 合法地消失，任务可以按新 owner 的自述完成——在 `dispatch=False` 的测试里这是夹具产物，
但它说明**「没有 ACK 不得推进」可以被一次 handoff 绕过**。真实派发下新单会被发出、闸门会重新生效，
但这条路径没有实测过。记在这里，不假装它不存在。

## 6. 仍未做

- 回读的**会话守卫没接线**：现在拿整条转录比，`session_checked` 在证据里如实写 `False`。
- `match is None` 的完成仍然只是「记下了没验证」，没有要求人复核。
- `ack_tracker` 未合并（见 §4）。
- 被放弃的任务不能复活；迟到的 ACK 仍会把订单从 `ABANDONED` 升成 `AGENT_ACK` 而任务停在 `blocked`。
