# v0.6.10 — 没有 ACK 就不推进，不是那个会话就不发

上一版在打字之前加了一道内容闸门。这一版补两件它管不到的事：
**对方到底接单没有**，以及**这到底是不是那个会话**。

两件事的共同点：系统里原本都只有一个「看起来成立」的结论。

## 1. ACK：字符串匹配一定是错的

根因一句话：**我们要对方回的那个 token，写在我们自己发出去的消息里。**

```
我们发： ... AEP-ACK:EVT-0A35419357B2467E ...
对方回： AEP-ACK:EVT-0A35419357B2467E
```

任何「在会话里找这个字符串」的实现，第一次命中都是我们自己的请求。
所以 ACK 不是一次字符串出现，是**一个带角色的事件、发生在正确的会话里、记录在发送之后**。
判定收进 `coordination/ack_protocol.py`，四道守卫：

| 守卫 | 挡掉什么 | 拒绝原因 |
|---|---|---|
| `role == "assistant"` | 我们自己那行；用户那行；**输入框草稿** | `not_assistant` |
| `direction == "incoming"` | 同一行被当作发出的内容捕获 | `not_incoming` |
| `session_id` 等于订单的 | **另一个会话在回答同一个问题** | `foreign_session` |
| `recorded_at > created_at` | 旧投递的答案（event id 每任务固定，重发复用） | `stale` |

拒绝原因分开写，因为它们要求不同的处置：「对方还没回」是等；「另一个会话回了」是
**消息发错地方了**；「以 outgoing 出现」是**你在读自己的请求**。合成一个 `False` 就全看不出来。

### `state` 里没有 timeout

> **v0.6.11 更正**：本版把 `state` 写成三个值，其中 `not_sent` 覆盖了
> `CEASED / SUBMISSION_UNCONFIRMED`（**可能已经发出去**）——那是一句假话。
> 真实订单当场抓到。现在有第四个值 `submitted_unconfirmed`，见 `v0.6.11.md`。
> 下面这段关于「没有 timeout」的论证不受影响，仍然成立。

只有 `not_sent` / `sent_unacked` / `acked`。**迟到的回复必须被接受**——
超时是关于我们耐心的陈述，不是关于对方的。把它当成拒绝，正是重复发送的来源；
2026-10-31 实测过一次（应答比 60 秒窗口晚到约一分钟，而消息早已送达）。

```powershell
aep --coord-root coordination coord-ack --order-id <id>    # 未接受则 exit 2
```

输出里除 `state`/`accepted` 还有 `rejected` 列表，每个被排除的候选带自己的原因。

## 2. 没有 ACK 不得推进

`supervisor._settle()` 原来只看 `assignment.complete_evidence()`：agent 自己写
`coord-task-state --phase done` 就算完成。`CommanderAdapter.acknowledged()` 写好了，
但**没有任何调用方**——一个只存在于定义里的检查。

现在的顺序：

```
刷新 ACK（只读，只升级状态，从不打字）
  → agent 报 done？
     → 已发送 + adapter 能报 ACK + 没有 ACK → hold_unacked，任务保持 running，下游不启动
     → 否则 → 正常 complete
```

三条限定，每条都有理由：

1. **只对「已发送」的单生效。** 没发出去的订单没有可确认的对象；等一个没人投递的回复
   不是严谨，是死锁。
2. **只对能报 ACK 的 adapter 生效。** 拿 adapter 给不出的证据要求它，是另一种死锁。
3. **`FAILED` 仍是终态，`CEASED` 仍可被迟到的 ACK 升级。** 这条没动。

hold 出现在 `step()` 返回的 `held` 里（同时 `closed` 为空），
所以「为什么没推进」是回执上的字段，不靠猜。

## 3. 会话指纹

标记检查回答「这个字符串在不在屏幕上」——侧边栏里也有，另一个实例的会话列表里也有。
指纹回答「还是不是那个会话」。

参与哈希：`agent + exe + title + session_marker + model_marker`。

**故意排除 pid。** 重启不是换会话，而一个每次重启就失效的指纹，操作者会学会无脑重录，
等于没有指纹。pid 仍然记录，作为上下文：「同一个会话，现在在 pid 4242」。

本机实测（只读）：

```
qoder      pid=22796  fp=332555763b7f26a5
qoder_cn   pid=56368  fp=20eb3eb74f41b52d
workbuddy  pid=3560   fp=82dad2ad037bae62
```

`qoder` 与 `qoder_cn` 指纹不同——上一版靠 exe 仲裁区分这两个产品，现在有了独立的一票。

### 它抓什么，抓不到什么

| 情况 | 能否发现 |
|---|---|
| 同一会话重启 | **不算变化**（设计如此） |
| 换目录 / 换产品 | 能（`exe` 进 `diff`） |
| profile 指向另一个会话 | 能（`session_marker` 进 `diff`） |
| 模型切换 | 能（`model_marker` 进 `diff`） |
| **同一 profile、窗口现在显示另一个会话** | **不能** |

最后一行必须说清楚：两个标记来自 **profile**，不是从屏幕读的。
「窗口里现在是不是那个会话」仍是 `ui_fallback` 的 `SESSION_NOT_VERIFIED` 在管。
把指纹说成能解决会话错配，是这一版最容易犯的过度声称。

没有记录时 `compare().match` 是 **`None`**，不是 `True`——「没人记录过」和「一致」是两件事。
派发时 `None` 照常发送并把指纹写进 `WINDOW_FOUND` 回执；`False` 则 `DEFERRED` +
`SESSION_FINGERPRINT_MISMATCH`，`diff` 指出具体哪个字段不同。

```powershell
aep --coord-root coordination coord-client fingerprint --agent qoder --show   # 只看
aep --coord-root coordination coord-client fingerprint --agent qoder          # 记录
```

## 4. 没做的

- **会话内容不在指纹里**（见上表最后一行）。
- **hold 没有上限**：永不 ACK 的 agent 会让任务永久 `running`。这是有意的（无人值守不该在
  未验证的工作上宣布胜利），但也意味着需要一个「放弃并标 blocked」的策略，本版没写。
- **`ack_tracker.py` 没合并**。它是另一套基于租约的 ACK 记录（`clients/acks/`），和本协议并存。
  合并要动 wake 链路，本版没碰——两套并存正是这个仓库一直警告的事，记在这里而不是假装统一了。
- **`provider_readback` 的 `aep-readback-v1` 仍是独立契约**，readback 回执格式没改。

| 环境 | 结果 |
|---|---|
| Windows `.tools/agent-runtime` 3.13.9 | 961 passed, 3 skipped, 113 subtests |
| WSL anaconda 3.12.7 | 914 passed, 50 skipped |

两边的增量一致：v0.6.9 是 Windows 933 / WSL 886，本版各 +28，就是上面那四组新测试。

**WSL 抓到一个我自己引入的缺陷，记在这里。** 指纹的路径规范化原本用 `os.path.normcase`，
它在 POSIX 上是恒等函数、也不把 `\` 当分隔符，于是同一路径在两个宿主算出两个不同的指纹。
WSL 首跑是 `1 failed, 913 passed, 50 skipped`，失败项正是
`test_path_case_and_separators_do_not_change_the_identity`。改成在 `_normalise()` 里自己实现
规范化（`/`→`\`、折叠重复分隔符、去尾分隔符、转小写）后，两个宿主各 9 passed。
教训和 10-31 那次同源：**别把判断交给宿主**——`normcase` 在 Windows 上做的三件事，
在 Linux 上一件都不做，而它失败的样子是「指纹变了」，看起来像被测系统的问题。

**另外记一个本机环境坑**（不是代码缺陷，但会让回归结果看起来像失败）：
这台机器上 `pytest` 收尾清理临时目录时会撞上 safe-delete shim
（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，一次 265 个目标），进程在**打印汇总行之前**
就以 exit 1 退出。所以「全部点通过、但没有汇总行、exit=1」是环境，不是测试失败。
加 `CODEBUDDY_SAFE_DELETE_ENABLED=0` 复跑即得干净的 `961 passed`。
上表两个数字都来自关掉 shim 之后的运行。

完整分析见 `docs/ACK_AND_SESSION_IDENTITY_20261101.zh-CN.md`。
