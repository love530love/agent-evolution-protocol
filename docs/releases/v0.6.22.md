# v0.6.22 — 操作拟真度：让「依次互测通过」第一次可判定

本版源于操作员 2026-11-05 的一次口径纠正与一条新的完成判据。

## 1. 口径修正：省积分不是本项目目标

> 「省积分只是我告诉你的，但不用要求实据……这不是我们项目该考虑的事。」

「省积分」只是背景说明：积分/用量上涨的根因是 Agent 执行步骤阻滞多、拖沓、
顺畅度低，属于**使用侧成本**。本项目**不追踪**积分、额度、token 用量、限流、
重置间隔或费用，也不需要拿实据去证明或证伪它。

因此 `docs/COORDINATOR_VISION_EVIDENCE.zh-CN.md` 的 **3.1 与 P1 作废**（不是被证伪，
而是整条命题移出范围），`docs/COORDINATOR_TICK.zh-CN.md` 也不再把 P1 额度账本列为欠账。
「观点需要实据」这条仍然成立，且继续适用于回环判定、来源核验与错误情报，
只是不套在这个范围外的命题上。已发布的 v0.6.20 / v0.6.21 Release 正文按历史记录保留不动。

## 2. 项目真正要解决的：操作拟真度

> 能够流畅快速的解决想要达到的操作：让手脚能够顺利达成所需的调度和代替人类工程师
> 操作那样的拟真度。

即：手脚能否流畅、快速、连贯地完成调度、分工派发、唤醒、插话、轮询、通报全队、
催促查看回表、促成辩论与推进，达到「像人类工程师在现场操作」的连贯程度。
这是**操作质量目标**，不是「项目已代替人类工程师」的身份断言——后者仍被 v0.6.20
事实基线否掉（无 OS 任务注册、无常驻进程、无跨重启恢复、VERIFIED 关单、reviewer≠author）。

**新的完成判据（操作员指定）**：在线 Agent 依次互相派发消息并回环总结，
**各个 Agent 依次互相测试通过之后才能算跑完**。可复算形式：

1. 每个参与者有**自己上报的、新鲜的**在线证据；
2. 有向环：每个 Agent 各发起一次、各接收一次；
3. 每环有同一 `event_id` 绑定的分析正文 + SHA-256 + 发起方回表；
4. **全部 `VERIFIED`** 才 `run_complete=true`。派发、可见、已输入、已 ACK 都不算跑完。

`online` 就是自导自演，「依次互测」这个判据从根上失效。

## 4. `loop_verdict.py`：第一次能回答「这次回环是否 VERIFIED」

此前全仓唯一产出 `RESULT_VERIFIED` 字面量的是 `dual_channel.WakeState`，
**src 内没有任何调用方**（只在测试里出现，还要求调用方自己传 `result_verified=True`）。
也就是说「只有 VERIFIED 能关单」一直是文档口径，代码回答不了这个问题。

新模块按 `docs/coordination/EVIDENCE_BACKED_AGENT_HANDOFF.zh-CN.md` **重算**三方证据：

1. `delegation/receipts/<event_id>.json` 为 `AGENT_ACK` 且 `agent_accepted=true`、目标匹配；
2. `delegation/artifacts/<event_id>/<target>.json` 的 SHA-256 **从存储的分析正文重算**；
3. 发起方 `<event_id>-reply.json` 与回执 `reply` 都含**同一哈希**。

三者一致才 `VERIFIED`；否则 `NOT_VERIFIED` 并给出具名原因
（`RECEIPT_NOT_ACK` / `ARTIFACT_DIGEST_MISMATCH` / `REPLY_HASH_MISMATCH` /
`REPLY_MISSING` / `TARGET_MISMATCH` 等）。纯只读、零模型、零进程、不写状态。

## 5. `relay_drill.py`：依次互派编排

- `fresh_online()` 只认 `presence.effective(row)=="online"`，**不看 `state` 字段**；
- 生成有向环 `agents[i] → agents[(i+1) % n]`，每个 Agent 恰好派一次、收一次；
- 默认 dry-run：给计划 + `blocked=NEED_AT_LEAST_TWO_ONLINE_AGENTS` + 各 Agent 自报在线指令，
  **零写入、不代报在线、不伪造 ACK**；
- `--apply` 才对每条腿调用既有 `team_dispatch.create()` 并保存 plan；
- **重复 `--apply` 会回放已保存 plan**（`writes_performed=0`、`replayed=true`），
  不会生成新 `event_id` 造成重复派工；只有 `--fresh-plan` 能显式重开；
- `run_complete` 由逐腿重跑 `loop_verdict.check()` 得出，只有全部 `VERIFIED` 才为真。

## 6. 真机 SOP（本轮没有跑完）

1. 各 Agent **自己**执行 `scripts/join-agent.ps1 -Agent <name> -SessionId <id>` 上报在线；
2. 协调器只读预览 `relay_drill --coord-root coordination`，确认成环且 `blocked=""`；
3. 加 `--apply` 按腿派发（桌面投递仍由既有 `wake_daemon` / `coord-uia deliver` 负责）；
4. 每个接收 Agent 写真实分析，用同一 `event_id` 执行 `handoff_worker --action accept`；
5. 重跑 `relay_drill` 读已保存 plan，抄 `verdicts` 与 `verified_legs`；
6. **只有 `run_complete=true` 且每腿 `VERIFIED` 才收工**。

**明确未完成**：真机「各个 Agent 依次互相测试」本轮没有跑完 —— 新鲜在线证据为 0、
实测派工被 `SENDER_NOT_ONLINE` 拒绝、没有发起任何真实互派、没有操作任何桌面窗口、
没有替任何 Agent 上报在线或 ACK。只读 `coord-uia observe` 没有返回可判定的会话闸门结果，
因此不做投递，避免把消息送进错误聊天。
