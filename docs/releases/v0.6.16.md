# v0.6.16 — 插话控件是晚到，不是不存在

v0.6.15 之后积累的 16 个提交。主线只有一条：**把「我看不见它」和「它不存在」分开**。
这条线上犯过一次错，记在 `7b9eb4b` 里，随后被实测推翻，改写在 `fa01027` 与 `7710857`。
本版把那个错误连同它的错因一起留在历史里，因为错因比结论更可复用。

## 1. 插话：控件的出现时机被误读成能力缺失

`7b9eb4b` 的结论是「Qoder 0.5.3 国际版与 CN 版都没有插话通道」，证据是：忙碌时输入区只有
`停止生成`，按回车不发送、不排队，连按两次转写无新增用户回合。

那个测量无效。它用 `ValuePattern.SetValue` 把文字写进输入框，而 **`SetValue` 只改 DOM，
不触发 web app 的 input event**。应用仍认为输入框是空的，发送控件保持 disabled，回车被静默吞掉。
于是「没有排队消息」→「没有插话按钮」→ 被读成「客户端没有这个能力」。

**这是一次操作失败被记录成了客户端属性。** 正确的最小序列是：

```
粘贴（真实输入事件，不是 ValuePattern）
  → 强制回车 1~2 次
  → 输入框清空、发送消息 变成 停止生成、出现「插话」Button
  → 点击「插话」
  → 消息进入正在跑的回合
```

### 判据顺序重排

原来的顺序是「回读转写 → 检查 composer 是否清空 → 结束」。忙碌态下这会白烧整个
`ReadBackTimeoutSeconds`：消息还没进转写（要等提升之后才会），而发送是否落地根本没验。
现在是 **发送 → 证明发出（composer 清空）→ 提升 → 回读**。

- **删掉发送前的 `interject_evidence.ready` 闸门**。它要求「发送前就能看见插话按钮」，
  而这个条件在 Qoder 上永远不成立——按钮是发送后的产物。
  一道永远过不去的闸门不是安全属性，是永久故障。现在准入只要求客户端**确实在忙**。
- **`Wait-InterjectControl` 轮询等控件**（`-InterjectTimeoutSeconds`，默认 10s）。
  「看一眼没有」正是当初误判的直接原因。
- **重试阶梯改成「先补一次回车，再重贴重发」**（`enter-again` → `paste+…`）。
  第一次回车被吞，第二次才可能生效，而且比重贴便宜。回执新增 `send_attempts` / `send_retry`。
- **`interruption` 与 `interject_promoted` 拆成两个字段**。`interruption=true` 的语义是
  「把正在跑的回合杀了」，调用方把它当失败；之前把「提升成功」写进 `interruption`，
  等于把成功记成事故。
- **`interject_evidence` 增 `appears_after_send` / `profile_hints`，修正 `interrupt_only`**。
  旧定义在 Qoder 上恒真（只看得到 `停止生成`），会把一个可插话的客户端判成「只能杀」。

### 两个 profile 都要成立才算数

适配器说「客户端在忙、profile 点名的控件此刻不在屏幕上」，profile 说「这个客户端的控件是
发送后才出现的」（`interject_after_send`）。只有 hint 是猜的 profile 依然过不去——
`codebuddy_cn` 保持严格闸门直到被实测。

## 2. 两个 Qoder 构建都实测通过（不是推断）

CN 版（pid 118632，09:42）：

```
aep coord-uia deliver --agent qoder_cn --urgent-interject
→ status=message-visible  task_delivered=true  promote_after_send=true
  interject_polls=1  interject_action=插话  interject_promoted=true
  interruption=false  send_attempts=3  send_retry=paste+enter
```

国际版（pid 75180，09:57）先造一个在跑的回合（`AEP-START-20261105-01`），
`observe` 报 `activity_state=busy`、`busy_hits=正在执行`、
`{ready:false, appears_after_send:true, interrupt_only:false}`，然后插话回执与 CN 同形。
**最强的一条证据是模型自己写的**：转写第 615 行

```
AEP-INTERJECT-20261105-04 已收到，国际版插话路径验证通过。
```

并说明原任务已在**同一回合**交付完（十二小节 + 附录 A 伪代码 + 附录 B 18 行失败矩阵）。
排队消息被正在跑的回合读到，不是跑完之后追加——CN 那次只能证明消息进了历史。

### 顺手修掉：`deliver` 不读 `maximize_window`

开测前截图发现国际版窗口被留在 **237×39**（空壳）。根因是 `AEP_MAXIMIZE_WINDOW` 只有
`capture` 和 `compose` 在读，`deliver` 硬编码 `SW_RESTORE(9)`；`qoder.json` 声明了
`maximize_window: true`，但那条声明在投递路径上根本不生效。
同一类缺陷：**profile 的声明必须被所有代码路径遵守，否则等于没声明。**
已改为 `$deliverShowMode`，show / foreground 三处统一。

### 代价，写出来而不是被发现

`composer_clear_polls=77`：ValuePattern 写入后第一次等待必然跑满超时，整条投递约 26 秒。
缩短能省时间，但会在「发送其实很慢」的客户端上多按一次回车，有重复投递风险。
先保住「没证明就不算送达」。

## 3. 投递判据：一条消息被送进侧栏编辑器，还回了「已送达」

`c09e007`。三个缺陷叠在一起，才让「投递到 ChatGPT 侧栏 Markdown 编辑器」报告
`message-visible / task_delivered=true`，并毁掉 112 行受跟踪文件。

- **候选排序偏好最大的下边缘**，于是一个 rect 比 1230 像素窗口低 6223 像素的编辑器排到了真
  composer 前面。`Get-InputCandidates` 现在拒绝 `OUTSIDE_WINDOW`（8px 容差）与
  `SCROLLED_CONTAINER`（高过三个窗口），两者都写进回执；`Select-InputElement` 说明是谁赢了：
  `composer-hint` / `lower-band` / `lowest-control`。hint 只来自 profile，通用 OCR 占位符
  不再参与竞价。
- **`task_delivered` 曾被输入框自身的文字作答**。现在要求三件事同时成立：事件 id 出现在
  composer 切面**之上**、composer 已清空、且有一个**不是 composer 祖先**的见证元素持有它。
  见证人按祖先关系排除，而不是按高度，所以回执不再需要 `too_tall` 这种二次判决。

## 4. 路由有了显式的「不知道」

`ff61d1b`。规则引擎从不说「我不知道」，它返回 `scenario="project-orientation"` 加
`requires_clarification=True`，于是只读 `scenario` 的调用方把无知当成了一次定向判断。
`unknown` 现在是字段；`read_only_explicit` 与 `read_only` 分开，因为兜底场景本身就是只读的，
用 `read_only` 把关会把提案者锁在它唯一存在的分支之外。

复合写入现在算歧义：「唤醒它然后上传」原来返回 `wake-agent` 并把上传整个丢掉。
收窄只做了一个 case（顺序连接词连起来的 `shared-resource-lock`），
把 `shared-resource-lock` 整个移出排除集会连「我来接管那个上传」也判成歧义，那是过度阻断。

## 5. 换表面，而不是问人

`3b27510`。操作员的判断：**同意提示就是一次停机**——UAC 提权弹窗和任务执行中重新征得同意，
都是任务阻断行为。调度器早就能看出目标不可驱动，但唯一反应是延后等人去提权；
一个等到有人注意到才继续的无人值守，不是无人值守。

现在当回执**证明什么都没输入**时，订单会在可驱动的表面上继续同一段对话。
`EXECUTOR_TOO_LOW` 是唯一满足这一条的回执：UIPI 在输入到达窗口之前就拒绝了它。
「已证明没输入」正是「换表面不需要征询」的全部理由——一次不确定的发送之后再换，
等于把消息发两遍，任何策略都不能让它变成可接受。
`test_an_uncertain_send_never_switches` 钉住这条边界；忙碌的目标也不换，因为「忙」讲的是别的事。

## 6. 其余五项

- **OCR 中继能自证粘贴了**（`8585601`）。国内版 WorkBuddy 没有 UIA 树，OCR 是唯一通路，
  但那条路永远无法确认粘贴：它在屏幕上找 30 字符的 ASCII 事件 id（识别器读不出），
  且只在激活后 400ms 采样一次，页面还没重排完。于是每次都是
  `composer-not-confirmed → SEND_UNCERTAIN → CEASED`，一个等人来的队列而不是循环。
  现在等布局稳定（hint 可见且窗口 rect 两次采样一致），用 `VK_DELETE` 真正清空选区
  （选中不等于清空），并把探针改成消息尾部连续汉字。
- **常驻循环遵守 `--no-perceive` 并自述**（`307e6fa`）。该参数停在 CLI，`watch` 调
  `tick(root)` 时它根本没传下去；同时循环一行都不打印，所以 201 字节的日志既可能是
  「健康且安静」也可能是「卡住了」。现在每次 tick 一行 JSON：数量、时刻、发了什么、是否做了感知。
- **wake id 契约统一**（`35a3653`）。`dispatch_gate` 只认 `EVT-` 前缀，而 `coord-send` 把
  信箱时间戳 id 直接当 `event_id` 传下去，于是每个 `--dispatch` 订单都在
  `one_event_id` 上自我拒绝，一个字符都没打出去。两套规范词汇都认，
  单一来源 `is_stamp_id()`（原来有三份拷贝）。`coord-send` 现在把 order_id/event_id
  持久化进信箱消息，而不只是打印。
- **吸收三项外部能力，拒绝五项**（`a38b06c`）。CLI 面由 `build_parser` 生成，
  所以手册不可能描述一个不同的 CLI；风险默认 `mutating`，只守危险方向；
  89 个命令里 64 个定义附近没有描述，这现在是棘轮而不是一排短横线。
  `session_fingerprint` 把五个身份字段拆成会话、模型、表面三类，摘要覆盖表面，
  所以同一段对话换个客户端打开一定读作不同。
- **一个 ISO 解析器**（`2fe2299`）。CI 自 2026-11-02 起红了三个提交，本地全绿：
  `datetime.fromisoformat` 在 3.10 上对尾部 `Z` 抛 `ValueError`，而那个字面量在模块作用域，
  整个测试文件导入失败。库早就学会了这件事并在七处手写 `.replace("Z", "+00:00")`——
  同一个约定的七份拷贝，就是会被抄出第八份而没有 replace。现在是 `isotime.parse_iso`。
  另一半：Windows 在比较同一个目录的两种拼写（8.3 短路径 vs 长路径）。

1. `7b9eb4b` 的结论是错的，错因写进了提交信息和 `docs/`，没有改写历史掩盖它。
2. `qoder.json` 的插话证据从「操作员报告 + 同 shell 推断」升级为直接实测 + 模型回执。
3. 国际版有两个本机特有事实写进了 profile：窗口可能被留在极小尺寸；
   它内嵌浏览器面板，动作标签清单里混着 `后退 / 前进 / 重新加载 / 关闭 … 标签页`。
   停止词护栏能防「杀回合」，**防不了「点错页面控件」**，所以 hint 必须足够具体。
