# v0.6.18 — 新 Agent 调度入口：接入、认领、派工、回执判定

v0.6.17 建立了弱 Agent 能力卡规范与两张卡，但留了一个入口缺口：
**一个新 Agent 刚接入、被要求「开始调度任务」时，第一件事该做什么、哪些状态能算成功，
散落在 `docs/JOINING_ANY_TASK.zh-CN.md`、`docs/AGENT_ONBOARDING_CONTRACT.zh-CN.md`、
`docs/coordination/ANY_AGENT_CAN_DISPATCH.md` 和 `docs/DELIVERY_TRUTH_MATRIX.zh-CN.md`
四份文档里。** 旧卡 `aep-agent-onboarding` 是散文规范，没有回执判定表，弱 Agent 无法机械照做。

本版补上 `skills/aep-start-dispatch/SKILL.md`：一张 `min_agent_capability: file-only` 的入口卡，
把「接入 → 首读 → 认领 → 派工 → 查回执 → 关单」固化成编号步骤 + 查表结论。

## 1. 两条路径，按 Agent 能力选

**路径 A（file-only，最低能力）**：只写文件也能发起一次派工。按
`docs/coordination/ANY_AGENT_CAN_DISPATCH.md` 的结构写
`coordination/delegation/inbox/<id>.json`（`id` 格式、文件名与 id 一致、
`reply_due_at` 带时区且不超过 3 小时、`allow_new_session: false`），
再抄 `coordination/delegation/receipts/<id>.json` 的状态字段。
有命令行时 `scripts/ask-teammate.ps1` 是同一动作的封装。
**此路径只能宣称「已排队」，不能宣称「已接单」。**

**路径 B（cli，完整调度）**：

```
aep --coord-root coordination --kernel-root .aep-kernel join --agent <name> --task <TASK> --workspace <path> --markdown
aep --coord-root coordination coord-status
aep --coord-root coordination coord-digest --agent <name>
aep --coord-root coordination --kernel-root .aep-kernel inspect --markdown
aep --coord-root coordination coord-claim --agent <name> --task <TASK> --paths <file> --ttl-hours 48
aep --coord-root coordination coord-dispatch --order-id <id> --show-body
aep --coord-root coordination coord-wake --from <name> --to <target> --task <TASK> --reason "<reason>" --dry-run
aep --coord-root coordination coord-delivery-status --to <target> --id <event-id>
aep --coord-root coordination coord-task-state --agent <name> --task <TASK> --phase working --goal "<goal>"
```

`coord-assign`（一步写 DAG 节点 + lease + 投递订单）与 `coord-send` 均为 irreversible，
卡片要求先预览或 dry-run；`coord-dispatch` 只预览排队订单，不碰桌面。

## 2. 卡片特意写死的四个陷阱

1. **Agent 名字不能自造**。`cli.py` 的 `valid_agent()` 只做字符校验
   （`[A-Z0-9][A-Z0-9_-]{0,63}`，转小写），**不校验是不是已登记成员**；
   `AGENTS` 常量用于推断目标，不用于拒绝输入。写错 `--to` 会静默生成一个没人读的信箱。
   卡片要求先用只读 `coord-status` 的 `sessions` 查名字，或问人类。
2. **四态都不算接单**：`WAKE_QUEUED_UNVERIFIED` / `RELAY_QUEUED_UNVERIFIED` /
   `MAILBOX_ONLY` / `REJECTED`。`DEPOSITED` / `WINDOW_FOUND` / `INPUT_SUBMITTED` /
   `MESSAGE_VISIBLE` 也不算送达。**只有 `VERIFIED` 能关单**，口径来自
   `docs/DELIVERY_TRUTH_MATRIX.zh-CN.md`。
3. **不新建会话、不消费旧 wake、不把普通消息当 wake**；忙态保持原 `event_id`
   并 `AGENT_BUSY/DEFERRED`，等下一次只读 readiness probe，不换通道重发。
4. **不承诺无人值守长任务**。`docs/NOVICE_LONGRUN_WORKFLOW.zh-CN.md` 明确写了
   mission planner 与持久化 DAG runner 尚未完成；`scripts/start-mission.ps1`
   只返回 `mission_id`，不等于阶段已自动执行完。

失败处置只允许「停止 / 延期 / 升级给人类」三选一；
`coord-guided-retry` 返回 `uncertain-outcome` 时不得重放写操作。

## 3. 顺手修了守线的一个假阳性

`tests/test_capability_cards.py` 原先用 `\b(coord-[a-z0-9-]+)\b` 提取命令名，
会把全局参数 `--coord-root` 当成命令，导致新卡一加入就红。
修法不是放宽：正则改为 `(?<!-)\b(coord-[a-z0-9-]+)\b` 只匹配命令位置，
**同时新增** `test_global_flags_used_in_cards_are_declared`，
从生成物 `docs/coordination/skill-manifest.json` 的 `global_arguments` 读取真实全局参数
（`--root` / `--coord-root` / `--kernel-root`），逐一校验卡片里出现的全局 flag。
被排除的参数现在有独立守线，标准比之前更严。

同时把 `test_file_only_card_really_offers_a_file_path` 改为遍历所有
`min_agent_capability: file-only` 的卡片，并断言至少发现 2 张，防止新卡绕过「只写文件」要求。
