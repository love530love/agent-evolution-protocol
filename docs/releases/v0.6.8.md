# v0.6.8 — 把规则接到活路径上，然后发现它不知道什么是对的

v0.6.7 留了两条明确的欠账：路由只在 `coord-route` 里离线回放，视觉腿一次都没真跑过。
这一版把两条都还了，并且还债的过程本身给出了一个比原计划更重要的结论：
**闸门管合法性，不管对错。**

## 1. 路由接进了活路径

`ui_fallback.run()` 现在每一次尝试都调用 `input_routing.resolve_target()`，
`state["route"]` **无条件**写进回执——包括 UIA 一锤定音的那次。
理由不是记录癖：一个只记录「有意思的情况」的回执，事后无法回答
「这一次我们到底问过模型没有」。这是上一版最容易出现的自我欺骗。

### 判定条件改对了：`input_found` 而不是 `count == 1`

上一版写的是 `input_candidate_count == 1` 才让 UIA 决断。实测打了这个条件：
本机 ChatGPT 的回执是 `input_candidate_count: 2` 且 `input_ambiguous: false`，
消息正常送达。把「找到两个候选」当成「分不清」会**丢掉一条本来能用的路径**。

现在读的是适配器自己的判断：

```python
def is_ambiguous(observation):
    flag = observation.get("input_ambiguous")
    if isinstance(flag, bool):
        return flag          # 适配器说了算
    return candidate_count(observation) > 1   # 老回执的兜底
```

一个能自证「我知道是哪个」的适配器，比一个从计数反推的规则更可信。

### 没有窗口几何时，不问模型

`[0, 999]` 的答案乘不了任何东西——没有分母，那个数字在屏幕上没有位置。
旧回执不带 `window_size`，旧代码会照样调用 grounder 然后在 `admissible()` 里
`AttributeError`。现在提前记 `NO_WINDOW_GEOMETRY` 并不问。

### 两条传输的处置不同，且都写清楚

| `transport` | 路由给出 | 动作 |
|---|---|---|
| `uia` | `uia` | 正常送达（`ValuePattern`） |
| `uia` | `vision` / `geometry` | **不发**，记 `located_by` / `located_region` / `TRANSPORT_CANNOT_USE_LOCATED_REGION` |
| `ocr` | `vision` / `geometry` | 区域换算成中心比例，交给 `-AllowComposerGeometryFallback` |
| `ocr` | 区域换不出合法比例 | `ROUTE_REGION_UNUSABLE`（可重试） |
| 任意 | 驱动不接受 `composer_ratios` | `ROUTE_UNSUPPORTED_BY_DRIVER`（可重试） |

`uia` 那一行是关键：`ValuePattern.SetValue` 只能作用于 UIA 自己认出的控件，
拿一个模型给的框去喂它是没有意义的。适配器唯一的替代是「往当前焦点盲粘贴」，
那正是 `docs/DESKTOP_SEND_AND_URGENT_INTERJECT.zh-CN.md` 里标成
"only with human supervision" 的动作。所以这里**记录下来然后停下**，而不是悄悄改走粘贴。

`_deliver()` 用 `inspect.signature` 判断驱动是否接受 `composer_ratios`，
不接受就返回 `composer-region-unsupported`。**算出来再丢掉**和「根本没算」在回执上
长得一模一样，所以宁可报一个可重试的失败。

实测比例（ChatGPT 窗口）：`0.4948 / 0.9167`，`state["composer_ratios"]` 原样落盘。

## 2. 视觉腿真跑了：12 格，4 格过闸门，1 格正确

预注册的判决点这次真的执行了。完整数据在 `docs/VISION_GROUNDING_PROBE_20261031.zh-CN.md`，
这里只放结论。

3 个真实窗口 × 2 种坐标格式 × 2 种说法：

| 格式 | 说法 | Qoder | ChatGPT | WorkBuddy |
|---|---|---|---|---|
| 网格 0-999 | `composer` | 拒（越界） | 拒（出窗） | 拒（越界） |
| 网格 0-999 | 人话 | 拒（越界） | 拒（越界） | 拒（越界） |
| 像素 | `composer` | **通过**（错） | **通过**（错） | **通过**（错） |
| 像素 | 人话 | **通过（对）** | 拒（出窗） | 拒（出窗） |

### 2.1 闸门管合法性，不管对错

像素 + `composer` 那 3 格置信度 **0.99~1.0**，全部落在窗口内，全部是错的：

| 窗口 | 模型给的框 | 框内 OCR 实际是什么 |
|---|---|---|
| Qoder | 145,197 1000×1000 | 左侧栏（`BETA`、`专家．技能．连接器`） |
| ChatGPT | 456,18 764×192 | 对话顶部（`mrexodia/ida-pro-mcp` 那个标题） |
| WorkBuddy | 145,167 188×188 | 右栏表格单元格（`写入输入框`） |

**如果拿 `admissible()` 当「可以点」，四次里会点错三次。**
v0.6.7 把 `vision` 的 `needs_verification` 定成 `True`、`delivery_verdict` 默认 defer，
当时是设计口味；现在它有数据了。

唯一正确的那格同时过两个独立判据——人标定点 (1429,1941) 落在框内，
且 OCR 文本命中输入框占位符 `天帮你做些什么？`。两个判据一致才算证据，
这一条也写进了探针的 `summarize.py`。

### 2.2 提示词格式比模型影响更大

同一个模型、同一张图，网格格式 **6/6** 全部越界（模型答 `width=1021`、
`height=1000`——它把网格当像素用了）。仓库里给 Mage 写的那份 `[0,999]` 提示词，
换到 Qwen2.5-VL 上**系统性不可用**，不是「偶尔偏一点」，是坐标空间不对。
任何「换个小模型顶上」的打算都必须先测格式。

### 2.3 术语是被解释的，不是被查表的

像素格式下只说 `composer`，3/3 全错；换成人话，Qoder 那格才对。
一个 3B 模型不认识 `composer` 这个 UI 术语。

### 2.4 许可证

`Qwen2.5-VL-3B-Instruct` 是 **Qwen RESEARCH LICENSE AGREEMENT**，不是 Apache-2.0。
所以无论准确率如何它都不能当生产 grounder。已写进 catalog 的 `license_note`，
`status` 保持 `candidate`——**一格对不构成晋升**。

## 3. 顺手抓到的静默：OCR 回执是非法 JSON

查探针为什么读不到中文时发现的：`windows_ocr_compat.ps1` 通过管道输出的 JSON
里，中文被控制台编码器变成 `?`，两个未识别字形变成裸 `0x07`（BEL），
`json.loads` 在 offset 205 直接失败。

后果不是「少几个字」：**下游拿到的是非法 JSON，于是整段 OCR 文本被丢掉，
中文 marker 永不命中**——一个「字明明认出来了、下游全丢」的静默失败。
Qoder 这类只能走 OCR 的 Electron 客户端，整条送达路径就卡在这里。

修法三层，缺一层都不行：

1. 脚本自己写 UTF-8 字节到标准输出，绕开控制台编码器（和 v0.6.4 在 `Write-Report` 上同一类修复）。
2. 新增 `-OutFile`，让调用方用文件交接，彻底不进管道。
3. `uia_session.ps1` 侧用 `ReadAllText($ocrFile, UTF8Encoding)` 读回——
   否则文件是 UTF-8、读的人按 GBK 解，变成 `σ¢ù Q τ╝ûµùº`。

诊断过程本身值得记一笔：我先用 `'#'` 替换 BEL 做标记、又插桩打印 `IndexOf([char]7)`，
两次都显示「没找到」。那不是因为缺陷不存在，是因为**我改的那一段不在缺陷路径上**。
最后是「中文也一起变 `?`」这条线索把方向拨正的——两个症状同一个病因。

守卫：`tests/test_ocr_wiring.py` 新增 4 项，覆盖直写、`-OutFile`、按 UTF-8 读回、失败路径。

## 4. 两个逆向工具登记（只登记，不晋升）

用户提出「能力整合以备不时之需」，处置是**先如实登记进 catalog**，不写连接器。
理由是这两个工具的能力面都超出「读」：

- **`rea`**（`morluto/rea`，npm `rea-agents`，MIT）：上一版登记有两处事实错误——
  写成 `python` 运行时、写成有 AEP 连接器。实际是 **Node**（`^22.23.4 || ^24.22.1 || >=26.12.1`）
  的 MCP + CLI，没有 AEP 连接器。已改正并加 `source_note` 写明上一版错在哪。
  旧条目里的「crash dump / 网络抓包」也删了——那不是它文档里承诺的能力。
- **`ida_pro_mcp`**（`mrexodia/ida-pro-mcp`，MIT，`candidate`）：需要 IDA Pro 8.3+
  （`idalib` headless），**IDA Free 不支持**。它暴露 `py_eval` 和 `patch*`——
  可以在目标库里任意执行 Python 并改字节。`acceptance` 第一条就是
  「只开放只读子集，禁止 `py_eval` / `patch*` / `rename`」。上游自己也已推荐转用
  Hex-Rays 官方 `ida-mcp` 并把 GUI 插件标记弃用。

两者都留在 `candidate`。**登记一个工具的能力和风险，不等于把它接进执行面。**

## 5. 没做的

- **Mage 本身还是没跑。** 这一版的所有视觉数字来自 Qwen2.5-VL-3B，
  一个**不同**的模型。预注册的四步探针里只有第 2 步（不一致率）被另一个模型替代做了。
- **只有一个窗口有独立参照。** ChatGPT / WorkBuddy 没有标定过的 `composer_*_ratio`，
  它们的「错」靠 OCR 文本内容判定，不是坐标比对。
- **没有多轮重采样。** `do_sample=False`，每格一个答案，稳定性未测。
- **路由接进活路径了，但没在活会话上真跑一次。** `run()` 的接线由
  `RouteWiringTests`（8 项，含真实 `composer_ratios` 数值）覆盖，
  `PowerShellUiaDriver` 的参数透传也测了，但没有一次「路由决定 → 真打字 → 收到 ACK」的端到端。
  按本仓库的规矩，这算**接线完成，未验证**。
- `rea` / `ida_pro_mcp` 只有 catalog 登记与校验测试，没有调用规约、没有连接器。

## 一句话

**把「谁能自证」这条规则接到了真正发消息的路径上，然后实测发现：能自证不等于说得对，
闸门拦的是不合法，不是错误。** 所以视觉腿仍然需要验证，而这条现在是数据，不是偏好。
