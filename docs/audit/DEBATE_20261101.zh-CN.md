# 对抗记录与裁决（2026-11-01）

三组审计 + 主程独立复核，四份报告互不引用。本文只做一件事：**把冲突摆出来，逐条裁决，写明理由**。

裁决权在主程。裁决原则只有三条，按优先级：

1. **一个动作不能删掉一条事实。** 让测试变绿、让告警消失、让判定放行——如果代价是系统少说一句真话，否决。
2. **数字对不上就不许写。** 任何「已修复」必须带复跑输出。
3. **不写第二套并存的标准。** 宁可对齐一个不完美的既有标准，也不新增一个更好的私有标准。

## 冲突一（最重要）：R-01 的修法方向

### 红队的判断

> 「不是因为它最难修——**加两行就能修**——而是因为它让整个『证据链』变成装饰。」

红队主张在三个采集点补上 `role="assistant", direction="incoming"`。

### 我的反对

**症状判断正确，修法错误。加这两行会让这个项目倒退。**

理由是：一次 UIA/OCR 捕获拿到的是**一个窗口的全部文本**，里面既有 agent 说的话，也有我们自己打进去的话。`ack_protocol` 的模块 docstring 第一句就写着这条守卫的用途：

```
10:  * ``role == "assistant"`` -- otherwise it is our own line, or the user's.
```

而 `not_assistant` 的理由文本是：

```
70:  "not_assistant": "the line is not attributed to the agent; our own request reads the same",
```

**「我们的请求读起来一模一样」——这是守卫存在的全部理由。** 在采集层无条件写 `role="assistant"`，等于让采集层宣称「这一整屏都是 agent 说的」，而它并不知道。那时 `not_assistant` 这条守卫就从「一道判断」退化成一个常数，**自回显（self-echo）重新变成合法的 ACK**：我们自己敲进去的 `AEP-ACK:EVT-...` 会被判成对方回话。

这不是理论风险。派工单里就带着 token（`commander.py:161` 存 `"text": body`），token 就在我们打进去的正文里。补两行之后，**每一张单在下单的同一秒就会自己 ACK 自己**。

### 裁决

**否决红队的修法，采纳它对症状的判断。**

正解分两半：

1. **采集层保持诚实**：`role` 继续是 `unknown`。它确实不知道，`unknown` 是它唯一能说真话的值。**不许为了下游好判而让它撒谎。**
2. **判定层把「未知」和「不是」分开**：`role == "unknown"` 不构成反证（它没说不是 agent），但也**不能免检**。替代保护是：接受的那一行**不得是订单自己的正文**。订单里存了 `"text"`，这一条可判定、可测试、可复跑。

也就是说，`not_assistant` 这个 reason 要拆成两个：
- `own_text` —— 这一行就是我们打进去的（**拒绝**，这是原来要防的东西）
- `not_agent_role` —— 明确标注成 `user`/`system`（**拒绝**，明确不是 agent）
- `unknown` —— 没有归属信息，但也不是己方正文（**放行，并在证据里标 `role_source: "inferred_absent_own_text"`**）

这样「拒」的理由更精确了，而不是更松了。**红队说的「加两行」，会让 1061 个测试继续绿、让门禁看起来复活——这正是本报告要防的那种修复。**

## 冲突二：`ack_policy` 的默认值该不该改成 `enforce`

### 双方的立场

- SRE 侧立场（可预期）：默认值应当保守，`record` 会让「没有 ACK」这件事被静默放行，属于「默认不安全」。
- 红队侧立场：`record` 在 R-01 未修时是**唯一**能让系统跑起来的取值。

### 我的裁决

**两边都对，但这个问题现在问是错的。改默认值不是取值问题，是顺序问题。**

在 R-01 / R-02 未修的前提下：

| 取值 | 实际后果 |
|---|---|
| `enforce` | 每一张单永久 `sent_unacked`，DAG 永久钉死。不是「安全」，是「停机」 |
| `record` | 每一张单放行，回执写 `released_unacked / not_assistant`。不是「宽松」，是「说假话」 |

**两个都错，而错的原因不在默认值，在于这条规则的前提（`role == "assistant"`）在现实中不成立。** 在一个前提不成立的分支上调默认值，只是在选一种失败方式。

裁决：**默认值本版不动。** 先修 F-01/F-02，让「有 ACK」这件事在真实路径上可达；然后**用实测数据**决定默认值——如果修好之后真实客户端仍普遍不回报 ACK，那 `enforce` 就是不可用的，`record` 才是对的，而且那时它是**如实的** `record`（回执写 `no_ack` 而不是 `not_assistant`）。

**顺带记一条反对意见**：SRE 的「默认保守」在这里有一个隐含假设——「保守 = 不推进」是安全的。但当 `enforce` 的实际效果是「所有任务永久停在 running」，它保护的不是正确性，是**不动**。一个永远不动的系统和一个乱动的系统一样不可用。**保守必须可退出，否则它不是保守，是瘫痪。**

## 冲突四：R-07（`sha256` 字段名不副实）改不改

### 争议点

红队的证据是硬的（我复验完全一致）：

```
snapshot.artifact().sha256 = fa162c6e...
sha256 of the file bytes   = 51bc0fc1...
equal                      = False
```

但改它会让**所有已锚定的快照对不上**——历史交付审计会集体显示 `TAMPERED`。

### 裁决

**必须改，但不许静默改。**

理由是红队那句我认为本次审计最锋利的话：

> 一个名字叫错的字段会污染同一个文件里所有叫对的名字。

如果 `artifact.sha256` 永远对不上标准工具，操作者的学习曲线是「这里所有 sha256 都不可信」——而 `snapshot.digest`、`anchor.sha256`、事件链的 `sha256` 是真的。**一个错名字的代价是全部名字作废。**

处置（三步，缺一不可）：

1. 新字段 `sha256` 改为**真·文件字节摘要**；
2. 旧值保留为 `digest_json_wrapped`，并在字段旁写明「这是对 `{"bytes": hex}` 再取的摘要，为兼容 v0.6.15 及更早的锚点而保留」；
3. `snapshot.verify()` 同时认两种，且**在报告里说明它认的是哪一种**——不许把「两种都能过」写成「校验通过」。

**否决一种提议**：把字段改名成 `digest` 就算解决。不行。改名不改变「已经写进磁盘的锚点是错名」这个事实，只会让历史记录更难解释。

## 冲突五：R-09（事件日志半行）该不该自动截断

### 红队的建议

> `verify()` 返回 `{"valid": False, ...}`；`append()` 至少能报告「日志尾部有残行」而不是让整个工作区只读。

### 争议点

红队没有明说要截，但「让工作区重新可写」的自然推论就是截。SRE 侧的立场必然是「要能自愈」。

### 裁决

**`verify()` 不抛，照红队说的做。`append()` 不自动截，否决自愈。**

自动截断是**机器替人销毁证据**。半行可能是一条 `task_done` 的后半截，截掉之后「这件事做没做」永久无法回答。而这条日志是整个架构的信任根。

正解：
- `verify()` 返回报告（`valid: false`, `seq`, `reason: "torn line"`, `byte_offset`）；
- `append()` 抛一个**具名的** `EventLogTorn`，带行号与字节偏移，且**错误信息里直接给出处置命令**（`aep recover --truncate-torn-tail --confirm`），要人显式确认；
- `recover()` 不抛，返回 `valid: false` + 那句「日志尾部有 1 行残破，需要人工裁决」。

**这条的价值不在于修好它，而在于「可恢复的事实不该被表达成不可恢复的异常」——红队这句判断是对的，我按它执行；但它顺手带来的「顺便自愈」我不接受。**

## 冲突六：R-14（大小写折叠）算不算「只是难看」

### 红队的标注

> 严重度：`只是难看`（方向保守：多拦，不放行）

### 我的反对

**「方向保守」在安全判定上是免责理由，在可用性判定上不是。**

`overlaps('src/A.py', 'src/a.py')` 返回 `True`。在 Linux 上这是两个不同的文件。后果不是「多拦了一次」，而是：

1. 一个合法的写入被 `gate` 判 `BLOCKED`（exit 3）；
2. 被拦的人学到的是「改文件名」或「别跑 gate」；
3. 而 `.github/workflows/test.yml` 的矩阵一半在 ubuntu 上——**这一半 CI 全绿，因为没有一条测试用混合大小写路径**。

第 2 条比缺陷本身更糟：**一个会误报的门禁，最终会训练所有人绕过门禁。** 那时真正的冲突也拦不住了。

### 裁决

**升级为「静默失效」级别，本版必修。**

但不能简单删掉 `.lower()`：Windows 确实不分大小写，删了会让 Windows 漏拦。正解是**把折叠变成显式参数**，由调用方按目标工作区所在文件系统决定：

- `overlaps(left, right, *, casefold: bool)` —— 无默认值，强制调用方表态；
- `analyze(coord_root, *, casefold=None)` —— `None` 时按当前平台推断（`os.name == "nt"`），**并在报告里写出它按哪种假设判的**（`case_sensitivity: "insensitive"`）；
- `detail` 文案条件化：折叠时说「may write the same path」，不折叠时说「same path on a case-insensitive filesystem only」。

**关键在最后一句：报告必须说出自己的假设。** 一个按错误假设做出的判定，只要它说了假设是什么，就是可审计的；不说，就是假话。

## 冲突七：A-08（schema 文件名全对不上）改文件名还是改 `const`

### 争议点

7 份文件里 0 份能按名解析。改哪边都能让它们对上。

### 裁决

**改文件名，不许改 `const`。**

`const` 的值已经写进了**所有已发布事件**的 `schema` 字段。改 `const` 等于让历史上每一份事件都宣称了一个当时不存在的 schema 名——那是伪造。文件名只是磁盘上的寻址方式，改它不改变任何事实。

同时修 `execution-provider-catalog-v1` 的 `$id`：`.dev` 是真实 TLD 且强制 HTTPS，本项目的 `$id` 全是 `.local`，一份不一致就是第二套标准的起点。

## 我不接受红队的一条推论

红队在「最危险的三个」里写：

> R-01 修好之前，R-02 的窗口根本走不到。

**这句话是错的，而且错得危险。** R-01 与 R-02 是**独立失效**：

- R-01 让事件进不来（`role` 缺省）；
- R-02 让进来的事件看不见（只读最旧 500 条）。

如果只修 R-01，R-02 立刻从「走不到」变成「活跃」——一个跑了 500 条事件的 agent，它的 ACK 会被正确写入、正确归属，然后**读不到**。那时症状会从 `not_assistant` 变成 `candidates: 0`，看起来像「这个人真的没回」。

**修一个缺陷会让另一个缺陷从潜伏变成活跃——这是修复顺序本身会制造的风险。** 所以 F-01 与 F-02 必须同批交付，不许分批发布。这一条我写进修复计划的硬约束。

# 第二轮：SRE 加入后的裁决

## 冲突八（推翻我自己的第一条裁决）：`ack_policy="record"` 不只是「宽松」，它让整个告警子系统变成死代码

### SRE 的事实

> S-08：默认 `--ack-policy record` 让 `hold_alerts` **永不触发**（`held` 恒空），而 `status` 不显示 `ack_policy`，事后无法判断「没告警」还是「告警被关了」。

### 我上一轮的裁决

我在冲突二里写：**默认值本版不动**，理由是「在前提不成立的分支上调默认值，只是在选一种失败方式」。

### 我现在的更正

**那条裁决的前提被 SRE 这条事实改变了。**

我当时把 `record` 理解成「推进但记录」。实际上它同时做了第二件事：**`held` 恒为空 → `hold_alerts` 永远收不到输入 → 超限告警这条路径整条失效**。也就是说 `record` 不是一个「更宽松的策略」，而是**顺手关掉了一个独立的监控子系统**，而没有人被告知这件事。

这违反我自己定的第一条原则：**一个动作不能删掉一条事实。** 改默认值这个动作，删掉的是「有单卡住了」这条事实的传递路径。

更正后的裁决分三半：

1. **默认值仍然本版不动**——理由不变（前提未修，`enforce` 会钉死全 DAG）。
2. **`record` 下不告警这条设计，保留。** 我原本打算让 `record` 下也告警（只换文案），**这个打算是错的**，原文的推理比我强：

   ```
   Under ``"record"`` there is no hold left to shout about, so **no alert is
   emitted** -- the task is not stuck, and an alert that asks a person to
   abandon a finished task would be worse than silence.
   ```

   任务已经完成了。发一条「请签字放弃这张单」的告警，是在叫人去处理一件已经不需要处理的事。**噪音不是「多给一点信息」，是让人学会忽略告警。** 我撤回那半条。

3. **真正的缺陷比我原先说的窄，也更难发现**：`record` 下每张单的完成回执里都有 `released_unacked`，**信息是存在的**——但它散在几千份回执里，没有任何地方聚合，`status` 也不显示 `ack_policy`。于是「这一版放行了 47 张没有 ACK 的单」这个事实，**只能靠一条一条读回执才知道**。

   所以修法不是改告警，是**把已经存在的事实聚合出来**：
   - `status` 显示 `ack_policy` / `alerts_enabled`；
   - `status` 显示 `released_unacked_count`（从回执聚合，不新增记录）；
   - `serve` 在 `record` 下启动时，往 stderr 打一行，明确说出「未确认订单的超限告警在本策略下关闭」。

**「放行」和「不报警」是绑在一起的，这是对的；但「不报警」这件事本身没人知道，这才是缺陷。** 我第一版把它写成「绑在一起是缺陷」，是我读错了。

这一条我记在这里，是因为**它是本次审计里我自己判错、被别人证据推翻的一条**。留着它比删掉它有用。**而且我第一次推翻自己时推翻错了方向——这说明「发现自己在纠错」不等于「纠对了」。**

## 冲突九：`status` 的退出码——「我读不了」和「我读了，它坏了」必须分开

### 争议

SRE 的第一推荐是「让 `federate status` 变成能回答问题的命令」，并要求坏链时 `exit != 0`。但我在 P3（F-12）里定的通则是「被拒 → exit 2」。

两条规矩撞在一起：一个脚本跑 `status`，拿到 exit 2，它无法判断是「CLI 拒绝了我（参数错了）」还是「工作区坏了」。**这两种情况下脚本该做的事完全相反。**

### 裁决

**三个退出码，语义不重叠：**

| 码 | 含义 | 脚本该做什么 |
|---|---|---|
| 0 | 读到了，且被读的对象健康 | 继续 |
| 2 | **我拒绝执行**（参数不合法、工作区 id 不存在） | 修参数，重试 |
| 3 | 读到了，**对象不健康**（坏链、状态与日志背离、有 stuck 任务） | 报警，别重试 |

exit 3 借用 `claim_conflicts analyze` 已有的语义（`3 == BLOCKED`），**不新造一个码**。这是我第一次在本次审计里主动复用既有约定而不是新定一个——因为新定一个就是第二套标准。

**否决一种做法**：让 `status` 在坏链时也 exit 0、把问题写在 JSON 里。理由是 SRE 那条实测：exit 0 加一个没人读的字段，等于「绿色的体检报告」，而人会相信退出码。

## 冲突十：`revive --force` 会不会立刻触发 F-04 的背离告警

### 争议

F-04 要求 `recover()` 把 `state.json` 与 `events.jsonl` 重放比对，不一致就 `valid: false`。
F-16 要求 `revive --force` 让人能强行动一个 blocked 任务。

**两条都是我写的，但它们会互相打架**：如果 `--force` 只改状态不写事件，`recover()` 立刻报背离；如果它写了事件但事件格式不在重放器的理解范围内，`recover()` 报的是「日志里没有这件事」。

### 裁决

**`--force` 必须写一条 `task_forced_revive` 事件，且重放器必须认它。**

具体要求（这是实施时的硬约束，不是建议）：

- 事件 payload 带 `previous_state` / `previous_blocked_reason` / `previous_owner` / `by` / `reason`；
- `recover()` 的重放器把 `task_forced_revive` 当作「合法状态转移」，**不是**当作背离；
- 反过来：**手改 `state.json` 仍然是背离**（因为没有事件）。这正是两者的区别——`--force` 和 `vim` 做的事一样，区别只在于一个留了记录。

**这一条是本次审计的核心论点在一个具体功能上的落地**：不是禁止人绕过规则，是让绕过有记录。**禁止不了的动作，就把它记录下来。**

## 冲突十一：先修语义还是先修可观测性

### 双方的立场

- 我：P0 修证据链前提，因为「前提不成立时讨论规则是选一种失败方式」。
- SRE：`status` 不能回答问题，则**任何修复都无法被验证**——你修完 F-01，怎么证明它好了？跑探针。但运维现场没有探针，只有 `status`。

### 裁决

**两边都对，所以不排序——但有一条先后不能动：F-14 的「接线」部分必须在 P0 之后、P2 之前。**

理由是一个具体的因果链：

1. F-01 修好后，ACK 从「永远 `not_assistant`」变成「可能 `acked`」；
2. 此时如果 `status` 仍然不显示 `ack_policy` 和 `held`，运维看到的是「没告警」——而真实原因可能是 `record` 把告警关了（冲突八）；
3. **修好判定之后，「看起来正常」会变成一种更危险的假象**，因为以前至少 `reason: not_assistant` 会出现在回执里。

所以 F-14 不是「顺便做的好事」，是 **F-01 的必要配套**：修好一个判定，必须同时给出观察它的窗口，否则修完比修前更难发现问题。

**SRE 的排序直觉在这里是对的，我接受它的顺序，但保留我的理由**——不是「可观测性优先」，是「改了判定就必须同时改观察」。

## 一条我不接受的 SRE 建议

SRE 建议 `federate status` 里放 `stuck[]`，把「`state=running` 但订单 `MESSAGE_VISIBLE` 超过 N 分钟」列为卡住。

**方向对，但不能作为「卡住」的唯一判据。** 理由是 `S-07` 那条 SRE 自己发现的缺陷：

> 心跳来自 order 文件的 `updated_at`，重试会自己刷新它。只改 `updated_at`，agent 什么也没做，`stalled(900s)` 从 `True` 变 `False`。

同一个陷阱会复制到 `stuck[]` 上：如果「卡住」用 `updated_at` 算，`DEFERRED` 重试每拍刷新它，于是**永远不卡**——而 `last_progress_at` 这个名字说的是「agent 上次有进展」，实际是「调度器上次写这个文件」。

裁决：`stuck[]` 必须用**两个**时间戳并**分开显示**：
- `order_age`：订单从下单到现在（不因重试而刷新）；
- `last_agent_evidence_at`：最后一次**来自 agent 的证据**（ACK 或产物回读），没有就是 `null`。

**一个字段如果会在没人干活时自己前进，它就不是进展指标。** 这和 R-08（`sent_at` 是下单时间）是同一类错误：**字段名承诺了一件事，取值说的是另一件事。**

## 冲突十二：什么算「告警」——两条投递路径，默认值最危险的那条是默认动作

### SRE 提的问题

> 「所有告警都靠往窗口打字」这个前提对 `hold_alerts` 不成立（它只 `mkstemp+fsync+os.replace` 写文件），对 `coord-send --kind warning` 成立（`cli.py:580` 默认打字，`--mailbox-only` 才是退出）。

### 裁决

**两条都算告警，而且 `coord-send` 的默认值是反的。**

理由是「最危险的动作不该是默认动作」这条通用原则。往一个人的桌面窗口里打字是不可逆的副作用（可能落在一个正在开会的屏幕上、可能触发对方的快捷键），它必须是**显式选择**。而写文件不是副作用，它可以默认。

所以：

1. `coord-send --kind warning` 的默认改为**只写信箱**，要打字必须显式 `--dispatch`。
2. **但这个改动不能静默**：翻转默认值的那一版，凡是用到 `--kind warning` 又没给 `--dispatch` 的调用，往 stderr 打一行「从本版起不再往窗口打字；需要打字请加 `--dispatch`」。**一行，保留一个版本，然后删掉。**
3. `hold_alerts` 这条路径**不动**——SRE 说得对，客户端坏了它照样送达，这是设计对了的地方。**不要因为「统一」而去改一条已经正确的路径**，那是拿一致性冒充正确性。

### 顺带裁决 `kernel` 这个收件人

`event_id` 匹配不上时静默落到 `messages/kernel/`，agent 名变 `unknown`。SRE 那句「告警不会丢，会安静地待在 `messages/kernel/` 里，而 `kernel` 不是一个人」是本次审计最好的一句话。

裁决：**`kernel` 不许作为静默兜底。** 没有指定真人收件人时：
- 告警仍写入 `messages/kernel/`（**不丢**，这条对）；
- 但 `status` 必须显示 `alerts.undelivered: N` 和 `alerts.kernel_backlog: N`——**一个没人读的信箱，必须有一个数字让人看见它在堆积**；
- `serve --alert-to <name>` 指定真人。

**「没丢」不等于「送达」。一个文件躺在磁盘上，和一个通知被送到人手上，是两件事，而系统现在把前者报成后者。**

## 冲突十三：hash chain 的可检测性覆盖什么

### SRE 提的问题

> 红队如果得出「hash chain 保证篡改可检测」，那**只对 `events.jsonl` 成立**。`state.json` 没有 `sha256`、没有 `digest`、没有 `prev`，而它才是决定系统下一步做什么的文件。实测：手改 `t0000 -> done`，`verify()` 仍 `{'valid': True, 'head': 'a9ddfe37…'}`，head 一模一样。

### 裁决

**SRE 对，而且这不是「和红队冲突」，是「两份报告都在说同一件事」——我确认过：红队的 R-06 结论与 SRE 的 S-15 完全一致（`recover()` 报 valid 而状态已背离）。**

要裁决的是**文档的措辞**。`store.py` 的模块 docstring 写：

> a deleted, reordered or edited event is detectable rather than silently accepted

这句话本身是准确的（它说的是 **event**）。问题在于**读者会把它读成「这个工作区不可篡改」**。这个项目在 `docs/` 里多处把 hash chain 当作可信根来引用。

裁决（一条硬规矩，写进文档）：

> **可检测性的对象是事件，不是状态。**
> `events.jsonl` 的 hash chain 保证「历史没被改过」。它**不**保证 `state.json` 与历史一致——那是 `recover()` 的职责，而 `recover()` 现在只校验链、不校验一致性（A-04 / R-06 / S-15 三条从三个方向指向同一处）。

因此：
1. 所有引用 hash chain 的文档，必须同时写出它**不覆盖**什么。**一个安全性质的表述，如果不写清边界，就会被当成比它更强的保证使用。**
2. `state.json` 必须有自己的锚（A-04 的修法：把 `state` 的摘要写进一条事件，`recover()` 比对）。这样「改状态」和「改事件」会留下同样类型的痕迹。

# 第三轮：新人视角加入后的裁决

## 冲突十四：`.aep/workspace.json` 入库是「有意」还是「意外」

### 新人的提问

> 若有意 → D-01 不是 bug，但必须写进 README；若意外 → 与 `.gitignore` 自相矛盾，必须移除。我倾向「意外」，但这是意图问题，判不了。

### 裁决：**判「意外」，但理由不是猜作者意图**

意图判不了，**但矛盾判得了**。同一个仓库里同时存在两条互斥的声明：

| 声明 | 位置 | 内容 |
|---|---|---|
| 「`coordination/` 是本机状态，不入库」 | `.gitignore:9,39` | 忽略 `coordination/`、`.aep-kernel/`、`.tools/` |
| 「`coordination/` 在 `K:\...`」 | `.aep/workspace.json`（**入库**） | 硬编码绝对路径 |

**两处配置互相矛盾时，以更安全的那条为准。** 这不是猜意图，是选边——而安全的那条边恰好也是 `.gitignore` 已经选过的。

补充一条证据支持「意外」：`cli.py:2134` 写这个文件时**无条件写绝对路径**，没有任何「这个文件会入库吗」的判断。一个有意设计的东西，通常会在写的时候想过它要交给谁。

### 一个新人没提、但更关键的点

`configured_root()` 的绝对路径分支是 `return path if path.is_absolute() else workspace / path`——**绝对路径直接信任**。这意味着缺陷不在「文件入库」这一个动作上，而在**代码信任了一个不该信任的输入**。

所以修法必须两条一起（F-22）：文件出库**并且**代码拒绝跨工作区绝对路径。**只做出库，下一个把配置写错的人会重新制造同一个缺陷**；只做代码校验，仓库里仍然躺着一份指向我机器的配置。

## 冲突十五：「被拒 exit 2」是约定还是巧合

### 新人的提问

> 4 份文档承诺 exit 2；实测 `coord-claim` 作用域冲突是 **exit 3**，`grep "exit 3" docs/` = 0 命中。`cli.py:3339` 只对 `agent-evolution-claim-result-v1` 这一个 schema id 特判成 3——按 schema 字符串匹配决定退出码，不像设计，像补丁。

### 我复核的结果

`main()` 的真实形状：

```python
result = args.func(args)
if isinstance(result, dict) and result.get("schema") == "agent-evolution-claim-result-v1" and not result.get("claimed"):
    return 3
return 0
```

**新人对「像补丁」的判断成立。** 一个函数里的退出码规则按 schema 字符串分支，说明规则没有抽象出来。

### 裁决：保留 3，改掉特判，改掉文档

按冲突九已经定的三分法：

| 码 | 含义 | `coord-claim` 作用域冲突属于哪个 |
|---|---|---|
| 0 | 读到了，且健康 | — |
| 2 | **我拒绝执行**（参数不合法、工作区不存在） | 不属于：命令完整执行了 |
| 3 | 读到了，**对象说不行** | **属于**：「这个文件归别人」是一个成功的答案 |

**「你无权写这个文件」不是「我拒绝回答」，是「答案是：不行」。** 所以 3 是对的，**四份文档里承诺 exit 2 的地方是错的**，要改文档。

但特判必须换掉：

1. `main()` 不再认 schema 字符串，改认结果里的 `"blocked": true`（或等价的统一字段），**任何**结果声明被阻塞就返回 3。
2. `claim_conflicts.py:511-515` 那三处 `return 3` 与 `main()` 的规则合并成一处。
3. 新增 `docs/EXIT_CODES.zh-CN.md`：一张表，每个码 + 判据 + 一个真实命令示例。**退出码是对外契约，没有表的契约不算契约。**

**一条我不改的**：`coord-improvement validate` 失败返回 2（`EVOLUTION_EXECUTION_PACT.zh-CN.md:150`）。那个 2 表示「我拒绝把它标成 VALIDATED」——是「我拒绝」，不是「对象不健康」。**两者看起来像，但脚本该做的事不同**，所以分开。

## 冲突十六：`README.md` 和 `README.zh-CN.md` 谁是主文档

### 新人的判断

> 英文版 234 行到 v0.6.15，中文版 86 行停在 v0.5.0。若英文版是主文档，正确动作是把中文版改成一行「已停止维护」；若中文才是目标读者，要花时间把 234 行翻回去。我倾向前者。

### 我实测的更正

**前提不成立：`README.md` 不是英文文档。**

```
README.md        汉字 1295 / 拉丁字母 9936 → 汉字占比 11.5%
README.md        233 行
README.zh-CN.md  汉字 1064 / 85 行
```

`README.md` 第 3 行就是「红皇后—鲶鱼—创造性破坏：多 Agent 自治协作与进化体系。」——**它本身就是中文文档**，拉丁字母多是因为里面全是命令名、文件名、schema id。

所以「中英文两份 README」这个框架是错的。真实情况是：**两份中文文档，一新一旧。** `README.zh-CN.md` 不是 `README.md` 的翻译，它是一份 85 行的更早版本。

### 裁决

**不存在翻译问题，存在的是「两个同名概念的旧副本」。**

1. `README.md` 是唯一主文档（`pyproject.toml` 的 `readme = "README.md"` 也是它）。**不许改它的语言定位**——它是中文的，这是事实，不是缺陷。
2. `README.zh-CN.md` **删掉**，或把内容替换成三行：「本文件是 v0.5.0 时代的中文说明，已停止维护；请读 `README.md`（同样为中文，当前版本 v0.6.15）。」**保留一份 85 行的旧文档在根目录，比没有它更危险**——它看起来是权威的。
3. 文件名造成的误解要一并消除：如果将来真要英文版，文件名是 `README.en.md`，**不是把中文版叫 `README.zh-CN.md` 而让主文档叫 `README.md`**——那会让每个人（包括新人、包括 SRE、包括我）都以为主文档是英文的。**这一次三个人都被它骗了。**

## 一条新人没提、但会卡住修复方案的

`tests/test_federation_schemas.py:14-22` 把 7 个 schema 文件名写成**集合相等的字面量白名单**：

```python
assert {p.name for p in paths} == {
    "event-envelope-v1.schema.json", ...
}
```

后果有两个，方向相反：

- **加第 8 份 schema 会直接红**（哪怕它完全正确）——新人报的 D-06。
- **改文件名（F-13 要求的）也会直接红**——所以我的 F-13 按现在的写法，第一步就会被自己的测试挡住。

**这个测试编码的不是「schema 是否有效」，是「仓库里恰好有这 7 个文件名」。** 前者是要守的性质，后者不是。

裁决：把断言换成**真正要守的不变量**——

> 每个 `*.schema.json` 的文件名，必须等于它内部 `const` 去掉 `aep-` 前缀再加 `.schema.json`。

这条断言同时做到三件事：文件名与 `const` 不再漂移（F-13 的目标）、加第 8 份不会红、删掉一份会红（因为它会从 glob 里消失但引用它的代码还在——那由另一条测试守）。

**这是本次审计里「一个测试守错了性质」的最清楚例子**：它守的是一个快照，不是一条规则。快照会红得莫名其妙，规则不会。

## 总结：本次审计推翻了我自己的三条

1. **`record` 只影响推进、不影响告警** —— 错。它让告警子系统整条失效。
2. **先修语义、可观测性可以后放** —— 错。改判定必须同时改观察窗口，否则修完更危险。
3. **`record` 下应该照样告警（只换文案）** —— **错，而且这是我纠错纠反了方向。** 原文的推理是「让一个人去签字放弃一件已经完成的事，比沉默更糟」，这个理由成立。真正的缺陷是「不告警这件事没人知道」，不是「不该不告警」。

**第 3 条比前两条更重要。** 前两条是别人给的证据推翻了我；第 3 条是**我自己发现了自己的错，然后修成了另一个错**，直到我读到原文那两行折行的 docstring 才停下。

留这条，是因为它说明一件事：**「发现自己在纠错」和「纠对了」是两回事。** 一份审计报告如果只记录「我被推翻过」，读者会以为纠错一定收敛。它不一定。

留下这三条，是因为一份只有「别人错了」的裁决记录不可信。**如果审计者的判断一条都没被推翻，说明他没有真的在判断。**
