# 第二部分：三个运维问题

## Q1 · `serve` 连跑 7 天，哪一处先耗尽

**先纠正我自己。** 我此前算过「200 任务 68 MiB/天 stdout」，那个数是错的——它假设 2880 拍/天，而 200 任务时一拍要 170 秒，一天只有约 500 拍。下面是重算的实测值。

### 实测数据

同一台机器，`--no-dispatch`，连续三拍（第二拍是稳态，第一拍因为要首次投递而便宜）：

```
N=100:  tick1  14.74s  stdout=12589B  events +100
        tick2  49.21s  stdout= 6791B  events   +0
        tick3  56.05s  stdout= 6791B  events   +0

N=200:  tick1  52.29s  stdout=24789B  events +200
        tick2 164.09s  stdout=13191B  events   +0
        tick3  被我的 400 秒超时掐断，未覆盖
```

各目录单价：

```
events.jsonl      : 490 B/event
commander/inbox   : 4469 B/file（每任务每次尝试 1 个文件）
state.json        : 261 B/task
stdout（稳态）    : 68 B/task + 约 200 B 固定
```

### 结论：先耗尽的不是磁盘，是**墙上时间**

`--interval` 默认 **30 秒**。

| 任务数 | 稳态单拍 | 相对 30s 预算 | 一天能跑几拍 |
|---|---|---|---|
| 50 | 5.95s | 0.2× | 2880（受 interval 限） |
| 100 | 49.21s | **1.6×** | 1630 |
| 200 | 164.09s | **5.5×** | 508 |

**交叉点大约在 60–70 个任务。** 超过之后心跳永久落后：一拍没跑完下一拍的 30 秒已经过了，`serve` 会背靠背地跑，永远追不上。而每多一个任务、inbox 每多一个文件，下一拍还会更慢——这是发散，不是稳态。

### 第二名：`commander/inbox` 的文件数

4469 B/文件，每任务每次尝试写一个，**永不归档**（`coord-archive-stale` 只处理 `wake_queue`，`cli.py:1346-1352`）。而每一拍里，`CommanderAdapter._orders()` 为**每个任务**全量扫一遍这个目录：

```
cProfile（100 任务，17.2s 总耗时）:
  100  commander_adapter.py:82(_orders_for_task)
  101  commander.py:185(_orders)
  5056 pathlib/_local.py:539(read_text)      <- 100 个任务读了 5056 个文件
```

即每拍文件读取次数 = 任务数 × inbox 文件数。1000 任务时是 100 万次。**这是先撞墙的地方**：不是字节数，是 inode 数 × 任务数。

### 第三名：`events.jsonl` 的读取成本（不是磁盘）

490 B/event，且只在状态跃迁时增长（实测 tick1 +100，tick2/tick3 +0）。磁盘上它最慢。但 `_append_locked` 每次 append 都先 `events()` 全量读+解析整个文件（`store.py:111`），所以单价随文件线性上涨：

```
log 约  500 events: 10.8 ms/append
log 约 1000 events: 17.9 ms/append
log 约 2000 events: 18.8 ms/append
log 约 4000 events: 29.4 ms/append
log 约 8000 events: 41.7 ms/append   （4.26 MiB）
```

外推 10 万事件约 0.5s/append，且每次 append 要把 49 MiB 解析成 dict 列表。**这是延迟问题，不是容量问题。**

### 第四名：stdout 磁盘（最后才轮到）

| 场景 | 拍/天 | stdout/天 | 7 天 |
|---|---|---|---|
| 100 任务 | 1630 | 11.1 MB | **78 MB** |
| 200 任务 | 508 | 6.7 MB | **47 MB** |
| 10 任务（interval 限速） | 2880 | 2.4 MB | **17 MB** |

7 天最多 78 MB。**磁盘不会先满。** 无轮转是真的（`grep rotat|maxBytes|RotatingFile` 零命中），但它不是第一顺位的风险。

### 一句话回答

**先耗尽的是「一拍的时间预算」，交叉点约 60–70 个任务；第二名是 `commander/inbox` 的文件数（每拍按 任务数×文件数 扫描，永不归档）；磁盘排第四，7 天最多 78 MB。**

## Q2 · 3 条命令内能不能定位「哪个任务卡住了、卡在哪一步」

实测的最短路径：

```
① ls .agent-evolution/workspaces/                      <- 不是 aep 命令
   W-c2842a115502441f82608a75

② aep federate status --workspace W-c284...            <- 需要①的输出
   tasks.execute: state=blocked, note="no capable successor agent",
                  signal=no_heartbeat, owner=alpha, attempts=1
   ← 到这里你知道「哪个任务卡住了」，但不知道卡在哪一步

③ aep coord-dispatch --all                             <- 看起来对，其实是死路
   输出顶层只有两个键：preview / gate
   "state" False  "note" False  "attempts" False  "sent_at" False   <- 实测
```

也就是说：**5 步，其中 2 步是 `ls`，第 3 步是一条会误导你的命令。** 而真正的原因（订单是 `DEFERRED` 还是 `CEASED`、`note` 里写的是 `EXECUTOR_TOO_LOW` 还是 `PREINPUT_NOT_READY`）藏在 `commander/state/<order>.json` 里，没有任何命令读它。

## Q3 · 告警都靠往客户端窗口打字，那个客户端正好坏了，告警去哪了

**这个前提要分两半纠正：一半是错的，另一半比你想的更糟。**

### 一半错：`hold_alerts` 不打字，它只写文件

`hold_alerts.emit` 最终走 `_write_once(path, message)`（`hold_alerts.py:276`），只做 `mkstemp + fsync + os.replace`，**不调 `commander.dispatch`，不碰任何窗口**。模块 docstring 明确说「An alert is a message, not a transition」。

实测（`repro_alert.py`）：

```
"to": "human", "agent": "alpha", "order": "ORD-1"
→ messages/human/20261101T141947…json
→ coord-status: unread {'human': 1, ...}
→ coord-digest --agent human: unread_count 1，正文完整
```

**所以客户端坏了，这条告警照样送达。这是设计对了的地方。**

### 另一半更糟：通用告警路径确实往窗口打字，而且失败只留一个字段

`coord-send --kind warning` 的默认行为是**打进目标窗口**：

```python
# cli.py:580
dispatch_now = (getattr(args, "dispatch", False) or args.kind == "warning") \
               and not getattr(args, "mailbox_only", False)
```

`--mailbox-only` 才是退出（帮助文本：「for warning messages, opt out of the default immediate desktop attempt」）。也就是说：**同一个仓库里存在两种告警投递方式，而通用那条默认打字。**

如果那个客户端正好坏了：`commander.dispatch` 会返回 `NO_WINDOW` / `EXECUTOR_TOO_LOW` / `CEASED`。此时：

- 消息文件**已经写好了**（`cli.py:579` 先写文件，`581` 才 dispatch），所以信箱里有一份；
- 窗口里没有；
- 唯一的痕迹是 `coord-send` 返回 JSON 里的 `desktop_delivery.state` 和 `note`（`cli.py:590-593`）；
- **没有人会去读那个字段**，因为 `coord-send` 是给「我主动发一条消息」用的，返回值的语义是「发出去了」。

### 真正的答案：告警不会丢，会落在没人读的地方

按收件人分三种情况：

| 告警来源 | 投递方式 | 客户端坏了会怎样 | 谁会看到 |
|---|---|---|---|
| `hold_alerts`（超限 hold） | **只写信箱** | 照常送达 | 收件人（常常是 `kernel`，见 S-07）——**没人** |
| `coord-send --kind warning` | **默认打进窗口** | 文件在、窗口没有，返回 JSON 里 `state=CEASED` | 没人读那个字段 |
| `coord-send --kind warning --mailbox-only` | 只写信箱 | 照常送达 | 同上 |

**所以最坏的情况不是「告警丢了」，是「告警安静地待在 `messages/kernel/` 里，而 `kernel` 不是一个人」。** 唯一读法是 `coord-digest --agent kernel`，而凌晨三点没有人会想到敲这个——`coord-status` 只会告诉你 `"kernel": 1`，一个裸数字，不说它是告警、不说它多旧、不说它多严重。

### 我需要的

1. `federate serve --alert-to <human_name>`：把 `hold_alerts` 的收件人钉死成一个真人，不依赖订单的 `sender`；
2. `coord-status` 的 `unread` 从裸数字改成 `{"human": {"total": 1, "oldest_seconds": 7200, "kinds": {"warning": 1}}}`；
3. `coord-send --kind warning` 的默认改成 `--mailbox-only`（要打字得显式 `--dispatch`）——现在这个默认反了：最危险的动作是不写参数的那个。

### S-04 `doctor` 和 `coord-status` 在系统已经坏掉时说「正常」

- **复现**：`aep doctor`；`aep --coord-root <空目录> coord-status`
- **实测输出**：
  ```

  $ aep doctor
  ok = True
  failed = ['sticky_sessions_locatable']
  total checks = 14

  # 完全空的目录
  $ aep --coord-root /tmp/aep-empty coord-status
  exit=0
  "sessions": {"autoclaw": {...}, "codebuddy": {...}, "codex": {...},
               "github_copilot": {...}, "hermes_desktop": {...}, "qoder": {...}, "workbuddy": {...}}

  ```

# 第四部分：做得比一般项目好的地方

一个只会骂的 SRE 没人信，所以这部分也是实测的。

**1. `atomic_write` 是真原子，`kill -9` 之后状态干净。**（`repro.py kill9`，60 任务跑 4 秒后 `taskkill /F`）
```
--- leftover files in workspace dir ---
  .lock  1 bytes      events.jsonl  49085 bytes
  snapshots  0 bytes  state.json  15593 bytes
state.json: parses OK
events.jsonl verify: {'valid': True, 'events': 102, 'head': 'debd9993…'}
--- restart after kill -9 --- exit=0
```
`mkstemp + fsync + os.replace` 这条链是对的，`events.jsonl` 的 `flush + fsync` 也是对的。**这不是运气。**

**2. 投递是幂等的，重启不会重复下单。**（`repro_diverge.py`）磁盘满导致 `save()` 失败后重启，日志写 `already queued as 2026-11-01T1555267589790000-ec8f094f (DEPOSITED)`，订单没有被重复写入。说明作者想过「写到一半崩了怎么办」，而且想到了点子上。

**3. 告警正文是人写的，不是机器拼的。**（`repro_alert.py`）
```
AEP 超限告警 / HOLD PAST LIMIT
task: execute   agent: alpha
order: ORD-1  event: EVT-1
waited: 7200s (120 min)  limit: 3600s

这单已经投递，但 alpha 的会话里始终没有出现 AEP-ACK:EVT-1。
任务仍是 running，下游仍是 pending：超限不推进任何东西，这是刻意的。

结束等待需要签字（结果是 blocked，绝不是 done）：
  aep --coord-root … coord-ack --order-id ORD-1 --abandon --by <你> --reason "<理由>"
```
它给了**下一步要敲的那条完整命令**。凌晨三点我最需要的就是这个，而绝大多数系统的告警只告诉我 something is wrong。

**4. 告警幂等，崩溃不会重复轰炸。** `message_id` 由 `sent_at` 派生（`_message_id`），不依赖当前时钟。进程崩了重启、时钟回拨、重复 tick，都只在信箱里留同一个文件。`_write_once` 的「先查再写，输了竞态也只是写同一个路径同样的内容」这个论证是对的。

**5. `hold_alerts` 不打字，只写文件。**（Q3）这是它比 `coord-send --kind warning` 更正确的关键——告警不依赖那个可能坏掉的窗口。

**6. UIPI 报错是教科书级别的。**（`commander.py:813`）
```
EXECUTOR_TOO_LOW: UIPI refuses input from a lower integrity level;
nothing was typed -- start the executor elevated, then resume
```
说了「为什么」「什么都没发生」「怎么修」。`a11y.elevation()` 在拿不到 token 时返回 `"unknown"` 而不是 `"standard"`，注释写着「Saying so here is better than a silent no-op three steps downstream」——这个判断是对的。可惜它只落在 `commander/state/<order>.json` 的 `note` 里，`federate status` 不显示（S-03）。

**7. `workspace_lock` 的 Windows 细节是被真实 bug 教出来的。**（`locking.py`）`_open_lock_file` 重试 `PermissionError`（两进程同时 `O_CREAT` 的竞态）、`fstat` 后补写首字节并容忍 `EACCES`（注释说清了「这是冗余不是失败」）、释放时关句柄（否则 Windows 删不掉工作区目录）。三条都不是抄的。

**8. docstring 诚实得罕见。** `supervisor.step` 自己写「That is a real loss of visibility … the price of the relaxation rather than a detail」；`hold_alerts` 自己写「this closes the 'nobody was told' gap, not the 'nobody looked' one」。一个会在文档里承认自己放弃了什么的项目，比一个声称全都做到了的项目可信。

# 第五部分：如果只允许修三件事

排序标准：**修完之后我的夜班能少醒几次。**

## 第一件：让「哪个任务卡在哪一步」变成一条命令

现在需要 5 步、2 步是 `ls`、第 3 步是死路（Q2）。这一条修好能消掉一半「不知道发生了什么」的起床。

- `aep federate list` —— 无参数（S-01）
- `aep federate explain --task <id>` —— 替我做 task↔order 的 join（S-03）
- `federate status` 加 `chain{valid,events,head}`（接已写好的 `verify()`）、`supervisor{pid,last_tick_at,ack_policy,alerts_enabled}`、`adapters[].source`、`at_local`（S-02/S-04/S-07/S-09/S-15）

其中 `chain`、`supervisor`、`adapters[].source` 是纯接线。

## 第二件：给 `blocked` 一条 CLI 出路

现在单 agent 场景 15 分钟内必然进入一个 `revive` 拒绝、`tick` 不碰、报错指向不存在命令的状态（S-05）。这一条修好能消掉「我醒了但什么都做不了」的那几次——那种最难受，因为已经醒了还是只能 `vim`。

```
aep federate revive --task X --by Y --reason Z --force
```
配套：`events()` 容忍尾部半行（S-09），否则磁盘满之后连 `--force` 都跑不了。

## 第三件：别让心跳追不上自己

交叉点约 60–70 任务（Q1），之后永久落后且没有任何指标说这件事（S-12）。

- `commander._orders()` 每拍只扫一次——单这一条就能把 100 任务从 49s 降到个位数
- `aep coord-archive-orders --older-than-hours 72`
- `serve --log-level` 默认 `quiet`，只输出变化行
- `events.jsonl` 轮转
