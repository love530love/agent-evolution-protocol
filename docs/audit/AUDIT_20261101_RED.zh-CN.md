## R-02 `read_events(limit=N)` 返回的是**最旧**的 N 条，而且上限硬编码 500；转写一超过 500 条，ACK 就永久不可见

- **场景**：一个正常跑上几小时的会话就会产出几百条事件。`transcript_bus.read_events` 按文件名（时间戳）升序遍历，凑够 `limit` 就 `break`；`limit` 被限制在 `1..500`。所有调用方（`commander.check_acks`、`CommanderAdapter.ack_verdict`、`supervisor._result_blocks`、`digest()`）都把它当"最近的历史"用，`digest()` 甚至写了 `read_events(...)[-since_events:]`——取尾部，说明作者的意图确实是"最新"。
- **证据**（`docs/audit/repro/r03_read_events_returns_oldest.py`，先发 500 条普通对话、再发那条带 token 的回复）：

```
ack event id = 20261101T155540199312Z-4dfb1d8eb119
events returned          = 500
newest returned id       = 20261101T155540176030Z-e4db12234bb1
ack event is in the list = False
verdict.state    = sent_unacked
verdict.accepted = False
verdict.candidates = 0
check_acks       = []
limit=501 -> ValueError limit must be 1..500
event files on disk      = 501
newest file on disk      = 20261101T155540199312Z-4dfb1d8eb119
```

- **实际说了什么**：`verdict.candidates = 0`、`state = "sent_unacked"`、`check_acks` 返回空——即"整个转写里没有任何一条带 token 的事件"。磁盘上有 501 个事件文件，最新那个就是 ACK，API 没有任何参数能读到它。
- **应该是**：返回最新的 500 条（或者至少让调用方能用 `after=` 游标读到尾部）；`candidates` 应为 1，`state` 应为 `acked`。
- **谁会怎么被坑**：长跑工作区。前 500 条事件把窗口占满之后，ACK 检测、产物回读（`_result_blocks` 只看得到最初的 500 条）、`digest()` 全都冻结在早期内容上。症状是"越跑越像所有 agent 都不说话"，而 `verdict.rejected` 里连一条 `stale`/`foreign_session` 都没有——因为那些事件根本没被读进来。运维会去重启客户端、重发派工，实际只需要读第 501 个文件。
- **严重度**：`说假话`（"没有候选事件"）+ `静默失效`
- **置信度**：`实测`
- **复现**：`docs/audit/repro/r03_read_events_returns_oldest.py`

## R-03 两个进程同时认领同一路径，**两个都被告知 `claimed: true`**；八个进程是八个都成

- **场景**：`claim_conflicts.claim()` 是"先 `gate()` 再 `mkdir(exist_ok=False)`"，两步之间没有锁，也没有原子性。两个 agent 在同一瞬间认领 `src/shared.py`（不同 task id → 不同目录 → `mkdir` 都会成功）。
- **证据**（`docs/audit/repro/r12_claim_race.py`，`ProcessPoolExecutor` + 同一时刻起跑）：

```
trial 0: 2 processes -> claimed 2/2  [(0, True, ''), (1, True, '')]
trial 1: 2 processes -> claimed 2/2  [(0, True, ''), (1, True, '')]
...
two processes both won 10/10 trials

8 processes      = [(0, True, ''), (1, True, ''), (2, True, ''), (3, True, ''), (4, True, ''), (5, True, ''), (6, True, ''), (7, True, '')]
claimed: true    = 8 of 8
owners on disk   = ['agent0', 'agent1', 'agent2', 'agent3', 'agent4', 'agent5', 'agent6', 'agent7']
analyze.status   = CONFLICT blocking = 28
```

- **实际说了什么**：每个进程拿到的都是 `{"claimed": true, "task": "task<i>", "agent": "agent<i>", "paths": ["src/shared.py"], ...}`。也就是系统对 8 个 agent 各说了一次"这个文件归你"。事后 `analyze()` 自己算出 28 条 blocking 冲突，等于承认前面那 8 句里有 7 句是假的。
- **应该是**：只有一个 `claimed: true`，其余返回 `{"claimed": false, "reason": "scope_conflict"}`（这是串行执行时它们会得到的正确结果，脚本里 trial 2/3/9 单进程先赢的情况下就是这样）。
- **谁会怎么被坑**：两个 supervisor（或一个 supervisor + 一个手工 `aep coord-claim`）同时启动时。两个 agent 都收到"你已认领"的确认，都去改同一个文件，后写的覆盖先写的。模块自己的 docstring 写着"it refuses to create a claim whose scope already belongs to a live lease ... never overwrites another owner"——这句话在并发下不成立。这是本项目最容易造成真实数据丢失的一条：`claim` 的全部意义就是让"我能不能写"这个问题只有一个答案。
- **严重度**：`说假话`
- **置信度**：`实测`
- **复现**：`docs/audit/repro/r12_claim_race.py`

## R-04 `claims/<task>/` 里只要有一个没有 `owner.json` 的目录（崩溃残留），系统就同时说三句互相矛盾的话

- **场景**：`claim()` 先 `mkdir(parents=True, exist_ok=False)`，再写 `owner.json.partial` 再 `replace`。中间被 `kill -9`，留下一个空目录。复现里直接 `mkdir` 模拟这个状态。
- **证据**（`docs/audit/repro/r04_claim_orphan_dir.py`）：

```
healthy claim: true
gate.status            = ALLOWED allowed = True
claim.claimed          = False
claim.reason           = task_already_claimed
claim.owner            = None
analyze.status         = CLEAN claims = 1
_claim_scopes          = []
task.state after       = running
sibling claim.claimed  = True reason = None
```

- **实际说了什么**，三句话：
  1. `gate()`：`status: ALLOWED, allowed: true` —— "这个路径没人占，你可以写"；
  2. `claim()`：`claimed: false, reason: "task_already_claimed", owner: null` —— "这个 task 已经被认领了"（但没有 owner，也没有 owner.json）；
  3. `supervisor._claim_scopes`：返回 `[]`，`task.state` 仍是 `running` —— "这个任务的写范围已经处理好了"，于是回执里连一行 `claimed: false` 都没有。
- **应该是**：三处应当一致地说"这个 task 有一个残破的 claim 记录，需要清理后重新认领"，并**阻塞**这个任务（`_claim_scopes` 对真正 `claimed: false` 的分支是会 `blocked` 的，只有"目录存在"这一条提前 `continue` 掉了）。
- **谁会怎么被坑**：任何在 `claim()` 写盘期间被杀过一次的工作区。此后：`_claim_scopes` 永远跳过这个 task，任务照跑，**没有任何租约覆盖 `src/app.py`**；同时另一个 agent 可以用别的 task 认领同一路径并成功（上面 `sibling claim.claimed = True`）。两个写入者同时改同一文件，而工作区的记录说"已认领"。手工恢复也做不到：`claim()` 只会继续回 `task_already_claimed`，唯一出路是有人知道去 `rmdir` 那个目录——文档里没有这条。
- **严重度**：`说假话`（"已认领"）+ `静默失效`（守卫被跳过）
- **置信度**：`实测`
- **复现**：`docs/audit/repro/r04_claim_orphan_dir.py`

## R-05 同一时刻、同一目录，`analyze()` 说 `CONFLICT / write_allowed=false`，`gate()` 说 `ALLOWED`

- **场景**：有一条 claim 的 scope 无法规范化（例如 `../outside/secret.txt`）。`analyze()` 把它记为 `invalid_scope`、`severity: blocking`、`write_allowed: false`；`gate()` 重新从 `analyze()` 的冲突列表里挑 blocking，但只保留 `unreadable_claim` 和 `duplicate_task_id` 两种（`claim_conflicts.py:271-273`），`invalid_scope` 在这里被丢掉。
- **证据**（`docs/audit/repro/r05_analyze_vs_gate.py`）：

```
analyze.status       = CONFLICT
analyze.write_allowed= False
analyze.blocking     = 1
analyze.conflicts    = [{"kind": "invalid_scope", "severity": "blocking", "path": "../outside/secret.txt"}, {"kind": "stale_claim", "severity": "warning", "path": ""}]
gate.status          = ALLOWED
gate.allowed         = True
gate.blocking        = []
cli analyze exit     = 3
cli gate exit        = 0 (0 == ALLOWED, 3 == BLOCKED)
```

- **实际说了什么**：`aep ... claim_conflicts analyze` 退出码 3（"有 blocking 冲突，别写"），`aep ... claim_conflicts gate` 退出码 0（"可以写"）。两个命令，同一个 `coord_root`，同一秒。
- **应该是**：`gate()` 的 `blocking` 至少包含 `invalid_scope`，`allowed: false`，退出码 3——因为"有一条 claim 的 scope 我读不懂"和"有一条 claim 的文件读不出来"是同一类不确定性，而 `gate` 的 docstring 自己写着"An unreadable claim makes the ownership map untrustworthy, so it blocks instead of guessing"。
- **谁会怎么被坑**：写代码前跑 `gate` 的那个 agent（退出码 0 → 放心写），和跑 `analyze` 的那个人（退出码 3 → 以为已经拦住）。两个人看同一个仓库，得到相反结论；而 `claim()` 内部调用的也是 `gate()`，所以它会在 `analyze` 说"冲突"的目录上**创建新 claim**。CI 里挂 `analyze` 会红，挂 `gate` 会绿，谁挂哪个就成了两套标准。
- **严重度**：`说假话`
- **置信度**：`实测`
- **复现**：`docs/audit/repro/r05_analyze_vs_gate.py`

## R-06 `complete()` / `add_task()` 把没有重新读过的 state 整体写回；事件日志说做完了，state.json 说还没开始，`recover()` 说一切正常

- **场景**：`engine.update()` 的 docstring 明写"两个各自 load 过 state 的调用方仍然会丢掉其中一个写"，并让并发调用方改走它。但 `add_task` / `complete` / `pause` / `resume` / `ingest_external` / `report_conflict` 都没走它，`supervisor._settle` 更是先 `load` 一次、再在循环里反复 `complete`。
- **证据 A（进程内，`docs/audit/repro/r06_lost_update_complete.py`）**：

```
state.json execute.state = pending
state.json has publish   = True
event kinds              = ['workspace_created', 'checkpoint', 'task_added', 'task_added', 'task_done', 'task_added']
recover() says           = {'workspace_id': 'W-7d2e4a73e81c46f8bc7664f1', 'paused': False, 'tasks': 3, 'events': 6, 'snapshot': {'valid': True, ... 'tasks': 0}}
ready_tasks()            = ['execute', 'publish']
```

- **证据 B（4 个真实进程，`docs/audit/repro/r13_concurrent_add_task.py`）**：

```
task_added events   = 40
tasks in state.json = 10
missing from state  = ['t0-0', 't0-1', 't0-2', 't0-3', 't0-4', 't0-5', 't0-6', 't0-7']
chain.valid         = True events = 42
recover().tasks     = 10
```

- **实际说了什么**：`events.jsonl` 里有 `task_done(execute)`，`state.json` 里 `execute.state == "pending"`，而 `recover()` 返回 `chain.valid: true` 并报告 `tasks: 3`（A）/ `tasks: 10`（B）。B 里 40 条 `task_added` 事件对应的 30 个任务从 DAG 里消失了，`recover()` 说链路完好。另外 A 的输出里 `recover()` 同时给出 `tasks: 3` 和 `snapshot.tasks: 0`（快照只在 `create` 和 `_handoff` 时重建），两个数字并排出现且都被标成有效。
- **应该是**：`state.json` 与 `events.jsonl` 不一致时，`recover()` 必须报告 `valid: false`（这正是"hash 链 + 状态"这套设计存在的理由：`store.py` 的模块 docstring 说"a deleted, reordered or edited event is detectable rather than silently accepted"）；`complete`/`add_task` 应当在锁内重新读取，或直接走 `update()`。
- **谁会怎么被坑**：`supervisor.step` 里 `_settle` 与 `engine.tick` 是同一进程顺序执行，但 supervisor 和 scheduler 常常是两个进程（`serve` 与手工 `aep federate tick`）。一旦撞上，`ready_tasks()` 会把一个**已经做完**的任务重新排进队列（A 的输出就是 `['execute', 'publish']`），agent 被要求把同一件事再做一遍；而 `recover()` 这个"重启后重建同一幅画面"的函数，对"画面和日志不一致"这件事一个字都不说。
- **严重度**：`说假话`（`recover` 的 valid）
- **置信度**：`实测`
- **复现**：`docs/audit/repro/r06_lost_update_complete.py`、`docs/audit/repro/r13_concurrent_add_task.py`

## R-07 快照里叫 `sha256` 的字段不是文件的 SHA-256

- **场景**：`snapshot.artifact()` 写的是 `digest({"bytes": path.read_bytes().hex()})`——对"字节的十六进制字符串包在 JSON 里"再取 SHA-256。任何按字段名去核对的人（`sha256sum`、`hashlib.file_digest`、另一份实现同一 schema 的代码）都会得到不同的值。
- **证据**（`docs/audit/repro/r07_artifact_sha256.py`）：

```
snapshot.artifact().sha256 = fa162c6ea89b8a6f8b12d0e0a0940304798f9bec8e17692b2ad322cefd2089d2
sha256 of the file bytes   = 51bc0fc1f19104fa6e89ce50be9aa1f57c3346c1ca51ab49f5f00e14ce8f8076
equal                      = False
same bytes, other name     = True
verdict a verifier reaches = TAMPERED
```

- **实际说了什么**：`{"name": "report.md", "sha256": "fa162c6e...", "path": "...", "size": 15, ...}`——字段名叫 `sha256`，值与文件内容的 SHA-256 不同。`snapshot.py` 的模块 docstring 说"Finished artifacts as `{name, sha256, path}`. Content stays on disk; the snapshot only pins it."
- **应该是**：`sha256` 等于 `hashlib.sha256(bytes).hexdigest()`；如果作者想要的是"带域名分离的摘要"，字段名应叫 `digest` 并写清域，而不是复用 `sha256` 这个名字。
- **谁会怎么被坑**：做交付审计的人。`artifact` 是"这个产物被钉住了"的唯一凭据；用标准工具核对得到不一致，第一反应是"文件被改过"（我自己跑出来的结论就是 `TAMPERED`）。要么误判篡改，要么反过来——发现"每次都能对上"之后，就不再相信任何 sha256 字段，包括 `snapshot.digest`、`anchor.sha256`、事件链的 `sha256`，那些是真的。**一个名字叫错的字段会污染同一个文件里所有叫对的名字。**
- **严重度**：`说假话`
- **置信度**：`实测`
- **复现**：`docs/audit/repro/r07_artifact_sha256.py`

## R-11 防重发的"进程死亡栅栏"被拆成两个文件写，而重启只读其中一个——在两次写之间被杀就会重发

- **场景**：`dispatch()` 说"Keep the lock through delivery and durably fence process death before touching discovery/launch/transport. A later caller must not replay a send just because the final adapter receipt was never written."。`_mark_dispatching` 先 `_atomic(commander/state/<id>.json)`，再 `_atomic(commander/inbox/<id>.json)`。而 `_orders()`（所有判定逻辑的唯一入口）只读 `inbox/`；`state/` 目录全仓库只有 `delivery_audit.py` 会读。

## 我认为最危险的三个

### 1. R-01（role/direction 永远 `unknown`，ACK 与产物回读两层同时失效）

不是因为它最难修——加两行就能修——而是因为**它让整个"证据链"变成装饰，同时回执还在主动说假话**。这个项目的核心承诺是"只有 agent 自己写下的事实才算完成"。现在：ACK 判定的输入永远是"这一行不算 agent 说的"，产物回读的 `match` 永远是 `None`，`hold_result_mismatch`（agent 声称 `docs/claimed.md`、转写里却是 `docs/other.md`）永远不会触发——那个测试是通过手工补 `role="assistant"` 才绿的。更糟的是默认策略 `ack_policy="record"` 会把后果写成一张**看起来已经处理过**的回执：`action: "released_unacked"`、`reason: "not_assistant"`。操作者读到的是"这批客户端不支持 ACK"，于是会去做两件错事之一：换客户端，或者切回 `enforce`（那会把所有任务永久钉死）。**它把"我不知道"写成了"对方没回"，而"对方没回"会直接导致签字放弃。**

### 2. R-03（两个进程同时认领同一路径，两个都被告知 `claimed: true`）

因为这是唯一一条**会在真实文件上造成不可逆损失**的：两个 agent 各自拿到"这个文件归你"的确认，各自改，后写的覆盖先写的，而且谁都没有违反协议。它 10/10 可复现（两个进程），8/8（八个进程），不需要极端时序。`claim` 这个机制存在的唯一理由就是让"我能不能写"只有一个答案；现在它在并发下的答案是"都能写"。而事后的 `analyze()` 会报 28 条冲突——**系统有能力发现这件事，只是在写入发生之后才发现**，那时文件已经坏了。R-04（孤儿目录）是同一个洞的崩溃版本，R-05（analyze/gate 相反）是同一个洞的"两个答案"版本，三条指向同一个结构性缺失：`claim` 的"检查"和"占有"不是一步。

### 3. R-06（`complete`/`add_task` 丢写，`recover()` 说链路完好）

因为它**污染了唯一被信任的那份记录**。整个架构的信任根是"事件日志是 hash 链，删改会被发现"。R-06 里没有任何删改：40 条 `task_added` 事件都在，链是好的，`recover()` 返回 `valid: true`——但 `state.json` 只有 10 个任务，而且 `ready_tasks()` 会把一个日志里已经 `task_done` 的任务重新排进队列。这意味着**"日志完好"不再等价于"状态可信"**，而 `recover()` 这个专门用来回答"重启后能不能信磁盘"的函数，对两者不一致这件事一句话都不说。R-06 与 R-11 是一对：一个让"做完了"变成"没做"，一个让"发过了"变成"没发"，两者的后果都是让 agent 把同一件事再做一遍，而审计记录会显示两次都是合法的。

**为什么不是别的**：R-02（500 条上限）后果同样严重，但它需要 500 条事件才发作，而 R-01 从第一条事件起就发作——R-01 修好之前，R-02 的窗口根本走不到。R-08（`sent_at`）会误导人去签字放弃，但那张单本身确实没 ACK，损害是"提前放弃"而不是"错误完成"。R-09/R-12/R-13 是崩溃，按这次的标准，崩溃是**可接受的失败**：它吵闹、可定位、不会让人基于假话做决定。

```
no artifact      -> match = None reason = claim_without_artifact
```

（上面两行 `duplicate task id` 分别是"第一次插入"和"第二次插入同一个 id"；第一次 `ACCEPTED` 是正常的，第二次被拒才是被测的那一条。）

具体结论：

- **DAG 形状**：自环、依赖不存在的节点、重复 task id 全部被 `add_task` 拒绝（拒绝的是"不存在的依赖"，不是"自环"——效果一样：自环建不出来）。菱形和长链没有专门的守卫，但因为 `deps` 只能指向已存在的任务，环在构造上不可能。**这一块是真的结实。**
- **并发写 `state.json`**：`engine.update()` 在 4 进程 × 10 次下 40/40 无丢失，说明锁和"锁内重读"这套机制本身是对的——问题只在于有一半的写入口没走它（R-06）。
- **路径越界**：`normalize()` 对绝对路径、盘符、`..`、空串全部拒绝而不是"改写成一个看起来安全的值"，并且理由写得很清楚。**这是我在整个代码库里看到的防御质量最高的一处。**
- **`result_readback` 的三值逻辑**：空转写 → `None`（不是 `True`），`phase=done` 但没给路径 → `None` + `claim_without_artifact`，`may_complete()` 只认 `match is True` 且 `reason` 为空。**"`None` 不是 `True`"这条过去的教训确实被守住了**——只是它守的那个函数在生产里拿不到输入（R-01）。
- **`ack_protocol.abandoned()` 与 `may_advance()`**：放弃优先于 ACK、`may_advance` 对非本 schema 的 dict 返回 `False`。这一条我按"迟到 ACK 撤销签字"的老缺陷去找，**没有找到新的**。
- **`_preinput_retryable` 的默认值**：不确定的一律 `False`（不可重试），只有能在 receipt 里指名道姓证明"没输入"的几类才放行。方向是对的。
- **`dispatch_gate` 的缺省**：`profile is None` / `workspace is None` / `window is None` 都记成 `checked: false` 而不是 `ok: true`，回执里 `checked` 有计数。这是本项目里少数"我不知道"能被区分出来的地方。

## 没跑通 / 没覆盖的

- **真实桌面链路**（`_uia_deliver` / `_profiled_deliver` / `cdp.deliver`）没有实跑：需要 pwsh + 真实客户端窗口，且按约束不该去碰用户的桌面。R-11 因此只证明了"重发决策已做出"，没有执行真正的打字。**这一点我在 R-11 的置信度里标了。**
- **`ui_fallback` 的 `agent_accepted`**：`_dispatch` 在 `transport == "profiled-ui"` 且 `agent_accepted and task_delivered` 时直接记 `AGENT_ACK`。我没能确认这个布尔值是"challenge-response 真的成立"还是"屏幕上看到了 token"——如果是后者，那就是"自己的请求被当成回复"的翻版。**未验证猜测，没有写进发现列表。**
- **`engine.ingest_external` / `report_conflict` / `pause` / `resume`** 与 R-06 是同一类丢写，我按同一根因归入 R-06，没有单独实测每一条。
- **时钟**：`sent_at` 在未来、`created_at` 比 `recorded_at` 晚、跨年、闰秒，我只覆盖了"`created_at` 在未来 → 真回复被判 `stale`"（读码），没有构造实测。`_moment()` 系列函数对 naive 时间统一补 UTC，行为一致，没看到新的假话。
- **编码**：中文/emoji 在 JSON 里（`ensure_ascii=False` 全程一致）、UTF-8 BOM 的 `state.json`（会让 `engine.load` 抛 `JSONDecodeError`，属于 R-09 同一类）、非 ASCII 文件名（`artifact()` 用 `Path.read_bytes`，没问题）。没有发现独立的"说假话"，不单列。
- **`workspace-snapshot-v1` 与 `event-envelope-v1` 的 schema 校验**：本机没有 `jsonschema`（`pyproject.toml` 里是 test-only extra），我没有安装它，所以"schema 校验通过但其实校验了空对象"这一条**没有实测**。`snapshot.verify()` 只校验 `schema` 常量、`workspace_id`、锚点、自摘要和 `dag.nodes` 是 list——不校验节点字段、不校验 `artifacts` 内容，所以"schema 校验通过"这句话本身能提供的信息比它听起来少，但这一条我按 `读码推断` 记，没进发现列表。
