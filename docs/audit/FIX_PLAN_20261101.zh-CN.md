# 修复方案：从 v0.6.15 到可用的证据链（2026-11-01）

本方案不是缺陷清单的重排。清单在 `AUDIT_20261101_RED/SRE/NEWHIRE` 与 `AUDIT_20261101_LEAD` 里。
本文回答一个问题：**按什么顺序修，才不会在修 A 的时候让 B 从潜伏变成活跃。**

排序原则（按优先级）：

1. **前提先于规则**。一条判定规则的前提在现实中不成立时，调规则的参数（默认值、阈值、策略）只是在选一种失败方式。
2. **修复不能互斥**。如果修 A 会让 B 从「走不到」变成「活跃」，A 和 B 必须同批发布。
3. **不可逆的先修，但不可逆 ≠ 最优先**。认领竞态（R-03）是唯一会在真实文件上造成不可逆损失的，它与 F-01/F-02 不共享文件，因此并行。
4. **说假话 > 崩溃**。崩溃吵闹、可定位、不会让人基于假话做决定。**一个安静地说「对方没回话」的系统，比一个抛异常的服务器危险。**

# P0：地基（必须同批，否则互相引爆）

## F-01 让 ACK 判定接受「未归属但非己方」的行

**缺陷**：`ack_protocol.classify` 前两道守卫 `role != "assistant"` / `direction != "incoming"`，而生产三个采集点（`transcript_patrol.py:137`、`commander.py:443`、`cli.py:2752`）**一个都不传**，默认 `"unknown"`。实测：真实路径写出的 ACK → `accepted=False / not_assistant`；同一文本手工补 `role="assistant"` → `acked`。全仓 `src/` 里 `role="assistant"` 出现 **0** 次，`tests/` 里 **17** 次。

**为什么不能按红队说的「加两行」**：见 `DEBATE_20261101` 冲突一。采集层不知道整屏归属，给它写 `assistant` 是让它撒谎；而订单正文里就带着 token（`commander.py:161` 存 `"text": body`），补两行会让**每张单在下单同一秒自己 ACK 自己**。

**修法**（`coordination/ack_protocol.py`）：

1. `classify()` 增加参数 `own_text: str = ""`（订单正文）与 `line: str = ""`（命中 token 的那一行）。
2. 守卫改为三分支，`REASONS` 由 7 条扩到 9 条：

| 条件 | reason | accepted |
|---|---|---|
| `role == "assistant"` | —（通过） | 继续后续判定 |
| `role` ∈ {`user`, `system`} | `not_agent_role` | False |
| `role == "unknown"` 且命中行是己方正文（去空白后相等或包含） | `own_text` | False |
| `role == "unknown"` 且非己方正文 | —（通过） | 继续，证据里标 `role_source: "inferred_absent_own_text"` |

3. `direction` 同法：`incoming` 通过；`outgoing` 判 `own_text`；`unknown` 走与上面相同的替代保护。**不许把 `direction` 直接删掉**——它是「这一行是我们发的」的唯一显式声明，删了就把保护全押在文本比对上。
4. `verdict()` 把 `order.get("text", "")` 传给 `classify`。
5. `result_readback.observe()` 有**同一道守卫**（`role != "assistant"`），必须同批改。`hold_result_mismatch` 现在永不触发，正是这条。

**验收**（必须是真实路径，不是测试里手工补 role）：

- 新增 `tests/test_ack_real_capture.py`：**走 `transcript_bus.publish()` 的默认参数**写事件，断言 `accepted is True`。这是本次审计最重要的一条测试——它测的是「产品自己的调用方式」。
- 新增反向用例：把订单正文原样 publish 一次，断言 `reason == "own_text"` 且 `accepted is False`。**没有这条，F-01 就只是把守卫拆了。**
- 复跑 `docs/audit/repro/r01_ack_role_never_set.py`，输出必须变成 `accepted=True / acked`。

## F-02 `read_events` 的方向

**缺陷**：按文件名升序收集，凑够 `limit` 就 `break` → 返回**最旧**的 N 条。调用方一律 `limit=500` 且不传游标（`commander.py` ×3、`commander_adapter.py:196`、`supervisor.py:206`）。`digest()` 里那句 `read_events(root, limit=500)[-since_events:]` 是**作者自己写的变通**——说明意图是「最新」，只有一处补了，五处没补。

**修法**（`coordination/transcript_bus.py`）：

1. **不传 `after` = 问「现在是什么状态」** → 返回**最新**的 `limit` 条（收集完再 `[-limit:]`）。
2. **传 `after` = 向前翻页** → 保持现状（游标之后最旧的 `limit` 条），这是流式语义，是对的。
3. 两条语义写进 docstring，并说明「没有游标时返回最旧，是本项目历史上唯一一处『API 名与行为相反』的地方」。
4. `limit` 上限 500 保留，但**新增 `read_newest(coord_root, agent, limit)`** 供「我只要最近几条」的调用方用，避免它们为了拿 6 条而扫 500 条。

**验收**：

- 新增测试：写 `limit + 20` 条事件，断言返回里**包含最后一条**、**不含第一条**。当前 1061 个测试里**一条截断方向的都没有**。
- 新增测试：`after=<第 10 条>` 时返回的**第一条**是第 11 条（向前翻页语义不许被上面那条改坏）。
- 复跑 `docs/audit/repro/r03_read_events_returns_oldest.py`：`contains the ACK?` 必须变 `True`。

**硬约束**：F-01 与 F-02 **同批发布**。理由见 `DEBATE_20261101` 末节——只修 F-01 会让 F-02 从「走不到」变成「活跃」，症状从 `not_assistant` 变成 `candidates: 0`，看起来更像「这个人真的没回」。

## F-03 认领的「检查」与「占有」变成一步

**缺陷**：`claim_conflicts.claim()` = `gate()` 再 `mkdir(exist_ok=False)`，两步之间无锁。实测（`r12_claim_race.py`）：2 进程 **9/10 双赢**（红队报 10/10），8 进程 **8/8 全赢**，事后 `analyze()` 自己报 28 条 blocking——**系统有能力发现，只是在写入发生之后**。

**这是本次审计唯一一条会造成不可逆数据损失的缺陷。**

**修法**（`coordination/claim_conflicts.py`）：

1. 在 `coordination/claims/.lock` 上加文件锁（复用 `federation/locking.py` 已有的实现，**不新写一套**），把 `gate()` + `mkdir()` + `owner.json` 替换**整体**放进锁内。
2. 锁内必须**重新** `gate()`——锁外读到的结论在等待期间已经过期。这与 `federation/engine.update()` 的「锁内重读」是同一个教训，**用同一个写法**。
3. `claim()` 的 docstring 里「never overwrites another owner」这句话，只有在上面两步做完之后才成立；在此之前它是一句假话，**修完前不许留这句话**。

**已病处置**（修代码只防未来，盘上可能已有 8 个 owner）：

4. 新增 `aep coord-claim-conflicts resolve --coord <root> --keep <agent> --drop-others`：按 `analyze()` 的 `path_overlap` 分组，保留一个 owner，其余目录**移动到 `claims/.resolved/<timestamp>/`**（不删——一个动作不能删掉一条事实），并写一条事件记录「谁在什么时候裁决了哪几个 claim」。
5. `analyze()` 的输出新增 `case_sensitivity` 字段（见 F-13）。

**验收**：

- `r12_claim_race.py` 复跑：2 进程 **0/10 双赢**、8 进程 **1/8 成功**。这条测试要**跑 10 次**才算数（竞态测试跑一次通过是运气）。
- 新增测试：`resolve` 之后 `analyze().status == "CLEAN"`，且被移动的目录仍在盘上、有事件可查。

# P1：让说假话的地方改说真话

## F-04 `complete`/`add_task`/`pause`/`resume` 走 `update()`

**缺陷**：`engine.update()` 的 docstring 自己写着「两个各自 load 过 state 的调用方仍然会丢掉其中一个写」，并让并发调用方改走它。但 `add_task`(94)、`complete`(462)、`pause`(729)、`resume`(740)、`ingest_external`、`report_conflict` **都没走**。实测：4 进程 × 10 次 → 40 条 `task_added` 事件、`state.json` 只剩 10 个任务、**30 个从 DAG 消失**，而 `chain.valid: True`、`recover().tasks = 10`。

**后果不是「少几个任务」**：`ready_tasks()` 会把日志里已经 `task_done` 的任务重新排队——**做完的活会被再派一次**。

**修法**：

1. 这六个函数改为 `(root, workspace_id, ...)` 签名，内部 `with workspace_lock(...)` → `load` → 改 → `save`。**不要**让调用方自己拼 `update()`——现在的问题正是「有正确写法但没人用」，把它变成默认路径，而不是继续靠自觉。
2. 保留 `update(root, workspace_id, change)` 作为逃生口（P2 的 `revive` 已在用）。
3. **兼容层**：保留旧签名 `complete(root, state, ...)` 作为 `DeprecationWarning` 包装，内部丢弃传入的 `state`、重新 `load`。这样 `supervisor._settle` 里「先 load 一次、循环里反复 complete」的写法自动变正确，**不需要同时改 supervisor**。
4. `recover()` 新增一致性校验：把 `events.jsonl` 重放出 DAG，与 `state.json` 比对；不一致 → `valid: False` + `reason: "state diverged from log at seq N"` + 列出差异任务。

**验收**：

- `r13_concurrent_add_task.py` 复跑：40 事件 → 40 任务。
- `r06_lost_update_complete.py` 复跑：`state.json` 的 `execute.state` 必须与日志的 `task_done` 一致。
- 新增测试：手改 `state.json` 让某个任务 `running→done`，断言 `recover()['valid'] is False`。**这条测试是 A-04 的解药**——现在手改完全不可检测。

**注意一条反对意见**：`recover()` 变严格会让**现有工作区**在升级后立刻报 `valid: False`（因为历史丢写已经发生）。这是**正确的**，但必须给出路：`recover --accept-divergence --confirm` 把当前状态写成新的基线并记一条事件。不许静默通过。

## F-05 残破 claim 目录不许被跳过

**缺陷**：`claims/<task>/` 有目录无 `owner.json`（`mkdir` 后被杀）时，三处同时说三句互相矛盾的话：`gate` 说 `ALLOWED`、`claim()` 说 `task_already_claimed`（但 `owner: null`）、`supervisor._claim_scopes` 返回 `[]` 让任务照跑。而另一个 agent 用别的 task 能成功认领同一路径。

**修法**：`_claim_scopes` 与 `gate()` 对「目录存在但 `owner.json` 缺失/不可解析」的情况，**统一判 `blocked`，reason 用 `claim_record_torn`**，并在回执里给出处置命令。这与 `unreadable_claim` 是同一类不确定性，**用同一个 severity**——现在 `gate` 只保留 `unreadable_claim`/`duplicate_task_id` 两种 blocking（`claim_conflicts.py:271-273`），`invalid_scope` 被丢掉了（这是 F-06）。

**验收**：`r04_claim_orphan_dir.py` 复跑，三处输出必须一致地指向 `claim_record_torn`。

## F-06 `analyze()` 与 `gate()` 不许给出相反结论

**缺陷**：同目录同秒，`analyze` → `CONFLICT / write_allowed=false / exit 3`，`gate` → `ALLOWED / exit 0`。原因是 `gate` 只把 `unreadable_claim`、`duplicate_task_id` 算作 blocking，`invalid_scope` 被丢弃。

**修法**：把「哪些 kind 算 blocking」提成**一个常量**（`BLOCKING_KINDS`），`analyze()` 与 `gate()` 都读它。现在这条规则写了两遍、且不一致——**这是本项目「第二套并存标准」的最小实例**。

**验收**：新增测试断言 `analyze().write_allowed == gate().allowed`，**对每一种 conflict kind 都成立**。这是唯一能防止下次再漂移的写法。

## F-07 `sent_at` 必须是投递时间，handoff 必须带走未 ACK 事实

两条同源（都是「回执描述了一件没发生的事」），同批修。

**F-07a `sent_at`**：`verdict()` 把 `order["created_at"]`（下单）写进 `sent_at`。一个 `DEFERRED` 单排队 3 小时，一投递就 `over_limit: true`，告警正文写「已经等了 180 分钟」。修法：取 `attempts[-1].at` 中**证明字符到达**的那条（`MESSAGE_VISIBLE`/`INPUT_SUBMITTED`）；没有则回退 `created_at` 并在字段旁标 `sent_at_source: "deposit"`。**同时**：`hold_alerts._message_id` 派生自 `sent_at`，`sent_at` 一旦变成投递时间，「hold 清掉又回来」才会产生新 id——现在它被 `_write_once` 永久压掉，而 `hold_alerts` 的 docstring 承诺会重新告警。

**F-07b handoff**：`CommanderAdapter.order_for_task` 只返回发给**本 agent** 的最新订单；handoff 后 owner 变成继任者，闸门问的是继任者那张**从未发送**的单 → `not_sent` → 放行。实测 `enforce` 下 step 3 直接 `closed=[execute, complete, not_sent]`，而原始订单仍是 `MESSAGE_VISIBLE` / 从未 ACK。

修法：`switch_agent` 时把「上一任那张单 + 它的 verdict」写进任务节点的 `inherited_unacked` 字段；`supervisor._ack_blocks` 在问继任者之前**先看这个字段**，有未 ACK 的前任单就**继续按那张单判**。回执里的 reason 不许再出现 `not_sent` 指代一张 `MESSAGE_VISIBLE` 的单——那是可证伪的假话。

**验收**：`r08_sent_at_is_deposit_time.py` 复跑 `waited_seconds` 必须为 0、`over_limit: false`；`handoff_bypass_e2e.py` 复跑 step 3 必须 `held=[hold_unacked/...]`，不许 `closed`。

## F-08 `artifact.sha256` 改成真的 SHA-256

**缺陷**：`snapshot.artifact()` 写的是 `digest({"bytes": path.read_bytes().hex()})`。实测与 `hashlib.sha256(bytes)` 不等（`fa162c6e…` vs `51bc0fc1…`），任何按字段名核对的人得到 `TAMPERED`。

**修法**（三步，缺一不可，见 `DEBATE_20261101` 冲突四）：

1. `sha256` = 真文件字节摘要；
2. 旧值另存 `digest_json_wrapped`，字段旁注明「对 `{"bytes": hex}` 再取的摘要，为兼容 ≤v0.6.15 的锚点保留」；
3. `snapshot.verify()` 两种都认，**且报告里说明认的是哪一种**。不许把「两种都能过」写成「校验通过」。

**验收**：`r07_artifact_sha256.py` 复跑 `equal = True`；新增测试断言旧锚点（带 `digest_json_wrapped`）仍能通过，且 `verify()` 报告里出现它认的是 legacy。

## F-10 派发栅栏写到一个被读的地方

**缺陷**：`_mark_dispatching` 先写 `commander/state/<id>.json`，再写 `commander/inbox/<id>.json`；而所有判定逻辑只读 `inbox/`（`state/` 只有 `delivery_audit.py` 读）。两次写之间被杀 → `inbox` 说 `DEPOSITED`、`state` 说 `DISPATCHING` → `_preinput_retryable()` 返回 `True` → **同一单被再敲一遍**。

**修法**：栅栏写到 `inbox/`（被读的那个），`state/` 保留为审计副本；两次写之间必须能恢复——**先写 `inbox` 的 `DISPATCHING`，再写 `state/`**。顺序反过来就是现在的缺陷。

**验收**：`r11_fence_split_across_two_files.py` 复跑 `_preinput_retryable(inbox) = False`。

## F-11 认领失败不许继续派工

**缺陷**：`assignment.assign` 的 docstring 说它「writes all three in one call」（存在性/归属/接受）。第 2 步 `claim()` 失败时只往 `evidence` 追加 `claim:scope_conflict`，**不 return、不抛**，继续下单并把任务置 `running`。实测：任务 `owner=alpha`，`src/app.py` 的 claim 属于 `gamma`，而 `supervisor.step` 第 3 步自己写着「work that cannot be written must not be dispatched」。

**修法**：`claim.claimed is False` → 任务置 `blocked`、**不投递**、回执 `action: "blocked_claim_refused"`。`evidence` 里那行 `claim:scope_conflict` 现在没有任何判定逻辑读它——**写进证据但没人读，等于没写**。

**验收**：`r10_assign_ignores_claim_refusal.py` 复跑 `orders deposited = 0`、`task.state = blocked`。

# P3：CLI 契约与文档对齐

## F-12 CLI 的拒绝语义

| 缺陷 | 实测 | 修法 |
|---|---|---|
| A-05 | 880 处 `ValueError` vs 142 处 `ProtocolError`，`main()` 只捕后者 → 86% 的拒绝以 traceback + exit 1 逃逸，而文档承诺 exit 2 | `main()` 增加 `except ValueError` → `print("refused: ...")` + `return 2`。**不许**把 `ValueError` 改成 `ProtocolError`（880 处，改不动且会掩盖真 bug）；在 `except` 里保留 `--traceback` 开关给调试 |
| A-06 | `--agents ""` 静默扇出到 7 个内置客户端（含 `process`/`exe` 皆空的幽灵条目 `"agents"`），exit 0 | 显式空列表 → 报错 exit 2，**不许回退到 `known()`**；`client_registry.BUILTIN` 里删掉或补全 `"agents"` 这个幽灵条目 |
| A-07 | `--workspace "bad id"` 被静默忽略，另建新工作区，exit 0 | 显式给了 workspace 就校验；不合法 → exit 2 |

**一条通则**：**「用户显式给了一个值」和「用户没给值」必须是两条路径。** A-06/A-07 都是把「给了但给错了」当成「没给」。

## F-13 schema 文件名与大小写折叠

**A-08**：20 个 schema 名 vs 7 份文件，且 7 份里 0 份能按名解析（文件名无 `aep-` 前缀，`const` 有）。**改文件名，不许改 `const`**——`const` 已写进所有已发布事件的 `schema` 字段，改它是伪造。同时把 `execution-provider-catalog-v1` 的 `$id` 从 `.dev` 改成 `.local`（`.dev` 是真实 TLD 且强制 HTTPS，其余六份都是 `.local`）。

**R-14**：`overlaps()` 无条件 `.lower()`，POSIX 上 `src/A.py` 与 `src/a.py` 被判冲突，`gate` 返回 3，而 CI 矩阵一半在 ubuntu。**升级为静默失效级**（见 `DEBATE_20261101` 冲突六）。修法：`overlaps(left, right, *, casefold: bool)` 无默认值强制表态；`analyze(..., casefold=None)` 按 `os.name == "nt"` 推断，**并在报告里写出 `case_sensitivity`**。报告说出自己的假设，判定就是可审计的；不说，就是假话。

**验收**：新增测试断言 ubuntu 上 `overlaps('src/A.py','src/a.py', casefold=False) is False`，Windows 上 `casefold=True` 时 `True`，且 `analyze()` 报告里 `case_sensitivity` 与实际判定一致。

# 第二轮：SRE 视角补入（F-14…F-19）

红队和我的探针都在问「它说的是不是真的」。SRE 问的是另一个问题：**半夜三点被叫起来时，我能不能在三条命令内知道发生了什么。** 下面六条，没有一条会说假话，但它们合起来的效果是「你找不到它在说假话」。

## F-14 `federate status` 必须能回答「工作区现在是活的还是死的」

**缺陷（S-11，我复验过）**：把 `events.jsonl` 尾行截半（断电/磁盘满的常态）：

```
--- federate status ---
exit=0                     ← 看起来完全健康
--- federate serve (one tick) ---
exit=1
json.decoder.JSONDecodeError: Unterminated string starting at: line 1 column 213
--- can I repair it with the CLI? ---
exit=2
protocol error: only a blocked task can be revived; this one is pending
```

唯一能发现坏链的 `EventLog.verify()` 全仓库只有一个调用点 `engine.recover()`，而 `recover()` **没有任何 CLI 入口**。

**修法**（`cli.py` 的 status 分支 + `federation/store.py`）：

1. `status` 无条件调用 `EventLog.verify()`，输出新增 `chain: {valid, events, head, reason}`。**这一步是纯接线**——函数已经写好、已经正确，只是没人调它。
2. `status` 新增 `supervisor: {pid, last_tick_at, ack_policy, interval}`，以及 `alerts: {enabled, kernel_backlog, undelivered}`。
   - `ack_policy` 尤其重要（S-08）：现在「没告警」和「告警被关了」在输出上完全一样。
   - `alerts.kernel_backlog` 是「没人读的信箱里堆了多少」（见 F-20）。
3. `status` 新增 `released_unacked_count`：从完成回执里聚合「放行但未确认」的订单数。
   **这一条是 S-08 的真正解药**：`record` 下不告警是**有理由的**（见 `DEBATE_20261101` 冲突八的更正），但「这一版放行了 47 张没有 ACK 的单」这个事实必须是一个能一眼看到的数字，而不是散在几千份回执里。
4. `status` 新增 `stuck[]`：把任务与订单按 `task` 字段 join，列出「`state=running` 但订单 `MESSAGE_VISIBLE` 超过 N 分钟」和「`blocked` 且原因不是 abandonment」两类。**这两类正是需要人动手的全部情形。**
   - 每项必须给**两个**时间戳：`order_age`（从下单算，不因重试刷新）与 `last_agent_evidence_at`（最后一次来自 agent 的证据：ACK 或产物回读；没有就是 `null`）。**不许用订单文件的 `updated_at`**——它会被 `DEFERRED` 重试每拍刷新，于是永远不卡（S-07 实测）。
5. `adapters[].source` 标出每个 adapter 的名字从哪来（见 F-18）。
6. 所有时间字段旁边加 `at_local`（见 F-17）。

**退出码**（见 `DEBATE_20261101` 冲突九）：`0` 读到了且健康 / `2` 我拒绝执行 / `3` 读到了但对象不健康。**不许把坏链报成 exit 0**——SRE 的实测就是「绿色的体检报告」，而人会相信退出码。

**验收**：`repro.py truncated` 复跑，`status` 必须 `exit == 3` 且 `chain.valid: false` + `reason: "torn line at seq N"`。

## F-15 `federate list`：没有它，每条命令都在猜

**缺陷（S-01）**：每条命令都要一个 24 位随机 `workspace_id`，而**没有任何命令能列出工作区**（`grep -rn "iterdir\|list_workspaces" src/` 零命中）。`federate status` 不给 `--workspace` → exit 2；拼错 → 裸 `ValueError: invalid workspace_id` traceback。三个工作区就是三次猜，且无法判断哪个是活的。

**修法**：新增 `federate list`，扫描 `workspaces/*/state.json`，每行一个：`{id, created_at, paused, tasks: {total, running, blocked, done}, last_event_at, chain_valid}`。`chain_valid` 直接复用 F-14 的 `verify()`。

**为什么这条排在这个位置**：F-14 让单个工作区可诊断，F-15 让「我该诊断哪一个」可回答。**没有 F-15，F-14 的输出也没有入口。**

## F-16 `revive --force`：给「非放弃型 blocked」一条出路

**缺陷（S-06，我复验过）**：单个 agent、它不回话（真实世界最常见的失败），完整路径是：

```
tick1  running
tick2  blocked / "no capable successor agent"     ← 15 分钟后
revive exit=2  "this task is blocked for another reason (not an abandonment);
                clear that reason instead of reviving it"
```

**而这个 CLI 里没有 clear 命令。** 唯一出路是 `vim state.json`。更糟的是事件是 `handoff_blocked` 不是 `task_blocked`，`grep task_blocked` 会漏掉。

**修法**：`revive --force --reason <text> --by <name>`，跳过「必须是 abandonment」的检查，回 `pending`、清 owner、写 `task_forced_revive` 事件（带 `previous_state` / `previous_blocked_reason` / `previous_owner`），并按 `blocked_by_deps` 重开下游。

**这不是「放宽」，是「把已经存在的动作变得有记录」。** 现在人已经在 `vim state.json` 了——那个动作没有签名、没有原因、没有事件，事后完全不可审计（S-15 实测：手改不留痕）。**给一个没记录的逃生口加记录，比留着一个没记录的逃生口安全。**

配套：`revive` 的错误信息必须列出**可用的 reason 值**和**对应的正确命令**，不许只说「clear that reason」而工具不支持 clear。

## F-17 时间戳：排查时不能差 8 小时

**缺陷（S-16）**：全部 UTC，无本地渲染。本机 UTC+8，凌晨 3 点（11-02）排查，日志每行写的是 11-01。SRE 的原话值得记下来：**「凌晨三点的人看到日期是昨天，第一反应是日志没更新。」**

**修法**：所有人类可读输出（`status` / `list` / 告警正文 / `stuck[]`）保留 UTC 原值**并**加一个 `at_local` 字段（`datetime.astimezone()`）。机器可读的 JSON 顶层字段**不改**——改它会破坏所有既有解析。

**一条硬规矩**：`at_local` 必须带时区偏移（`+08:00`），不许只写本地时间。一个没有偏移的本地时间在两个时区的机器之间比 UTC 更难读。

## F-18 两套硬编码的 agent 名单

**缺陷（S-02）**：`federate status` 不带 `--agents` 时用 `client_registry.BUILTIN`（7 个）编 adapter，而真实 owner `alpha` 不在里面；`coord-status` 用的是另一批 7 个（`AGENTS` 常量）。**两个世界观。**

**这是本项目「不写第二套并存标准」这条规矩的最小实例**，也解释了 A-06（`--agents ""` 扇出到 7 个）为什么难发现——两套名单各自都「看起来对」。

**修法**：`AGENTS` 删掉，统一到 `client_registry`。`status` 的 `adapters[]` 每项带 `source: "registry" | "explicit" | "workspace_owner"`，并且**当 owner 不在 registry 里时，必须出现在输出里并标 `source: "workspace_owner"`**——不许因为「名单里没有」就不显示。一个不在名单里的 owner 是最需要被看见的那个。

## F-19 心跳不能追不上自己

**缺陷（S-13，两次独立测量，数字不一致——两个都留）**：单拍耗时 O(任务 × inbox)，而默认 `interval` 是 30 秒。cProfile 定位：`CommanderAdapter._orders()` 每个任务全量扫一遍 `commander/inbox`（100 任务读 5056 个文件，占 14/17 秒）。而 inbox **没有归档命令**，所以 `n` 是「历史总任务数」。

| N | SRE 实测 | 主程实测（`.tools/probes-0616/scale_lead.py`） |
|---|---|---|
| 25 | — | 3.32 s |
| 50 | 5.95 s | 7.14 s |
| 100 | 49.21 s | 18.94 s |
| 200 | 164.09 s | 64.64 s |

**两个数差 2.5 倍，我不选一个当结论。** 能同时成立的只有三件事：

1. 增长是**超线性**的（我的 50→100 是 2.65×，100→200 是 3.4×；近似二次）；
2. 按二次外推，撞上 30 秒默认 interval 的交叉点，我的数据约 **N≈137**，SRE 的约 **N≈85**；
3. 所以「**一两百个任务就会让心跳追不上自己**」这个结论**不依赖选哪一组数**。

差异原因未查明（可能是 `--no-dispatch` 下订单仍落盘但未投递，导致 inbox 文件数与 SRE 不同；也可能是机器负载）。**在查明之前，方案里引用「交叉点在 60–70 个任务」（SRE 早先的说法）这个数是不允许的**——那是最悲观的一组，且与它自己后来的数据不一致。

**心跳周期比心跳本身短**——这是自我否定的设计。

**修法（分两步，第二步要 SRE 的等价性证据）**：

1. **确定可做**：`coord-archive-orders`（把 `state` 为 `DONE`/`ABANDONED` 且超过 N 天的订单移入 `inbox/.archive/`，**移动不删除**），使 `n` 只与「活任务数」相关。这一步不改变任何判定语义。
2. **需验证**：`_orders()` 每拍只扫一次建索引。**我已要求 SRE 给出等价性 diff**：同一 agent 多张单时「取最新」的语义是否在批量化后仍然成立。**在拿到 diff 之前，这一条不进实施范围**——「快」不是理由，「快且同样正确」才是。

**顺带一条**（S-12）：`serve` 每拍全量打印，200 任务 68 MiB/天、1000 任务 340 MiB/天，而写满盘会杀死 serve——形成「日志写满盘 → 进程死 → 重启 → 继续写」的自噬链。`serve --log-level` 默认改为 `quiet`（只打印状态变化，不打印每一拍）。

## F-20 最危险的动作不该是默认动作，最安静的信箱不该没有数字

**缺陷（SRE 的 Q3，两半）**：

- `hold_alerts` **不往窗口打字**，只 `mkstemp+fsync+os.replace` 写文件（`hold_alerts.py:276`）。客户端坏了它照样送达——**这是设计对了的地方，不许动**。
- `coord-send --kind warning` **默认打字**（`cli.py:580`），`--mailbox-only` 才是退出。往一个人的桌面窗口里打字是不可逆副作用，它必须是显式选择。
- `event_id` 匹配不上时静默落到 `messages/kernel/`，agent 名变 `unknown`。SRE 的原话：**「告警不会丢，会安静地待在 `messages/kernel/` 里，而 `kernel` 不是一个人。」**

**修法**：

1. `coord-send --kind warning` 默认改为**只写信箱**，要打字必须显式 `--dispatch`。
2. 翻转那一版，凡用到 `--kind warning` 又没给 `--dispatch` 的调用，往 stderr 打一行「从本版起不再往窗口打字；需要打字请加 `--dispatch`」。**一行，保留一个版本，然后删掉。**
3. `kernel` 不许作为静默兜底：告警仍写入（**不丢**，这条对），但 `status` 必须显示 `alerts.kernel_backlog`——**一个没人读的信箱，必须有一个数字让人看见它在堆积**。
4. 新增 `serve --alert-to <name>` 指定真人收件人。

**一条要写进文档的区分**：**「没丢」不等于「送达」。一个文件躺在磁盘上，和一个通知被送到人手上，是两件事，而系统现在把前者报成后者。**

**验收**：`repro_alert.py` 复跑，无 `--dispatch` 时窗口无输入且 `desktop_delivery` 字段不存在（不是 `state: "skipped"`）；`kernel` 兜底时 `status.alerts.kernel_backlog > 0`。

## F-21 `state.json` 要有自己的锚

**缺陷（A-04 / R-06 / S-15，三条从三个方向指向同一处）**：`events.jsonl` 有 hash chain，`state.json` 没有 `sha256`、没有 `digest`、没有 `prev`——**而它才是决定系统下一步做什么的文件**。实测：手改 `t0000 -> done`，`verify()` 仍 `{'valid': True, 'head': 'a9ddfe37…'}`，head 一模一样。

**修法**：

1. 每次 `save()` 后追加一条 `state_anchor` 事件，payload 是 `state.json` 规范化序列化后的 SHA-256。
2. `recover()` 比对「最新 `state_anchor` 的摘要」与「磁盘上 `state.json` 的实际摘要」；不一致 → `valid: false, reason: "state edited outside the engine"`。
3. 重放器认 `task_forced_revive`（F-16）为合法转移——**`--force` 和 `vim` 做的事一样，区别只在于一个留了记录**。
4. **文档措辞收窄**（见 `DEBATE_20261101` 冲突十三）：所有引用 hash chain 的地方，必须同时写出它**不覆盖** `state.json`。一条硬规矩：

   > **可检测性的对象是事件，不是状态。**

   一个安全性质的表述，如果不写清边界，就会被当成比它更强的保证使用。

**验收**：`repro.py edit` 复跑，手改后 `recover()['valid'] is False`；而 `revive --force` 之后 `recover()['valid'] is True`（因为它写了事件）。**这两条必须同时成立**——只做到第一条，就是把人赶回 `vim`。

## F-22 新克隆的写命令会落进**原作者**的协作目录

**缺陷（N-01，我复验过）**：`.aep/workspace.json` **是入库文件**（`git ls-files .aep/` 有它），内容是硬编码绝对路径：

```json
{"coord_root":"K:\\PythonProjects5\\agent-evolution-protocol\\coordination",
 "kernel_root":"K:\\PythonProjects5\\agent-evolution-protocol\\.aep-kernel",
 "workspace":"K:\\PythonProjects5\\agent-evolution-protocol", ...}
```

而 `coordination/` 与 `.aep-kernel/` 都在 `.gitignore` 里（`.tools/` 也是，`git ls-files .tools` = 0）。`configured_root()`（`cli.py:190`）拿到 `coord_root` 后，**只要是绝对路径就直接用**：

```python
path = Path(config.get(key, default))
return path if path.is_absolute() else workspace / path
```

复验（在一个**只有** `.aep/workspace.json` 副本的无关目录里）：

```
cwd                = C:\Users\love\AppData\Local\Temp\n01probe
configured coord   = K:\PythonProjects5\agent-evolution-protocol\coordination
configured kernel  = K:\PythonProjects5\agent-evolution-protocol\.aep-kernel
```

**任何不带 `--coord-root` 的写命令（`coord-claim` / `coord-send` / `coord-wake`）都会写进原仓库。** 在新机器上则指向一个不存在的 `K:` 路径——要么失败，要么**被创建出来**，然后所有人共用一个 coordination。

**为什么进 P0**：这不是文档问题，是「这个仓库能不能被别人用」的问题。**如果修好 F-01…F-21 之后别人 clone 下来仍然往我的目录里写，那这个修复成果无法被任何人安全采用。**

**修法**：

1. `.aep/workspace.json` **出库**（`git rm --cached`），加进 `.gitignore`；改为入库一份 `.aep/workspace.example.json`（相对路径 `coordination` / `.aep-kernel`）。
2. `configured_root()` 对绝对路径做**归属校验**：若 `coord_root` 是绝对路径且不在当前 `workspace` 之下，**拒绝并报错**（exit 2），错误信息说明「配置指向另一个工作区；用 `--coord-root` 显式指定，或改成相对路径」。**不做静默回退**——静默回退就是现在这个缺陷。
3. `aep doctor` 增加一项 `workspace_config_is_portable`：检查配置里有没有指向别处的绝对路径。

**验收**：新增测试——在临时目录放一份 `workspace.example.json`，断言 `coord_root()` 落在该临时目录内；放一份指向 `K:\...` 的旧配置，断言抛错而不是返回原路径。

## F-23 解释器：`python` 指哪个，全靠运气

**缺陷（N-02 / N-13）**：Git Bash 里 `python -m agent_evolution_protocol` → `No module named agent_evolution_protocol`，`python -m pytest` → `No module named pytest`；PowerShell 里两条都正常（`python` 是 `D:\A\python` 3.13.9）。**87 份文档没有一处说明。** 另有 `pip show` 报 0.2.0 而 `pyproject.toml` 报 0.6.15，且没有 `--version`。

**修法**：README 顶部加一段「60 秒起步」，**钉死解释器绝对路径**（本项目自带的 `.tools/agent-runtime/Scripts/python.exe`），并给出一条能自证成功的命令。新增 `aep --version`（读 `importlib.metadata`，读不到就回退 `pyproject.toml`）。

**一条纪律**：**文档里凡是出现 `python` 的地方，必须写明是哪一个 python。** 本机 PATH 被 Git/MSYS2 抢占这件事已经踩过一次（`timeout /t` 报 `invalid time interval`），同一个坑不踩第二次。

## F-24 中文 README 停在 v0.5.0，且没有命令索引与术语表

**缺陷（N-04 / N-06 / N-14 / N-23，我复核了 N-04）**：

- `README.zh-CN.md` 最后提交是 `fb6497f release: v0.5.0`，全文**没有版本号字符串**，`coord-improvement` 出现 **0 次**；`README.md` 里出现 13 次、到 v0.6.15。**中文读者读到一份缺 10 个版本的世界。**
- `add_parser` 出现 83 次，其中大量子命令在两份 README 里一次都没出现，**没有命令参考文档**。

**修法**：

1. 中文 README 与英文 README **同一版发布同步更新**，并在文首写明对应版本号。**没有版本号的中文文档比没有中文文档更危险**——它看起来是权威的。
2. 新增 `docs/COMMANDS.zh-CN.md`：从 `argparse` **生成**，不手写（手写的一定会漂移，这个项目已经证明过）。

4. `hold_alerts.py:12` 的旧命令名改掉。

## F-25 有一条偶发失败的测试，而测试数闭合纪律依赖「测试全绿」

**缺陷（N-11，NEWHIRE 实测，主程未独立复现）**：同一条全量命令跑 5 次，1 次 `1 failed, 1058 passed`；定位到 `test_campaign_watcher_integration::test_file_event_reconciles_expired_assignment`（起 pwsh 子进程 + 20 秒墙钟 deadline）。4 文件批量 9 次挂 1 次，单跑 6 次全过。

**我自己的部分**：单独跑该文件 1 次 → `1 passed in 5.51s`，与 NEWHIRE「单跑全过」一致。**全量下的偶发我未独立复现**，所以这里只记「NEWHIRE 报 1/5，我单跑 1/1 通过」，不写成「确认偶发」。

**为什么必须修**：本项目的发布纪律是「测试数逐文件闭合」。**一条偶发失败的测试会让这条纪律失去意义**——一次红会被当成「又抖了」，于是真正的红也被当成抖动。这是纪律的自我腐蚀。

**修法**：把「墙钟 deadline」改成「子进程退出即判定 + 总超时只作为兜底」，或把该测试标 `@pytest.mark.flaky` 并**记录抖动率**。**不许直接删**——删掉它，「偶发」就变成了「不知道」。

# 第二轮之后仍未被覆盖的

诚实记账，这些**没有**进任何批次：

| 未覆盖 | 原因 |
|---|---|
| 真实桌面投递链路（UIA 打字、`_profiled_deliver`、`cdp.deliver`） | 需要 pwsh + 真实客户端窗口；不该在审计里碰用户桌面 |
| `ui_fallback.agent_accepted` 是「挑战应答」还是「屏幕上看到 token」 | 若是后者，就是「自己的请求被当成回复」的翻版。**红队主动标为未验证猜测并未写进发现列表，这个克制是对的**，我按同一标准处理 |
| 两种完整性级别同时访问同一目录 | 本机无法构造，SRE 明确拒绝给结论 |
| 1000 任务单拍真实耗时 | SRE 上次被 300 秒超时掐断，已要求重测 |
| 跨机器 / 网络文件系统 | 完全未测。`workspace_lock` 的语义在网络盘上是否成立，未知 |

**这一节比上面任何一节都重要。** 一份审计报告的价值不在于它找到了多少条，而在于它说清楚了**哪些地方它没看**——否则读者会把「没被列出」当成「没问题」。

## 发布与验证纪律

1. **P0 一次发布，不许拆。** F-01 单独发布会让 F-02 从潜伏变活跃。
2. 每个 F 的验收必须是**复跑 `docs/audit/repro/` 里的脚本**，不是「测试通过」。测试通过在本项目里已经被证明过不能说明问题——1061 个测试全绿时，A-01 让整条证据链是死的。
3. 测试数变化必须逐文件闭合（收集数 = 旧数 + 新增数 − 删除数），删除必须有解释。
4. 发布说明必须写**更正声明**：v0.6.12–v0.6.15 关于 ACK 的讨论建立在「`role == "assistant"` 会出现」这个不成立的前提上。用户当时说「不强制了，万一有特殊情况」——直觉对，但原因不是「规则太严」，是「规则的前提在现实中不存在」。
5. 每批修完，`docs/audit/repro/` 里对应的脚本要作为**回归证据**保留，并在脚本头部写「这条脚本在 vX.Y.Z 上输出 A，在 vX.Y.Z+1 上应输出 B」。**不许删探针**——探针是本项目唯一能证明「我们修的是真问题」的东西。

## 这份方案自己也有风险

诚实地写三条，因为一份只说「照这个做就好了」的方案不可信：

1. **F-01 是本次改动里唯一可能「修出新缺陷」的**。把 `role != "assistant"` 换成三分支判定，等于重写 ACK 的准入条件。若「己方正文」的比对写得不够严（例如只做前缀匹配、或没处理空白与换行差异），自回显会重新变成合法 ACK——而那时**它看起来是通过的**，比现在更危险。**因此 F-01 必须配一条反向测试，且该测试要在「订单正文被 publish 两次」的情况下仍然拒绝。**
2. **F-04 让 `recover()` 变严，会让所有存量工作区在升级后立刻报红**（历史丢写已经发生）。这是正确的，但如果没给 `--accept-divergence`，运维的第一反应是回滚版本——**于是修复被回滚，而不是缺陷被接受**。
3. **F-19 的批量化（`_orders()` 每拍只扫一次）在拿到等价性 diff 之前不许动。** 「快」不是理由。一个更快的、偶尔返回另一张订单的调度器，比一个慢的调度器危险得多——因为慢是可见的。

**如果只能修三件**：F-01 + F-02（同批，否则互相引爆）、F-03（唯一不可逆损失）、F-22（否则修好也没人能安全用）。
