# 双通道唤醒与回表验证

协议通道不是唤醒事实。它可能只代表消息写入队列、连接已建立或服务端返回成功；Qoder CN 等桌面 Agent 仍可能没有切换到原会话、没有开始生成或已经卡住。

## 双通道模型

```text
协议通道：低延迟发送、房间广播、投票、ACK
       │
       ├─ 协议 ACK：只证明接收方协议层处理了事件
       │
GUI/UIA 通道：窗口、原会话、输入框、生成状态、可见回复
       │
       └─ GUI 回表：证明 Agent 界面实际被唤醒并执行
```

## 统一状态

| 状态 | 证据 | 是否可继续 |
|---|---|---|
| `PROTOCOL_SENT` | socket/HTTP 写入成功 | 不足以证明唤醒 |
| `PROTOCOL_ACK` | Agent 返回事件 ACK | 仍需确认是否执行 |
| `GUI_SESSION_ACTIVE` | 原窗口、原会话已定位 | 可准备输入 |
| `GUI_MESSAGE_VISIBLE` | 点击发送后消息出现在会话记录 | 已实际投递 |
| `GUI_EXECUTING` | UI 出现生成/工具执行状态 | 已开始执行 |
| `RESULT_VERIFIED` | 回复、文件或外部结果经独立读取确认 | 完成 |

## 冲突处理

- 协议成功、GUI 无变化：标记 `WAKE_UNPROVEN`，不宣布唤醒；重新观察一次后转 UIA 重试或人工接管。
- GUI 已显示消息、协议无 ACK：标记 `DELIVERED_ACK_PENDING`，等待目标回执，不重复发送。
- 两边都成功但结果不一致：冻结后续动作，保留两侧证据，交给仲裁 Agent。
- GUI 发现错误弹层：暂停协议重试，按弹层策略处理后再恢复。

## 设计原则

GUI 不是低级备用方案，而是协议黑箱的独立观测器；协议也不是 GUI 的替代品，而是低延迟协作总线。只有两侧证据组合，才允许把“唤醒并执行”升级为已确认。
