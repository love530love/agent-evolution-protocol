# 小白用户的多日无人值守任务审计

## 结论

AEP 已具备“任务图、持久化 checkpoint、事件日志、会话注册、通道降级、ACK
租约、死信和监督脚本”等基础，因此可以承接复杂长任务；但不能把“启动了
supervisor”误称为“几天后必有结果”。生产完成的判据必须是最终 artifact、验收
记录和可追溯事件链都存在。

## 从一句话到交付的闭环

1. `intake`：把自然语言目标解析为 deliverable、期限、预算、禁止事项和成功标准。
2. `plan`：生成依赖图，按研究、实现、验证、发布拆分，给每个节点指定负责人和备用人。
3. `claim`：Agent 认领节点并注册工作区/会话，冲突时停止而非抢占。
4. `execute`：通过最佳 transport 唤醒，写入 event_id 和 checkpoint。
5. `accept`：收到同 event_id ACK 后才推进；产物必须落到共享工作区并通过验收。
6. `recover`：超时切换备用通道/负责人；高风险动作进入仲裁；超过上限进 dead-letter。
7. `resume`：机器或 Agent 重启后从最后 checkpoint 恢复，不重放已确认副作用。
8. `deliver`：汇总最终产物、证据、失败节点、剩余风险，并通知用户。

## 无人值守前必须满足

- 至少一个在线 hub 和一个备用 hub；
- 每个阶段都有 checkpoint 和可验证产物；
- 预算/额度/时间上限已写入任务；
- 外部副作用有 operation key 和人工仲裁规则；
- supervisor、事件目录和工作区路径可写；
- 关键 Agent 至少有两种唤醒 transport；
- 最终交付条件不是“所有 Agent 回复”，而是验收器通过。

## 仍需继续开发的缺口

- 自然语言 intake 到任务图的安全解析器；
- 多日预算、配额和时间窗调度器；
- 统一 artifact 验收器与最终报告生成器；
- supervisor 重启后的自动恢复演练；
- 用户可视化进度页和“只在需要人处理时”通知；
- Qoder/WorkBuddy/QClaw 的真实回合适配器。

因此，对小白用户应提供一个入口：`aep mission start --goal "..."`，其余由系统
自动规划、分工、唤醒、监督和交付；只有登录、权限、歧义或高风险外部操作才请求用户。
