# AEP 风险登记与控制基线

“消除隐患”在工程上意味着把风险变成可发现、可阻断、可回滚的状态，而不是声称风险为零。每项高风险变更都必须留下证据和责任边界。

| 风险 | 可能后果 | 当前控制 | 继续演化方向 |
|---|---|---|---|
| 许可证/NOTICE 遗漏 | 侵权、无法再分发 | Provider 默认 `unverified + reference-only`；保留上游链接；发布前核验 LICENSE | 锁定来源提交号、许可证文本哈希和 NOTICE 归档 |
| 供应链依赖被替换 | 恶意代码、构建漂移 | 隔离虚拟环境、pip check、依赖候选与审计门 | 为每个运行时生成 wheel/hash lock |
| 错误窗口/会话 | 把指令发给错误 Agent 或账户 | WorkspaceID、session anchor、readiness、事件 ACK | 加强 PID/窗口/浏览器 Target 三重绑定 |
| “已输入”冒充“已发送” | 任务假完成、额度浪费 | `MESSAGE_VISIBLE → AGENT_ACK → RESULT_VERIFIED` | 统一所有 Provider 的回读适配器 |
| 任意命令/桌面动作扩大影响 | 数据破坏、越权操作 | workspace lease、Provider 隔离、操作审计、显式生产验收 | 默认 dry-run，危险动作需要独立验收证据 |
| Token、登录态、模型权重泄露 | 账户接管、隐私泄露 | 不入库、不打包、不写日志；本地运行时在 `.tools` | Secret 引用与脱敏扫描进入 CI |
| 第三方模型/服务条款变化 | 任务中断、数据出境 | 目录中记录限制，Provider 状态可退役 | 增加条款/版本变更事件和降级路由 |
| 多 Agent 趋同或互相覆盖 | 整体能力平庸、返工 | 红皇后、鲶鱼、创造性破坏、独立证伪 | 把反证预算和独立性写入任务 Schema |
| 自动重试造成重复副作用 | 重复提交、额度耗尽 | event_id 幂等、状态门、未知回执停火 | 统一 `retry_class` 与外部副作用保护 |
| 版本号/发布物漂移 | 无法复现或回滚 | 版本一致性测试、tag、wheel 构建、CHANGELOG | CI 强制 tag 与包元数据一致 |

## 发布前必须回答的五个问题

1. 这次变更是否引入新依赖、模型、资产或上游代码？
2. 每个来源的许可证、版本/提交号和 NOTICE 是否可核验？
3. 是否有真实的会话/窗口/设备绑定和同事件回执？
4. 失败时能否只回滚本次 Provider/策略，而不破坏工作区？
5. 是否保留了独立的鲶鱼反证和可重复测试？

如果任一问题没有证据，发布状态必须保持 `HOLD`，不能用口头承诺替代。
