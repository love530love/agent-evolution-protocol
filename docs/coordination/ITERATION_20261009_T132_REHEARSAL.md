# 协作闭环迭代：T132 隔离演练

日期：2026-10-09。T124 的提交窗口已关闭，因此不再用它做执行验证。本次用第 9 批 T132 作为任务标识，在临时目录演练协作状态；**没有认领真实 T132，没有唤醒桌面代理，也没有上传或提交代码**。

## 本轮修复

1. 唤醒冷却仅对同一 `agent + task` 生效。此前只按 agent 去重，可能把同一代理的另一道新赛题误标为已处理。重复唤醒现在记录 `duplicate-wake` 与首个事件 ID；不同赛题继续派发。`adapter-executed` 仍只证明适配器运行，不证明代理接单。
2. `coord-task-state` 和兼容桥的 `task-state` 在写入前核对原子认领文件。若认领者不同，拒绝覆盖任务状态；认领目录尚未写完时也拒绝。接管必须先经正常释放/移交流程，不能靠改状态绕过。
3. `inspect` 显示认领与状态拥有者冲突，以及超过接单截止时间的唤醒回执。过期只触发人工诊断，**不自动重复唤醒**，避免不确定结果的重复执行。

## 验收证据

- T132 隔离演练：WorkBuddy 认领后，Qoder 的 `working` 状态写入被 `TASK_CLAIM_CONFLICT` 拒绝；WorkBuddy 可写入。
- T132 与 T130 并发唤醒模拟：同一 WorkBuddy 的 T132 冷却不吞掉 T130；T130 仍调用适配器并产生待接单回执。
- T132 故障注入：人为制造认领/状态冲突和过期回执，巡检器分别报告 1 项。
- 当前竞赛工作区只读巡检：26 条认领、19 条任务状态、3 条历史拥有者冲突（T116、T121、T123）；这不是对这些任务进行自动接管的授权。

## 仍未证明的能力

- 本轮未证明 WorkBuddy/Qoder 在真实桌面会话中接到新任务并作出回执；必须在协作室恢复连通后做有监督的端到端试验。
- 兼容桥与 AEP CLI 仍共享文件格式而非一个统一的事务 API。上传前的 lease/幂等闸门也尚未连接到所有提交入口。
- Hook 同步的是有限事件和摘要，不是跨产品完整聊天历史；后续应加事件游标、消息来源与按需取原文，避免重复灌入模型上下文。
- 红皇后—鲶鱼—创造性破坏目前仍以离线治理卡片为主。官方反证应生成可追溯 `threat`，由独立质疑者验证，并经领导者决议后更新团队假设；不能仅靠自动转发就宣称闭环。

## 下轮建议

先处理 3 处历史冲突的证据核对，不做自动抢占；然后在一个仍开放的新赛题上有监督地验证 `消息 → 原会话唤醒 → ACK/认领 → 状态更新 → 完成回执`。若真实桌面无法可靠注入任务，应明确降级为“通知已发、需人工接单”，不能显示为已执行。
