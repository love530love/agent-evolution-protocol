# AEP 项目审计与可移植开发目标

2026-11-21 · 审计基线 v0.6.43 / `1f1fe51`

## 产品目标

用户从发布包安装 AEP，在任意路径初始化工作区，就能组建团队、发布任务、查看进展和回执。另一台机器可以导入同一工作区的任务、交接与证据索引，再绑定自己的客户端、账号和原会话。团队能力通过版本化任务契约、适配器和验收用例复刻。Windows 桌面操作由适配器承担，能运行 CLI 或调用工具的 Agent 即可参与指挥。

## 审计结果

| 方面 | 当前证据 | 缺口 |
| --- | --- | --- |
| 安装与兼容 | Python ≥3.10，`pyproject.toml` 提供 CLI、MCP 入口和可选依赖。基线 [GitHub Actions](https://github.com/love530love/agent-evolution-protocol/actions/runs/43875638548) 成功 | 发布包在无源码、无旧运行时、不同路径的新机器上的全流程待验证 |
| 工作区复刻 | 已有工作区发现、任务、改进策略、租约与交接模块。根目录 `AEP_JOIN.md` 的操作示例固定本机盘符和历史任务 ID，另有脚本和包内手册引用特定工作站路径 | 可移植安装入口、版本化导入导出和新机手册是首要交付 |
| 实际派工 | 本机 `coord-delivery-audit --summary-only` 汇总 131 条消息记录，其中 4 条到达 `AGENT_ACK`，全部仍需 `ARTIFACT_VERIFIED`。107 条待客户端绑定，20 条待人工或程序核查 | 这是该账本的覆盖情况。尚须逐厂商保存原会话送达、同事件 ACK、结果读回和独立验收证据 |
| 桌面会话 | 严格证明已有入口；`ui_fallback.py` 中严格证明开关默认关闭，`session_fingerprint.observe` 的 marker 来自 profile | 指纹可参与配置匹配。执行准入需要独立的活动会话证据。先验收 Qoder 的 `agent-evolution-protocol → 请加入项目协作区` |
| 常驻和值守 | `schtasks /Query` 显示 CoreHost、DesktopHost 为 `Ready`。同次巡检两个 heartbeat 均过期，提升执行心跳缺失，控制面为 `HOLD` | 查清退出原因，验证登录、重启、断线恢复和进程回收。WebSocket Relay 属于计划 |
| 治理与接管 | 本机改进策略为 `cooperative`。仓库已有接力包、决策审计和阶段校验 | 实测额度中断、执行者掉线和用户接管时的上下文连续性、旧执行者隔离与产物一致性 |

基线工作树含现有 UIA 实现和测试改动以及本地审计材料。远程 CI 结论按上表提交归属，本机检查按当前工作树归属。

本机全量测试为 1808 通过、3 跳过、4 失败（另有 1036 个通过的子测试）。`test_campaign_watcher_integration.py` 的 watcher 子进程在生成就绪文件前退出，启动根因待定位。`test_ui_profile_examples.py` 的 ChatGPT、Qoder、Qoder CN 三个子项依赖本机校准配置，与提交的示例不一致。P0 应改用受版本控制的合成配置测试导出与脱敏，把真实校准对照留给部署验收。值守诊断应在子进程提前退出时保留退出码和启动日志。

## 开发顺序与验收门槛

| 顺序 | 交付物 | 可复验的退出条件 |
| --- | --- | --- |
| P0 安装与初始化 | Core 发布包，通用初始化与诊断入口，版本化最小示例。按项目配置发现根目录，按需安装桌面能力 | 干净 Windows 与 Linux 环境只用发布包，在含空格和中文的路径运行最小演练。操作者无需修改盘符、引用旧任务或使用开发机的 Python 路径 |
| P0 可迁移工作区 | 导出清单、格式版本、完整性校验、导入预检与迁移报告。包含任务、角色、审批范围、交接和经选择的产物 | A 机导出、B 机预检后导入，逻辑工作区和事件 ID 保持稳定，重复导入幂等。新机器重建登录绑定、设备凭据、局部 UI 校准和活动租约。损坏包拒绝导入且目标保持一致 |
| P0 原会话派工 | 共用适配器契约和错误码，接通绑定、探测、投递、观察、结果读回。先测试 Qoder，再测试另一厂商 | 同名会话、错误工作区、被抢焦点和剪贴板内容变化均可识别。成功路径记录原会话证据、消息可见、同事件 ACK、结果与验收。发送结果不明时凭历史核对后再决定是否重试 |
| P1 常驻运行 | 复用现有 Core Host 与 Desktop Host，补进程退出诊断和恢复。按需引入 WebSocket 注册、心跳、重连游标 | 进程崩溃、断网和重启后的队列与回执能恢复。连续 24 小时观察任务延迟、CPU、进程数和子进程回收，记录每次恢复及失败 |
| P1 跨 Agent 接管 | 给 CLI/MCP 客户端统一任务操作和状态查询，固化额度预警与周期性检查点 | 额度耗尽或进程退出后，备用 Agent 能凭持久记录继续未完成节点。旧执行者恢复后无法覆盖新结果。用户接管后队友可通过各自已验证的路线收令并回执 |
| P2 扩展与发布 | 厂商适配器 SDK、样例和能力验收矩阵。沿已验证需求引入 A2A 或 MCP 互操作 | 第三方仅依文档完成一个新适配器并通过契约测试。每个发布版本附构建来源、兼容矩阵、干净安装与迁移记录、实机证据和回滚说明 |

平台支持分级发布。CLI 和协议能力按操作系统与 Python 版本验收。桌面能力按厂商、客户端版本、操作系统和会话绑定分别验收。演示任务采用可复验的本地工件，记录 `安装 → 加入 → 认领 → 投递 → ACK → 产物校验 → 重启恢复 → 迁移` 各阶段结果。每个受支持的平台应有独立操作者从发布制品复跑，保存安装来源、版本、事件 ID、各阶段证据和耗时。

首个开发切片采用现有 CLI，交付一套可从空目录运行的双 Agent 演练和工作区导入预检。并行的实机验收线复用此前的[控制平面与厂商连接器交接](HANDOFF_CONTROL_PLANE_AND_VENDOR_CONNECTORS_20261116.zh-CN.md)，以两个厂商的原会话回执验证演练与真实桌面间的差距。

## 双 Agent 演练入口

安装 AEP 后，从任意目录运行：

```text
aep portable-demo --output "./AEP 演练"
```

每次运行在输出目录内创建独立子目录。演练通过现有联邦内核分派生产和复核任务，读回持久化任务状态，核验产物内容和事件链。报告的 `mode: simulated` 表明执行器为本地模拟适配器。真实桌面回执与跨机器工作区导入预检分别验收。

## 厂商额度接管契约

适配器可以用结构化 `quota_exhausted`、`credit_exhausted`、`usage_limit` 或 `time_limit` 信号报告容量中断。运行中任务可通过心跳报告，桌面监督器可读取终态失败回执里的相同信号。信号应来自可信的厂商状态或绑定原任务的报告。投递结果无法判定时，应保留不确定状态供核对。

联邦内核从工作区快照创建接管包，并按任务能力匹配替补。替补明确因额度拒绝任务时，继续检查剩余合格执行者，每轮跳过已失败的执行者。回执保留每次尝试的状态。桌面适配器接受订单表示排队，原会话消息可见、Agent 回执和结果验收继续走各自的证据链。

## 进程治理与实时插话审计

| 路径 | 代码审计 | 下一道验收门槛 |
| --- | --- | --- |
| Windows 外部执行器 | 先将 worker 加入父进程持有的 Job Object，再启动目标。超时可终止该受控进程树 | 演练退出、强制崩溃、后代继承管道及高频重启，记录每次剩余进程数 |
| 常驻 stdio 适配器 | 退出时等待直接子进程回收，并在重启前释放旧代资源。该路径仍缺进程树托管 | 接入同样的所有权隔离。在父进程崩溃或管道被孙进程持有时验证容器退出与进程回收 |
| MCP 生命周期账本 | 用于记录进程与清理陈旧登记 | 账本应记录启动代际、PID 与创建时间。回收操作只作用于 AEP 持有的进程组或 Job |
| 群聊发布 | `coord-chat-publish` 追加共享事件，消费端使用游标读回 | 显式指定目标成员的指令须生成逐目标派工单。以工作区、源事件和目标为幂等键。逐目标记录排队、发送、回执和超时 |
| 桌面插话 | 紧急单走 profile 专用路径。显式 CDP 紧急单返回可诊断的延期状态 | 实机验证正确会话、当前运行、专用插话控件以及插入后原运行是否继续 |
| 原生插话 | 当前通用派工尚未提供已验收的厂商原生忙碌态插话能力 | 用官方能力绑定原会话 ID 与运行 ID，分别记录接收、何时生效及同运行回执。客户端若只支持下一轮排队，应返回排队状态 |

端到端验收使用两条重叠的运行来覆盖同名会话和抢焦点。为同一群聊指令注入重复事件和断线，在目标会话读回唯一消息并验证同事件 ACK。用时间戳记录入队、发送、运行采纳及回执延迟。针对忙碌态分别验收当前运行接受补充消息、下一安全点接受消息和下一轮排队。

## 用户修订与群聊派工

`aep chat-dispatch --event JOURNAL_ID --workspace-id WORKSPACE_ID --task TASK_ID --target qoder --target workbuddy` 将显式选中的用户消息加入指定目标的派工队列。相同事件和目标重跑会复用订单。订单保留源事件和消息摘要，原会话投递由现有 commander 执行。

下一阶段给每个任务保存当前生效版本及变更历史。每次修订记录操作者、来源事件、适用范围、替代版本和验收条件差异。要求、偏好与临时例外分别记录，临时例外需要明确范围或到期条件。用户明确修订覆盖对应范围。含糊或矛盾的指令若影响不可逆提交，仅暂停受影响步骤，同时继续独立任务。

派工与执行前检查当前版本。尚未发送的旧单停止执行，已发送的旧单追加纠正并单独获取采纳回执。交接摘要保留生效要求、最近变更、未决冲突、已经发生的外部动作和有效产物。验收覆盖旧消息晚到、并发修订、用户改变偏好以及新执行者接管后仍遵循最新要求。
